# Nexus · 一个网页里的软件工厂

> 你在网页上打一句话，它自己走完六道工序，最后交给你一个**能运行、被验收过的软件包**。
> 全程看得见、随时拦得住、花了多少钱清清楚楚。

---

## 一、项目介绍

### 它解决什么问题

现在的 AI 编程工具本质是「对话式」的，有两个要命的问题：

1. **用户是过程的奴隶** —— 得陪着走，一轮一轮喂上下文，写偏了赶紧喊停重开
2. **它是黑盒** —— 跑到一半不知道在干什么、不知道花了多少钱、跑偏了没有后悔药

**长任务一旦在第八步失败，前面投入全废。**

所以真正要解决的不是「少打字」，而是 **长任务不失控**。拆成四个能力：

| 能力 | 含义 | 现状 |
| --- | --- | --- |
| **可观测** | 跑到第三十分钟，我知道它在干什么，每一步花了多少钱 | ✅ 已实现 |
| **可预算** | 设成本上限，超了自动降档，而不是继续烧 | ✅ 已实现（硬闸门） |
| **可干预** | 任务图上任意节点能暂停、能改指令、能从那个点重跑 | ⏳ 进行中 |
| **可恢复** | 崩了不从头开始 | ⏳ 进行中 |

**「可观测」和「可预算」是已经能演示的**：前者对应实时生成流 + 过程回放，
后者对应按次记账与单次运行的成本闸门。
「可干预」和「可恢复」依赖六阶段内核接入 —— 图的骨架已经在界面上，
但节点级操作还没有实际作用，**所以不勾选**。

### 用户

**第一场景**：学生与独立开发者 —— 有想法有需求，但缺工程能力或时间。
**远景**：所有需要把想法变成可运行软件的人。

## 二、技术架构

### 技术栈

赛题要求前端使用 **React / Vue 等**主流框架。本项目采用 **React 19 + Next.js 16**：

| 层 | 选型 | 说明 |
| --- | --- | --- |
| **前端框架** | **React 19.3** | 组件化 UI，服务端组件与客户端组件混合 |
| **全栈框架** | **Next.js 16.4**（App Router + Turbopack） | 同一个工程承担页面、API 路由与流式接口 |
| 样式 | Tailwind CSS 4.3 | 语义色令牌 + 工具类，无额外 CSS 框架 |
| 画布 | **自绘** | 任务图画在自己的无限画布上：一层 `transform` 承载世界坐标，网格用 CSS 渐变，位置算法全在 `core/` 里可单测 |
| 语言 | TypeScript 6.0 | 全量类型覆盖，`tsc --noEmit` 作为构建闸门 |
| 数据 | SQLite + Drizzle ORM | 单文件数据库，零运维 |
| 测试 | Vitest 5.0 | 内核纯逻辑可脱离 IO 单测 |

**为什么选 React 而不是 Vue**：本项目大量依赖「服务端渲染 + 流式推送 + 客户端水合」的组合，
Next.js 在这条路径上的成熟度更高。

**为什么画布是自绘的，而不用 React Flow**：一开始用过，后来搬回自绘，三个理由 ——
① 位置可以说清楚：每个节点的世界坐标由纯函数给，「第三道在哪儿」是一个能断言的数，
而不是一个库的内部实现；② 回退边要画成它该有的样子：React Flow 的边只能从预设的手柄出来，
绕行要么画不圆、要么得自己塞一个自定义边，而这里一条二次贝塞尔就够了；
③ 少一个运行时依赖（7 → 6）。

**为什么是 Next.js 而不是纯 React SPA**：SSE 流式接口、服务端会话校验、
生成产物的沙箱化预览都需要服务端能力。做成前后端两个工程会凭空多出一套
接口约定与跨域配置，而收益只有「技术上更纯粹」。

### 整体形态

**端口—适配器架构（六边形架构）**。依赖方向永远单向：

```
app/  ──▶  adapters/  ──▶  core/
（外壳）    （所有 IO）     （纯逻辑）
```

**内核不认识数据库、不认识 HTTP、不认识 Docker** —— 它只认识自己在 `core/ports/` 里定义的接口。

| 层 | 职责 | 约束 |
| --- | --- | --- |
| `core/` | 六阶段状态机、**工序权限模型**、产物契约、认证、生成编排、成本核算、流水线进度推算、07 回流 | **纯逻辑，零 IO，可单元测试** |
| `adapters/` | 模型调用与成本记账、状态持久化、产物落盘、阶段配置 | 实现 `core/ports/` 定义的接口，所有 IO 都在这里 |
| `app/` | Next.js 页面与 API 路由 | 只做编排与转发，不写业务逻辑 |

**为什么这样分层**：

1. **内核可单测** —— 认证的全部逻辑用内存假存储就能跑完，全程不碰数据库，约 1 秒
2. **存储可换** —— 端口是接口，换数据库只改 `adapters/store/` 下一个文件
3. **模型可换** —— 换供应商只改 `adapters/model/` 下一个文件；且接入点可注入，
   因此「平台默认接入」与「用户自配接入」能同时存在

### 流程：六阶段确定性状态机

```
一句话
  │
  ├─① 规格化 ──────── 人工门禁（全流程唯一需要人的地方）
  ├─② 架构定型
  ├─③ 界面设计
  ├─④ 并行构建        ← 并行粒度是「模块」而非「文件」
  ├─⑤ 集成装配        ← 上下文最重的一刻，必须做上下文裁剪
  └─⑥ 验收与交付      ← 把①的验收标准翻译成可执行断言，闭环
```

**三条设计判断**：

1. **流程是确定性骨架，AI 是概率性肌肉。** 流程由代码推进，零 token；AI 只在每一步内部提供判断。
2. **阶段之间靠结构化产物契约衔接。** 分层多智能体最经典的失败模式是层间信息丢失 —— 产物必须结构化且可机器校验，否则上游错误可以「看起来对」。
3. **骨架线性，但带反馈回路。** 每个阶段都声明失败可以退回到哪里，因此它不是瀑布模型。

> ⚠️ **接入状态（如实说明）**
>
> 六道工序中，**规格化**、**并行构建**与**验收与交付**已接入；
> **架构定型 / 界面设计 / 集成装配**尚未接入，界面上如实标注为
> 「未接入」而非「已通过」。
>
> **规格化**是完整接入的：它会调用模型把一句话需求整理成结构化规格
> （目标、使用人群、验收标准、明确不做的范围），产出 `spec.json`；
> 规格里出现需要用户确认的疑问时，**人工门禁**会真的停下来 ——
> 界面上把疑问做成可填写的表单，回答落成 `answers.json`，答完再继续。
>
> **并行构建**当前是「直通模式」：跳过②③，直接把一句话生成成单文件 HTML。
>
> 界面上写着已通过却交不出 `spec.json` / `arch.json`，比直接写「未接入」
> 严重得多 —— 所以流水线的进度推算被抽成纯函数，并有单元测试遍历
> 所有进度组合，断言「未接入的工序永远不会显示成已通过」。

### 人工门禁：全流程唯一需要人的地方

其余五道工序都能自动跑完 —— 模型判断得对不对，有产物契约和自检兜着。
唯独「你到底想要什么」这件事，模型没法自己判断，只能猜；
而猜错的代价要到最后一步才暴露，那时钱已经花完了。

所以规格化阶段允许停下：

```
规格里有疑问 → 状态置 paused、事件流结束
             → 界面上把疑问做成可填写的表单
             → 用户回答 → 存成 answers.json、状态放回 running
             → 再点生成 → 检查到答案存在，跳过门禁继续
```

**默认是放行的**（`SPEC_GATE=continue`），这是跑真实端到端之后改的：
模型对「做一个番茄钟」这种一句话需求也会问出 3 个问题，
默认拦的话几乎每次生成都要先回答三个问题才能看到东西 ——
而「一句话 → 一个能用的成品」是这个产品的承诺。
疑问仍然显示在界面上，用户可以主动回头改。
想要「不替你猜」的话设 `SPEC_GATE=pause`，两种模式都是完整实现。

### 任务图与过程回放（已实现）

**任务图**：六道工序的依赖关系以画布形式呈现，可平移、缩放，
悬停或点选时高亮该工序所在的链。

> ⚠️ 图上**不画失败回退的弧线**了。回退是流程内部的机制
> （`fallbackTo` 照建、失败该退到哪照算、点开工序看详情仍然列着回退目标），
> 但不显示在画布上 —— 六道工序之间那条顺序实线已经说清「谁接谁」，
> 再叠一层虚弧线，读者得先去分辨「这条虚线是什么」，
> 而那件事跟他此刻要看的（跑到哪一步了）无关。
> 几何函数 `fallbackPath` / `fallbackLabelAt` 保留着，随时能装回去。

**过程回放**：生成过程的事件会落库（片段按 250ms / 4000 字合并，
三千多个片段压缩到几十条）。因此可以拖动时间轴，看到「那一刻」的画面：
已写了多少字、花了多少钱、通过了几项检查。演示时不必现场等一次生成。

### 子树：每一步内部发生了什么（已实现）

六张工序卡是**骨架**，回答"跑到哪一步了"。子树回答下一个问题：
**"那一步里面发生了什么"**。

**一、位置**：每道工序都可能在自己下面长出子节点，六道工序因此是一张
**森林**。没有子树时按正常排列（**逐像素等于加子树之前的布局**，有单测钉着），
长出子树时**按子树宽度自动撑开**，兄弟之间不会重叠。
位置由一个纯函数算（`core/canvas/forest-layout.ts`）。

**二、连线**：一条**脊线**从父卡底边中点往下拉，每个孩子一根**短横枝**
插到它朝向脊线那条边的中点。脊线走的是父卡中心，而那恰好是两块子卡区的
中缝 —— **所以它永远不会从任何方块底下穿过**（这一点由单测保证，
对 n=1/2/3/4/5/7 逐行验过）。

> 第一版是"每个孩子各画一条线"，多行时会从上一行的方块底下穿过、
> 被盖住 —— 于是只有第一行看起来连着。**树的结构靠的是连线**，
> 少了那条线，子树就只是"另一堆漂着的卡片"。

**三、生长**：子树是**跑起来才长出来的**，所以位置变化会插值
（`lerpLayout`，纯函数）：新节点从**父节点的位置**长出来、尺寸 0 → 满、
透明度淡入，撑开的六个根同步滑动。`prefers-reduced-motion` 下直接给终态。

**四、样式**：子卡片和主卡片**同一套视觉语言** ——
状态胶囊、名称、判定依据、关键字胶囊、分隔线加一个数值，一一对得上。
**层级感由结构和连线给，不由样式给**（就像文件树里所有文件名长得一样，
层级全靠缩进）。

> ⚠️ 关键字胶囊和底部数值**现在是占位符「——」**。
> 编一个像模像样的词看着更完整，但那是替用户编事实 ——
> 这个项目宁可在界面上留一块空的，也不填一个假的。
> 常量在 `core/pipeline/forest.ts` 的 `CHILD_PLACEHOLDER`，接真数据时只改一处。

**五、聚焦**：双击一个工序 → 视口装下**它整棵子树**；
双击空白处回到全局。进去容易出来难的功能没人用，所以"出来"和"进去"一样便宜。

### 双层 Agent（设计已定，尚未接入）

每个阶段内部计划是一个自治小组：

```
阶段主 Agent（本阶段的规划 + 验收，永不写代码）
      ↓ 并行派发
执行 Agent × 1~N（本阶段的具体实现）
      ↓ 产出结构化产物
阶段主 Agent 验收 → 不过则局部重试
```

**三条铁律**：

- **阶段主 Agent 永不写代码** —— 保证最贵的模型只花在「判断」上，不花在「打字」上
- **验收者 ≠ 生产者** —— 写完某个模块的 Agent 不能是验收它的那个
- **阶段之间由代码推进，不由 Agent 决定** —— 否则复杂度和成本都是乘法级的

> 这一节描述的是**设计**，代码尚未落地。如实标注，不当作已完成能力陈述。

## 三、安装运行指南

### 环境要求

| 项 | 版本 |
| --- | --- |
| Node.js | ≥ 20（开发验证于 v24.18.1） |
| 包管理器 | npm（开发验证于 11.16.0） |
| 数据库 | 无（SQLite 单文件，首次运行自动创建） |
| Docker | **不需要**（沙箱尚未接入；当前产物直接在服务端落盘） |

### 安装

```bash
cd 源码
npm install
```

### 配置环境变量

```bash
# 复制模板
cp .env.example .env.local      # Windows: copy .env.example .env.local
```

然后编辑 `.env.local`，填入模型密钥：

```
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_API_KEY=sk-你的密钥
```

> **`.env.local` 已被 `.gitignore` 忽略，绝不会进入公开仓库。**
> 依据赛题要求：「API 密钥等敏感信息不得出现在公开仓库中，须通过环境变量方式配置」。

### 启动

```bash
npm run dev        # 开发模式，默认 http://localhost:3000
npm run build      # 生产构建
npm start          # 生产模式启动
```

### 质量校验

```bash
npm run typecheck  # TypeScript 类型检查
npm run lint       # ESLint 规范检查
npm run test       # 单元测试（248 条）
npm run verify     # 一次跑完以上全部 + 生产构建
```

端到端链路（需要开发服务器在跑）：

```bash
npm run e2e:auth       # 注册 / 登录 / 登出 / 归属隔离
npm run e2e:run        # 构建记录、任务图、过程记录接口
npm run e2e:settings   # 外观配置、主题、个人覆盖
npm run e2e:generate   # 真实调用模型跑一次完整生成（会产生费用）
```

一键建演示账号并跑一次真实生成（用于演示与截图）：

```bash
npm run demo:seed      # 建 demo 账号 + 跑一次生成，打印会话令牌
```
