> **状态：设计期存档（2026-11-02）。本文只解释六工序标准的来源与取舍，不作为执行依据；Skill 执行以《SKILL.md》为准。**
> 文中 `references/...` 路径均相对规范根目录。
> 版本：2026-11-02 · 缺口 A/B/C 已落入 SKILL.md，本文保留为决策记录
> 适用范围：软件开发全流程生成 Skill（规则面）与 Nexus 工作流编排（展示/执行面）的共同基准
> 定位一句话：**一套流程标准，两个呈现面——Nexus 负责把流程展示并执行出来，Skill 负责把流程定义并规定下来，两者向同一标准收敛，不互相适配。**

---

## 0. 定位：一套标准，两个面

- **唯一不变量**：软件开发流程标准本身（六工序骨架 + 工序契约 + 回流机制）。
- **Nexus = 展示/执行面**：六工序即画布上的确定性状态机节点，每节点显示契约满足情况、思考流、成本，由双层 Agent 自治执行；流程被"看见、被执行"。
- **Skill = 定义/规则面**：同一流程写成规则书——每道工序做什么、怎么判定、加载哪个分支文件、怎么回流；流程被"规定、可复用"，独立于 Nexus 单独可用。
- **同构即验证**：两个实现彼此独立，不刻意适配，却向同一标准长出相同骨架——本质层一致 = 标准成立；实现层差异 = 自由度，不算不一致。

---

## 1. 标准层（不变量）三要素

1. **流程骨架**：需求分析 → 架构设计 → 三方向开发（前端/后端/数据库，顺序执行）→ 集成装配 → 自动化测试 → 验收交付。
2. **工序契约**：每道工序有明确的 输入 → 产物（结构化、可机器校验）→ 验收标准；产物不是自然语言描述，必须可被下一工序消费、可被机器校验。
3. **回流机制**：验收不过 → 携带判定意见打回产生问题的工序，只重跑受影响下游；骨架线性但带反馈回路，不是瀑布。

---

## 2. 六工序定义表

| 工序 | 动作 | 产物 | 验收 |
|---|---|---|---|
| ① 需求分析 | 解析自然语言需求：业务实体、功能范围、使用角色、隐含约束 | 需求规格（含验收基线） | 范围可执行、无歧义 |
| ② 架构设计 | 全局形态决策、分层技术选型、目录规划 | 架构方案（技术选型组合） | 形态可达、组合合理 |
| ③ 三方向开发（顺序执行） | 数据库构建（schema/建表脚本）→ 后端构建（接口定义+业务实现）→ 前端构建（UI 规范子产物 → 页面代码与交互） | 三域代码、脚本与 UI 规范子产物 | 各域独立校验通过（SQL 执行 / 启动+连通 / 构建通过） |
| ④ 集成装配 | 模块组装、引用闭合、全栈链路接通 | 整体可运行包 | 链路闭合、无断裂引用 |
| ⑤ 自动化测试 | 执行确定性校验/测试动作，产出客观结果 | 测试结果报告 | 达合格线（只检验，不承担判定与交付） |
| ⑥ 验收交付 | 对照①需求基线逐项核对，判定是否全部覆盖 | 签收交付物（可运行项目 + 接口定义 + 示例测试 + 运行说明） | 需求闭环、全部覆盖；未覆盖项回流 |

**回流路径**：⑤发现代码问题 → 打回③；⑥发现架构问题 → 打回②；④装配失败 → 打回③；按失败归因（环境错/代码错/模型错）分流，只重跑受影响下游。

---

## 3. 旧六工序的问题诊断（"一直不对劲"的三个结构原因）

1. **结构不对称（最核心）**：旧流程把前端拆成"界面设计（③）+ 功能实现（④）"两个串行工序，而后端、数据库没有对应的"设计/实现分离"（其设计被笼统含在"方案"里）。同一个"设计"概念，对前端重复了一遍、对后端和数据库却没有——结构待遇不一致，是"不对劲"感的根源。
2. **组织维度错位**：旧流程按"专业阶段"串行，名为"并行构建"却没有显式的前端/后端/数据库三方向结构，"并行"名不副实。
3. **检验与判定混淆**："自动化测试"（找问题，执行动作）与"验收交付"（判定 + 签收，对照需求）合在一道工序里，职责不单一。

---

## 4. 新六工序合理性的三条判据（标准的检验标准）

- **对称原则**：三个技术方向的结构待遇一致——设计统一收到②架构设计（全局），三方向开发各自内含"设计 + 实现"（前端含 UI 规范、后端含接口与详细设计、数据库含 schema 设计），不重复、不缺失。
- **产物边界原则**：每道工序有单一、可独立验收的结构化产物，且产物可机器校验。
- **闭环原则**：①需求规格中的验收基线，在⑥验收交付时逐项核对，首尾闭环；外加回流回路，避免纯瀑布。

---

## 5. 本质同构 vs 实现异构

**必须一致（本质同构 = 标准内容）**：流程骨架、工序契约、回流机制、三方向顺序执行。
**允许不同（实现异构 = 自由度）**：执行机制（Skill 单执行者关卡制 vs Nexus 多 Agent 双层自治）、判定载体（Skill 规则 + 脚本 + 大模型语义判定 vs Nexus 阶段主 Agent 验收 + 失败归因分流）、工序粒度（Skill 8 节点 vs Nexus 6 工序）。

**含义**：一致性出现在本质层，自由度留在实现层，才叫"不过度特意适配还能保持一致"。同构不是目标，是检验标准正确性的工具——若两个独立实现长出漂移的骨架，说明某一方偏离了标准。

## 6. 对 Skill 的映射与缺口

**Skill 现行流程（SKILL.md §1）**：阶段0 需求澄清 → 阶段1 全局形态决策 → 阶段2 分层技术选型 → 关卡Ⅰ 组合合理性 → 阶段3 脚手架初始化 → 阶段4 有序代码生成 → 关卡Ⅱ 验证门 → 交付。

**映射**：①需求分析 ≈ 阶段0；②架构设计 ≈ 阶段1 + 阶段2 + 关卡Ⅰ（Skill 已覆盖且更细）；③三方向开发 ≈ 阶段3 + 阶段4；④集成装配 ≈ 阶段4 引用闭合 + 关卡Ⅱ 全栈联调（内嵌、非独立工序）；⑤自动化测试 ≈ 关卡Ⅱ 验证门；⑥验收交付 ≈ 交付节点。

**确认缺口（吸收方向）**：
- **缺口 A 三方向显式化**：阶段4 行文按"数据库构建 / 后端构建 / 前端构建"三域列示产物，各域独立校验（执行顺序不变，仍按依赖序一步步来）。
- **缺口 B UI 规范子产物**：前端构建先产出"页面结构清单 + 组件集"（UI 规范子产物），再生成页面代码——UI 契约下沉，不单独成工序但契约不消失。
- **缺口 C 需求闭环验收**：交付前对照阶段0 需求清单逐项核对，未覆盖项回流。

**执行机制保持异构（不动项）**：不引入双层 Agent、不改 8 节点命名与关卡数量、验证门合格线维持现状、单元测试体系维持"不纳入默认交付"。
