## 一、定位与目标

本 Skill 是一个面向 **AI 辅助软件开发全流程、全链路**的可复用生产能力，目标是让用户以自然语言输入需求（"一句话生成可交付软件"），经由内置的**流程编排（Process Orchestration）**机制，自动完成从需求理解、形态决策、技术选型、工程初始化到代码生成、质量自检的完整链路，最终交付结构规范、可直接运行的软件项目。

其"批量"能力包含两个层面：

- **单项目全量生成**：一次输出整个项目的完整目录、配置、业务代码与接口定义，而非逐句片段式产出；
- **生产线级复用**：同一套固化流程可反复承接不同需求，消除每次临时对话带来的结构漂移与质量波动。

## 二、要解决的核心问题

无 Skill 约束的自由对话式开发存在三个结构性缺陷：产出结构随机、技术决策缺乏依据、生成结果没有质量闭环。同时，软件开发领域本身是一棵由四个正交维度构成的**决策树（Decision Tree）**：

- **流程维**：需求 → 架构 → 编码 → 测试 → 交付；
- **角色维**：前端、后端、数据库；
- **技术栈维**：各角色下的语言与框架分支（如 Java / Python、Next.js / 原生 HTML、MySQL 等）；
- **工程约定维**：目录划分、命名规范、请求格式、接口定义、异常处理等。

本 Skill 的本质，就是把这棵决策树的判断路径与每个分支的专业约定预先固化，使大模型沿既定路径执行，而非每次即兴发挥。决策树的完整纵横形态见《决策树.md》。

## 三、执行机制：三层分工

Skill 自身不具备推理能力，实际执行由三个层次协同完成：

1. **规则层（Skill 本体）**：规则书、领域知识库与脚本的集合，定义"什么情况下按什么标准做"；
2. **推理层（大模型 / Agent）**：承担全部**语义判定**任务——需求理解、选型匹配、组合合理性判断、业务代码生成；
3. **校验层（脚本与工具）**：承担全部**确定性校验**任务——依赖安装、构建结果、服务启动、接口连通、SQL 执行、文件完整性，输出客观结果后由推理层解读。

## 四、核心工作流程（流程编排）

整条链路按固定顺序推进，采用**阶段关卡制（Stage-Gate）**：只在阶段结束处设判定门，不在每个小步打断；门不通过则不进入下一阶段。

1. **需求输入与澄清**：接收自然语言需求。决策树可自动确定的事项直接执行、不反问；仅在遇到关键大选择（项目形态、语言、框架级决策）时，由推理层发起**选型征询**，固定输出"1 个主选择 + 2 个次选择 + 1 个开放补充项"，且主、次选择的排序依据（场景适配度、主流程度、兼容性）必须预先写入规则，禁止随机推荐。阶段0 产物为结构化**需求规格**——需求清单条目（编号/描述/涉及实体与角色/验收条件）+ 决策记录（回写选型征询结论与默认路径），作为阶段4 与交付验收的唯一基线。
2. **全局形态决策（主规定）**：在进入任何具体技术选择之前，先由顶层规则确定项目整体形态，再向下分流。第一批主干覆盖两种形态：**前后端分离架构**（独立前端工程 + 后端 REST API + 数据库）与**传统单体架构**（后端模板渲染 + 原生 HTML + 数据库）；Next.js 全栈、纯静态等形态列为后续扩展。
3. **分层技术选型（技术选型）**：形态确定后，在前端、后端、数据库各角色内部沿决策树分支完成选型，形成完整技术组合。
4. **组合合理性判定（组合关卡）**：选型完成后执行一次整体复核——推理层按规则清单做语义判定，校验层对可客观检查的项做确定性校验，确认各组件之间适配、无冲突。
5. **脚手架初始化（Scaffolding）**：项目结构一律采用对应技术栈的**官方工程结构或官方脚手架**生成（如 create-next-app、Spring Initializr 模式、FastAPI 官方推荐结构），禁止模型即兴发明目录；无官方脚手架的，使用 Skill 内置的标准化模板。
6. **有序代码生成（三方向顺序执行）**：按功能依赖顺序执行、按三方向组织产物——数据库构建（建表/迁移脚本）→ 后端构建（接口定义+业务实现）→ 前端构建（先产出 UI 规范子产物：页面结构与组件集，再生成页面代码），各方向产物独立校验；配套输出完整接口定义、请求与响应格式、命名规范等工程约定，保证文件间引用关系闭合。
7. **质量门验证（验证门 / Quality Gate）**：生成完成后自动执行自检：后端依赖可安装、服务可启动、接口可连通；前端依赖可安装、构建可通过；数据库建表脚本可完整执行。通过后方可交付。

**判定回流（Decision Feedback Loop）**：任一关卡判定不通过时，流程不向前推进，而是携带具体判定意见**回流**到产生问题的对应节点（形态决策、选型或代码生成），修正后重新经过同一道门，直至通过，形成完整闭环。

## 五、质量保障体系

- **验证门为强制环节**：批量自动化场景下，它是生产线判断自身成败的唯一客观依据，也是"生成即自检、通过才交付"的核心交付承诺；
- **接口级示例测试**：每个对外接口配套标准请求与预期返回，与接口定义同步产出，同时承担接口文档职能；
- **全覆盖单元测试体系暂不纳入**主干，避免多栈测试框架导致分支膨胀，列为后续扩展项；
- 大型分布式、微服务体系等超出单次生成能力的场景，明确列入排除范围。

## 六、覆盖范围与主干分支

**范围边界：**

- 输入边界：仅支持从零生成及生成后的小范围修改，不承接遗留项目改造；
- 输出边界：交付到本地可运行且验证门通过为止，Docker 化部署等列为可选扩展；
- 规模边界：限定中小型 Web 应用、信息管理系统与工具类项目。

**主干分支（先做深、后做广）：**

| 角色 | 主干分支 |
|---|---|
| 后端 | Java、Python |
| 前端 | Next.js（React 体系）、原生 HTML |
| 数据库 | MySQL |

主干分支将从树根到树叶完整做透，固化为标准样本；后续新增语言或框架时，只按样本复制分支结构并填充对应约定，不重新设计组织方式。

## 七、版本与选型策略

版本号不做硬性锁定，以应对技术持续更新。规则中只写入**约束条件**——须为稳定版本、组件间相互适配、与官方当前推荐实践一致；具体版本由推理层在执行时依据条件判定。每个分支保留一套默认技术组合作为决策树的自动路径，仅当用户明确提出特殊要求时才偏离默认组合。

## 八、与外部系统的关系

本 Skill 以独立通用形态为主体设计，不依赖任何特定外部系统。其阶段关卡与流程节点天然具备映射为 Agent 工作流编排系统节点的能力，未来可作为上层"二重 AI 管理"类系统的内嵌能力接入，接入时再按具体契约调整，不影响 Skill 本体结构。
