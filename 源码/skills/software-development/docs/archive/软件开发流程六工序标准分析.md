## 一、核心结论

软件开发全流程应收敛为一条统一的六工序标准：

**需求分析 → 架构设计 → 三方向开发（数据库构建 / 后端构建 / 前端构建，按依赖顺序执行）→ 集成装配 → 自动化测试 → 验收交付**

该标准同时作为两个产物的共同地基：

- **Nexus**（面向软件开发的 AI 工作流编排工具，Web 形态软件工厂）：以"展示与执行"形态承载流程——流程层确定性状态机 + 阶段层双层 Agent 自治；
- **软件开发 Skill**（静态规则库）：以"定义与规则"形态承载流程——阶段关卡制 + 分支文件 + 验证门。

两者形态不同，但本质都在回答同一个问题：**软件开发流程应该怎样被组织、被校验、被复用**。流程标准唯一，Nexus 负责展示与执行，Skill 负责定义与规定。

## 二、旧六工序的三个结构问题

旧划分：`需求 → ①方案 → ②UI设计 → ③功能实现 → ④集成交付 → ⑤自动化测试`（即 规格化 / 架构定型 / 界面设计 / 并行构建 / 集成装配 / 验收交付）。

### 1. 结构不对称（最核心）

旧流程把"前端"拆成了两道串行工序（界面设计、功能实现），而后端、数据库的"设计"统一含在方案工序内。同一个"设计"概念，对前端重复了一遍，对后端和数据库却缺失——三个技术方向的结构待遇不一致。

### 2. 组织维度错位

旧流程按"专业阶段"串行（设计阶段 → 构建阶段），没有显式划分前端 / 后端 / 数据库三个方向，"并行构建"名不副实。软件开发的实际执行顺序由功能依赖决定（先有表 → 才能写接口 → 才能做页面），组织维度应当是三方向，执行维度才是顺序。

### 3. 检验与判定混淆

自动化测试与验收交付被合并在一道工序。测试是执行动作（跑用例、出报告、找问题），验收是判定与签收（对照需求清单逐项核对、通过验证门、打包交付物）。两者合并导致"是否达到交付标准"的判定缺乏独立对照基线。

## 三、新六工序标准

| 工序 | 核心动作 | 结构化产物 | 验收标准 |
|---|---|---|---|
| ① 需求分析 | 解析需求、业务实体、角色、隐含约束 | 需求规格（含验收基线） | 范围可执行、无歧义 |
| ② 架构设计 | 形态决策、技术选型、目录规划 | 架构方案（选型组合） | 形态可达、组合合理 |
| ③ 三方向开发（顺序执行） | 数据库构建：建表/迁移脚本；后端构建：接口定义 + 业务实现；前端构建：UI 规范子产物先行 → 页面代码 | 三域代码（各域独立产物清单） | 各域独立校验通过（数据库=SQL 执行、后端=启动+接口连通、前端=构建通过） |
| ④ 集成装配 | 模块组装、引用闭合 | 整体可运行包 | 链路闭合、无断裂引用 |
| ⑤ 自动化测试 | 执行校验/测试动作 | 测试结果报告 | 达到合格线（不承担判定交付） |
| ⑥ 验收交付 | 对照需求基线逐项核对 | 签收交付物 | 需求闭环、全部覆盖 |

要点：

- **执行按依赖顺序，组织按三方向**：不是真并行，是按功能一步一步来；但产物与校验按前端 / 后端 / 数据库三个方向独立组织、各自可独立验收。
- **UI 不单独成工序，但契约下沉**：前端构建内先产出"UI 规范子产物"（页面结构清单、组件集、视觉基调），再生成页面代码，防止前端多个执行体各自为政拼出"缝合怪"界面。
- **回流回路（防纯瀑布）**：⑤ 发现代码问题 → 打回 ③；⑥ 发现架构问题 → 打回 ②；④ 装配失败 → 打回 ③。按失败归因分流，只重跑受影响下游。

## 四、三条合理性判据

1. **对称原则**：三个技术方向的结构待遇一致，设计/实现不重复、不缺失；
2. **产物边界原则**：每道工序有单一、可独立验收的结构化产物，且可机器校验；
3. **闭环原则**：①需求规格中的验收基线，在⑥验收交付时逐项核对，首尾闭环；回流回路保证不是瀑布。

## 五、一个流程，两个面

| 面 | 形态 | 职责 | 关键机制 |
|---|---|---|---|
| Nexus（展示/执行面） | 运行时编排 | 流程被看见、被执行 | 流程层确定性状态机；阶段层双层 Agent（阶段主 Agent 规划+验收，执行 Agent×N 并行）；阶段契约表 |
| Skill（定义/规则面） | 静态规则库 | 流程被规定、可复用 | 阶段关卡制（阶段0-4 + 关卡Ⅰ/Ⅱ）；判定规则；路由表；验证门；判定回流 |

## 六、同构验证

Skill 与 Nexus 彼此独立、不互相适配；两者向同一个标准收敛，自发长出相同骨架，即证明标准成立。

- **本质同构（应一致）**：流程骨架、工序契约、回流机制、三方向顺序执行；
- **实现异构（允许不同）**：执行机制（Skill 单执行者关卡制 vs Nexus 多 Agent 双层）、判定载体（规则+脚本 vs 主 Agent 验收）、工序粒度（Skill 8 节点 vs Nexus 6 工序）。

一致性出现在"本质层"，自由度留在"实现层"——这才叫"不过度特意适配还能保持一致"。同构不是目标，而是检验标准正确性的工具。

## 七、后续建议

- **Skill 修改方向**（向标准收敛，非向 Nexus 适配）：
  1. §1 阶段4 显式按"前端 / 后端 / 数据库"三工作域组织产物，各域独立校验；
  2. 前端构建增加"UI 规范子产物先行"约定；
  3. 交付节点补充"对照阶段0 需求清单逐项核对"的需求闭环验收。
- **Nexus 修改方向**：按新六工序重排流程层（需求分析 / 架构设计 / 三方向开发 / 集成装配 / 自动化测试 / 验收交付），完善各工序契约表。
- **可选**：把"标准层（不变量清单）"独立成文，作为两个项目共同引用的第三方基准。
