# 方法论1 · 需求切片

## 1.1 问题

一个人开始设计软件，一定有需求；但需求通常是复杂的。复杂体现在：

- 一次描述包含多个意图，混在一起无法单独分析；
- 表述夸张、包装、含混，字面与实际意图不一致；
- 解释错乱、顺序颠倒、前后重复；
- 内容过多，超出一次分析能承载的量。

不处理这些复杂性，需求就无法被分析、被推导、被验收。

## 1.2 方法论来源

借用 RAG 检索中的**内容切片（chunking）**方法论——不是与 RAG 同一性质，而是迁移其处理思路：

| RAG 的做法 | 迁移到需求分析 |
|---|---|
| 长文本无法一次处理 → 切成语义完整的块 | 复杂需求无法一次分析 → 切成可独立核验的需求片 |
| 每个块带元数据（来源/主题/位置） | 每个需求片带标签（来源/主题/类型） |
| 按相关度/重要度对块排序 | 按重要程度对需求片分层分级 |
| 多源内容混杂 → 整合重排去重 | 错乱、重复、过多的需求 → 整合划分 |
| 检索时按需取块 | 下游（接口/页面/建模/验收）按需引用需求片 |

## 1.3 方法四步

### 第 1 步 · 切片

把原始需求拆成**语义完整的最小可核验单元**（需求片）。

**粒度说明**：所谓"一句话一条需求"只是概括性说法，不必死板理解为字面的一句话。切片的唯一标准是**语义完整、可独立核验**——一片可以是一句话、一段话、或一段话中的一个完整意图，取决于原始表述的实际粒度。切片的粒度由语义完整性决定，不为凑"一句话"硬切。

**切片规则**：

| 原始情况 | 处理 |
|---|---|
| 一句话包含多个意图 | 拆成多片，每片一个意图 |
| 一个意图散落在多处 | 并成一片，记录合并来源 |
| "为什么"（背景）与"是什么"（规则）混写 | 分开：背景归背景，规则归规则 |
| 条件、动作、结果纠缠 | 一片内保留完整语义链，不拆散 |

**每片必带三个标签**：

| 标签 | 内容 | 用途 |
|---|---|---|
| 来源 | 回指原始需求的位置（第几段/原话） | 复核可追溯（对应 RAG 的 source） |
| 主题 | 涉及的业务对象（实体/角色） | 支撑实体识别 |
| 类型 | 功能 / 约束 / 流程 / 性能 | 支撑分类处理与下游路由 |

### 第 2 步 · 分级

按重要程度划分层级，三轴交叉定级：

| 轴 | 分级 | 含义 | 用途 |
|---|---|---|---|
| 价值层 | 核心 / 重要 / 增强 | 缺了这一片系统能不能用 | 决定验收的强制/可选 |
| 依赖层 | 基础能力 / 业务能力 / 展示能力 | 谁依赖谁（登录→订单→报表） | 决定生成顺序与回流方向 |
| 牵连度 | 高 / 中 / 低 | 会牵连多少个接口/表/页面 | 决定变更成本与风险 |

每片定级后，携带"有多重要、在哪一层、改了影响多大"的完整信息进入下游。

### 第 3 步 · 整合

处理复杂难懂、解释错乱、内容过多三类问题：

| 问题 | 处理 |
|---|---|
| 难懂 | 用大白话重述，保留原文映射（原句可查） |
| 错乱 | 按固定逻辑重排：目标 → 角色 → 流程 → 规则 → 边界 → 约束 |
| 重复 | 合并，记录合并来源（几处原文合成一片） |
| 过多 | 抽象成"规则 + 例表"（如权限规则一句话 + 角色权限矩阵表） |

### 第 4 步 · 可分析

切片分级整合后的需求片，必须能直接支撑以下分析动作，缺一即视为切片未完成：

| 分析动作 | 从切片取什么 |
|---|---|
| 实体识别 | 每片的主题标签与名词 |
| 接口推导 | 每片的验收条件 → 接口 |
| 页面推导 | 每片的使用角色与操作 → 页面 |
| 数据建模 | 每片的业务对象 → 表 |
| 变更影响 | 改一片 → 按标签查牵连的接口/表/页面 |
| 验收 | 工序⑥ 逐片核验，未覆盖即回流 |

## 1.4 产物形态

需求规格不采用平铺列表，而是三层结构 + 标签：

```
需求域（业务顶层，如"图书借阅"）
├── 需求组（功能域，如"借阅流程"）
│   ├── 需求片 R1（原子单元：语义完整可核验 + 标签 + 级别）
│   ├── 需求片 R2
│   └── …
└── 需求组（功能域，如"图书管理"）
    └── …
```

下游（接口、页面、表、验收）一律按**片 ID** 引用，不引用整篇需求文档。

# 方法论2 · 系统提问

## 2.1 问题

agent 执行需求分析时，面临两个对立的错误倾向：

- **完全依照自己的想法进行**：不向用户确认，自行决定一切 → 结果偏离用户真实意图；
- **确定方案后再反复确认**：边做边问、挤牙膏式确认 → 打断流程、消耗耐心、前后不一致。

正确姿态：**不自行决定，也不反复确认**。

## 2.2 核心思路

关键在于 agent **提前规划好内容**——这个内容不是简单地对功能点提问，而是**一次性明确后续所有方案**：依照真实开发过程中可能涉及的所有内容，对用户进行恰当且明确的提问。

即：在进入开发前，agent 先把"后续全链路所有需要用户拍板的决策点"规划成一张完整的问题清单，**一次问完**；之后按用户答复执行，不再反复确认（出现新的重大分叉除外）。

## 2.3 提问维度清单（真实开发全链路）

提问必须覆盖以下维度，缺项视为规划不完整；每个维度按项目实际取舍，无决策点的维度记录"无此项"而非跳过：

| 维度 | 提问内容（示例） | 为什么必须问 |
|---|---|---|
| 1 目标与验收 | 做什么、给谁用、成功的标准 | 决定全流程的验收基线 |
| 2 范围与边界 | 包含什么、明确不做什么 | 防止范围蔓延，划清交付边界 |
| 3 形态与架构 | A/B/C/D 形态、是否需要登录、单机/多端 | 决定下游可达路径（工序②） |
| 4 技术栈 | 语言/框架偏好、团队已有积累、部署环境 | 决定技术选型（工序②） |
| 5 数据 | 核心业务对象、数据量级、导入导出、历史数据 | 决定数据建模与迁移（工序③） |
| 6 用户与权限 | 角色划分、权限粒度、是否需要注册 | 决定页面与接口的鉴权设计 |
| 7 交互与页面 | 页面数量级、风格偏好、响应式/移动端 | 决定页面结构设计（工序③） |
| 8 集成与外部 | 是否需要第三方（支付/短信/地图）、外部系统对接 | 决定接口设计与范围边界 |
| 9 部署与运维 | 部署环境、域名/HTTPS、是否容器化 | 决定配置管理与运行说明 |
| 10 非功能 | 性能、安全、合规、备份 | 决定隐含约束清单（工序①） |
| 11 交付形态 | 需要什么交付物（代码+文档/演示/部署包） | 决定工序⑥ 交付包构成 |

## 2.4 提问规则

1. **恰当**：问题要与项目真实相关，不问无关细节；能用选择题表达的不开放式发散。
2. **明确**：每个问题让用户能直接回答，选项即答案；确需开放输入时，说明需要补充什么。
3. **一次问完**：全维度问题在同一轮内提出（受实际问答机制限制时，按维度分组一次性抛出），不边做边补问。
4. **按答复执行**：用户答复后按答复执行；未明确答复的项按默认值执行并在决策记录中写明，不因等待而停住流程（破坏性操作除外）。
5. **记录**：提问与答复全部回写决策记录（见 SKILL.md §1.2），作为后续偏离判定与验收对照的依据。

## 2.5 与 SKILL.md §2.1 的关系

SKILL.md §2.1 的选型征询（1 主选择 + 2 次选择 + 1 开放补充）是**遇到关键大选择时**的征询格式；方法论2 是**开始阶段的全链路提问规划**，粒度更大、时机更早。两者是"总规划 + 分点征询"的关系：方法论2 先问清全链路，§2.1 在规划后仍遇关键分叉时按格式补问。
