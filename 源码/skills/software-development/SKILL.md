## §0 总则

### 0.1 目的与范围

**目的**：把模糊需求转化为可运行、可验证、可交接的本地项目，使交付质量不随执行者与执行次数波动。

**范围内**：

- 从零生成中小型 Web 应用、信息管理系统、工具类项目；
- 对已有工程做小范围新增、修复与重构，限结构清晰、可本地运行的中小型工程。

**范围外**（不承接）：

- 遗留系统改造、既有系统接入、微服务与分布式架构、大型系统迁移；
- 纯视觉与界面设计、纯文档/表格/PPT 产出；
- 需要连续多轮无人值守推进的长跑任务。

**交付边界**：交付到本地可运行且验证门通过为止。容器化、云上部署为可选扩展，不在默认交付范围。

### 0.2 角色与职责

| 层次 | 承担者 | 职责 | 边界 |
|---|---|---|---|
| 规则层 | 本文件与 `references/` 分支文件 | 固化流程、判定规则、路由表与各栈工程约定 | 自身不执行推理，不承载业务判断 |
| 推理层 | 执行模型 | 需求理解、形态决策、技术选型、组合合理性判定、代码生成 | 不得用主观判断替代可查表、可执行的事实 |
| 校验层 | 命令行工具与项目自带脚本 | 环境预检、依赖安装、构建、启动、接口连通、SQL 执行、文件完整性 | 只输出客观结果，不做语义裁定 |

原则：语义判定不得下沉为脚本，确定性校验不得交由模型主观判断。

### 0.3 文档结构与效力

1. **执行前必须完整读取本文件**；分支文件按 §3 路由按需加载，未命中的分支不加载。
2. **加载顺序**：本文件 → 工序文件（§3.4 按工序加载）→ 横切约定 → 技术栈分支 → 接口示例测试。
3. **效力顺序**：流程与判定以本文件为准；协议与约定（返回体、错误码、分页、命名、认证）以横切约定为准（§0.4 的数值默认值除外，以 §0.4 表为准）；栈内写法以分支文件为准。三者矛盾时按 §2.4 回流修正，不得自行取舍。
4. **`references/02-架构设计/形态判定.md` 是形态与可达规则的唯一权威**。`docs/archive/` 下的三份设计文档（Skill 简介、六工序标准、六工序分析）为设计期存档，不作为执行依据，执行时不必读取。

**文档体系**：

| 文档类 | 位置 | 作用 | 效力 |
|---|---|---|---|
| 规范正文 | `SKILL.md` | 流程、判定、路由、交付 | 最高；流程与判定冲突时以其为准 |
| 工序文件 | `references/01-` ~ `06-` | 各工序方法与判定（需求分析、形态判定、选型对照、页面/接口/数据建模、装配联调、验证门、交付清单） | 各工序方法的唯一权威 |
| 技术栈分支 | `references/03-三方向开发/` | 各栈目录、依赖、写法、验证命令 | 栈内写法（目录、依赖、命令）的唯一权威；数值默认值见 §0.4 |
| 横切约定 | `references/横切约定/` | 返回体、错误码、分页、命名、认证、日志等协议 | 协议与约定的唯一权威 |
| 设计存档 | `docs/archive/` | 设计期讨论记录 | 无执行效力，仅供追溯 |

### 0.4 全局默认值

以下默认值在全部分支生效。分支文件引用本表，数值以本表为唯一来源；需要偏离时，经 §2.1 征询确认并写入决策记录后执行。

| 类别 | 默认值 | 权威出处 |
|---|---|---|
| 统一返回体 | `{"code":0,"message":"success","data":{}}`；分页 data 固定 `{list,total,page,page_size}` | 接口规范 §二 / §五 |
| 分页 | `page` 从 1 起；`page_size` 默认 10、上限 100（超限截断，不报错） | 接口规范 §五 |
| 主键 | 统一 `id`；数据库层 BIGINT UNSIGNED 自增（PostgreSQL 用 identity/serial，SQLite 用 rowid 别名） | 命名规范 §五 / 数据库分支 |
| 审计字段 | `created_at` / `updated_at` / `deleted_at`（软删除，NULL=未删除），毫秒精度 DATETIME(3) / TIMESTAMP(3) | 命名规范 §五 / MySQL 分支 |
| 服务端口 | Java/Spring Boot 8080；Python/FastAPI 8000；Flask 5000；Go 8080；均可由 `SERVER_PORT` 覆盖 | 各后端分支文件 |
| 令牌有效期 | 访问令牌 120 分钟（`JWT_EXPIRE_MINUTES`）；刷新令牌 7 天（`JWT_REFRESH_EXPIRE_DAYS`） | 认证鉴权 §一 |
| MySQL 字符集 | InnoDB + utf8mb4；排序规则 utf8mb4_0900_ai_ci（旧版本回退该版本官方默认大小写不敏感规则） | MySQL 分支 |

### 0.5 执行模式

| 模式 | 触发条件 | 流程差异 |
|---|---|---|
| 新建 | 空目录，或从零起项目 | 完整执行工序① → ⑥ |
| 改造 | 已有工程（本规范生成过的，或结构清晰、可本地运行的中小型工程），做小范围新增、修复或重构 | 跳过工序② 的形态决策与工序③ 的工程初始化，从生成阶段进入；先读现有目录、依赖清单与相邻代码，沿用既有分层与风格；只改受影响文件，不重建工程、不重排目录 |

改造模式的附加约束：

1. **基线可运行**：改造前必须确认基线能构建、能启动；基线本身跑不起来时，先报告并停在基线修复，不得在坏基线上叠加改动。
2. **最小改动**：只改与本需求相关的文件；顺手重构无关部分属于范围外，应单独立项。
3. **选型收敛**：涉及 ≥3 个模块或数据结构变更时，只对受影响角色重过工序② 选型，不得在既有工程里另起一套技术栈。
4. **验收同标**：改造同样受 §4.2 验证门约束；需求规格以「改动范围 + 验收条件 + 明确不碰的部分」为主。

### 0.6 质量目标

交付物必须同时满足以下四项，缺一项即视为未完成：

| 目标 | 判定方式 |
|---|---|
| 可运行 | 按 README 的步骤在本地能启动，核心路径可操作 |
| 可验证 | 验证门全部通过，且保留命令与输出证据 |
| 可交接 | 需求规格、接口定义、接口示例测试、运行说明齐全，接口与实现 1:1 |
| 可回滚 | 有基线提交号，或有明确的改动文件清单与手工回滚步骤 |

## §1 流程

### 1.1 流程总览

流程按 6 道工序依次进行：只在工序衔接处设检查点，不通过不得进入下一道工序。完整形态分支见 `references/02-架构设计/形态判定.md`，本文件不重复其树图。

| 工序 | 输入 | 动作 | 产物 | 通过条件 |
|---|---|---|---|---|
| ① 需求分析 | 自然语言需求、既有资料 | 识别业务实体、功能范围、使用角色与隐含约束；写验收条件 | 需求规格 `docs/requirements.md` | 每条需求有可核验的验收条件；无未记录假设 |
| ② 架构设计 | 需求规格 | 步骤1 形态判定（A/B/C/D）→ 步骤2 技术选型 | 形态结论、技术组合与版本约束 | 形态符合可达规则且与需求不矛盾；选型落在可达路径内 |
| 检查点 · 组合合理性 | 技术组合 | 按 §2.2 做语义复核与确定性查表 | 判定记录 | 四条检查全部通过 |
| ③ 三方向开发 | 技术组合、需求规格 | 步骤1 工程初始化（官方结构）；步骤2 原型开发（成品级页面+占位数据）；步骤3 原型判定（对照需求，通过即锁定为权威依据）；步骤4 依原型推导并实现 数据库 → 后端 → 前端（前端原型代码接真实数据） | 三方向产物、接口定义、示例测试、UI 规范子产物 | 原型判定通过并锁定；引用关系闭合；接口定义与实现 1:1；各方向自检通过 |
| ④ 集成装配 | 三方向产物 | 引用闭合检查 + 全栈联调检查 | 装配结论 | 跨方向引用全部闭合 |
| ⑤ 自动化测试 | 完整项目 | 按 §4.2 在真实环境执行验证门 | 验证证据 | 五层合格线全部通过 |
| ⑥ 验收交付 | 通过验证门项目 | 对照需求清单逐项核对，写交付说明 | 交付包 | 需求全部覆盖，或未覆盖项已记录并按 §2.4 处理 |

### 1.2 工序① 产物：需求规格

工序① 必须产出结构化的**需求规格**，作为工序③ 代码生成与工序⑥ 验收的唯一基线。格式固定，不得由执行模型每次即兴改变。方法与完整模板见 `references/01-需求分析/`（入口 `需求分析.md`，模板 `需求规格模板.md`，子方法按 §3.4 加载），本文只列条目格式。

**需求清单**（条目格式）：

| 条目 | 内容 | 示例 |
|---|---|---|
| 编号 | 顺序编号 `R1`、`R2`…；工序③/⑥ 逐项引用 | R1 |
| 描述 | 一条可独立核验的功能或约束，一条一题 | 支持按 ISBN 精确查询图书 |
| 涉及实体/角色 | 挂接识别出的业务实体与使用角色 | Book / 管理员 |
| 验收条件 | 可客观核验的通过标准（接口、行为或数据层面） | `GET /api/v1/books/{id}` 返回该图书完整信息 |

**决策记录**：工序② 的形态与技术选型结论、依据、以及「用户明确选择 / 用户未作答按默认执行（§2.1）」两种情形，一并回写。后续偏离既定决策时，先追加说明再执行。

**落盘要求**：需求规格必须写入工程根 `docs/requirements.md`，交付时随项目提交。它不得只存在于对话或模型上下文中。

**变更规则**：生成过程中发现缺项或需求变更，回流工序① 追加 / 修订条目，再重走受影响工序。

## §2 判定规则

### 2.1 选型征询

- 工序① 先按《方法论.md》方法论2 做全链路提问规划（执行规则见 `references/01-需求分析/提问规划.md`）；本文是规划后仍遇关键分叉时的征询格式。
- 判定表与形态树可自动确定的事项直接执行，不反问。
- 仅在关键大选择（项目形态、语言、框架级决策）无法从需求与默认路径确定时，发起征询。
- 征询一次性问完，固定输出四项，顺序与编号不得变更：

| 编号 | 项 | 要求 |
|---|---|---|
| 1 | 主选择 | 默认推荐项，说明推荐理由 |
| 2 | 次选择一 | 可替代项，说明适用差异 |
| 3 | 次选择二 | 可替代项，说明适用差异 |
| 4 | 开放补充 | 用户可指定四项之外的方案，并明确告知其自行承担组合适配风险 |

- 排序依据固定为三项，权重从高到低：**场景适配度 → 主流程度 → 兼容性**。
- 用户未作答时，按主选择执行并记录该决策；不得因等待回答而停住流程（破坏性操作除外）。

### 2.2 组合合理性（工序② 末检查点）

四条检查全部通过才放行进入工序③；任一条不通过按 §2.4 回流。查表依据见 `references/02-架构设计/选型对照.md` §七。

1. **形态可达性**：所选技术栈全部落在当前形态的可达路径内（以 `形态判定.md` §四为准）。例如形态 B 不可达独立前端工程，形态 C 不可达独立后端工程。
2. **组件适配**：ORM 与数据库正确配对；前端调用协议与后端一致（统一 REST）；认证、配置等组件与框架版本兼容。
3. **版本约束**：均为稳定版本，组件间相互兼容，符合官方当前推荐实践；不使用已废弃或预览版组件。
4. **规模边界**：整体方案处于中小型范围内，未引入微服务、消息中间件集群等超范围组件，未触碰排除项。

**确定性校验项**（可客观核查的部分，由命令或脚本客观判定）：

| 编号 | 校验 | 方法 |
|---|---|---|
| C1 | 形态可达路径 | 对照 `形态判定.md` §四 可达规则逐角色查表 |
| C2 | ORM × 数据库配对 | 按 `选型对照.md` §五 配对表查表：MyBatis/JPA↔MySQL、SQLAlchemy↔MySQL/PostgreSQL、Prisma↔MySQL/PostgreSQL/SQLite |
| C3 | 版本兼容 | 按 §2.3 约束核对官方发布说明与兼容矩阵 |

语义项（方案整体适配度、规模判断）由推理层判定，不因查表通过而豁免。

### 2.3 版本策略

- 不锁死具体版本号，只写约束：稳定版、组件适配、官方当前推荐实践。
- 具体版本由推理层在执行时判定；验证门负责暴露不兼容并触发回流。
- 判定前应核对官方发布说明与兼容矩阵。无法联网时，选取已知稳定大版本，并在交付说明的「已知限制」中标注版本假设与后续升级点；版本号以官方发布说明与兼容矩阵为准。

### 2.4 判定回流

检查点不通过时，流程不向前推进：携带具体判定意见回流到产生问题的工序，修正后重新经过同一检查点。

| 失败现象 | 回流节点 | 必须携带的信息 |
|---|---|---|
| 形态与需求矛盾、分支不可达 | 工序② 架构设计 | 矛盾点与可达路径约束 |
| 组件配对错误、协议不一致、版本冲突 | 工序② 架构设计 | 冲突组件对与适配要求 |
| 原型判定不通过（页面缺失/交互不全/需求未覆盖） | 工序③ 原型开发 | 未通过的判定项与具体修正意见 |
| 目录结构违规、工程初始化错误 | 工序③ 三方向开发 | 违规位置与官方结构要求 |
| 引用断裂、接口与实现不符、自检失败 | 工序③ 三方向开发 | 失败文件、复现命令与预期结果 |
| 验证门命令报错 | 工序③ / 工序④（按失败层定位） | 完整命令、报错输出与失败环节 |

回流的判定意见必须可复现：写明命令、输出与预期；只写「失败了」不构成有效回流。连续 3 次不通过按 §2.5 止损。

### 2.5 重试与止损

1. 同一道工序末检查点连续 3 次不通过，停止自动重试，输出失败清单：复现命令、完整报错、已尝试的修正、仍缺的条件，交回用户决策。不得无限循环重写。
2. 因环境缺失（工具链未安装、数据库不可连、端口被占）导致的失败不计入重试次数，直接报告环境问题与安装 / 释放办法。
3. 不得用降低验收标准的方式止损（改需求、删用例、放宽校验、跳过接口）。确需降标准时，必须由用户明确同意并写入决策记录。

### 4.1 交付物

| 序号 | 交付物 | 要求 |

| 5 | 需求验收对照 | `docs/requirements.md` 中逐条标注落实位置（文件/接口）、验证方式与结果（通过 / 未覆盖及原因） |

**目录卫生**：本规范本体文件夹遵循 Skill 规范，不创建 README、INSTALLATION、CHANGELOG 等多余文件；本规范**生成的软件项目**是正常软件，应在根目录提供 `README.md`。删除约束只针对本规范本体，不适用于被生成项目。

### 4.2 验证门（工序⑤）

验证门为强制环节，全部合格才交付；任一环节失败按 §2.4 回流，重过本门。五层合格线、各栈具体命令与执行约定见 `references/05-自动化测试/验证门.md`，本文只列层与合格线。

| 层 | 校验动作 | 合格线 |
|---|---|---|
| 环境预检 | 确认工具链可用：JDK/Maven、Python/pip、Node/npm、MySQL 客户端、Go（按所选栈取） | 版本满足分支文件约束；缺工具链立即停止并报告缺什么、怎么装，不得跳过 |
| 后端 | 依赖安装 → 服务启动 → 接口连通（成功与失败各至少一条） | 依赖安装无致命错误；服务可启动且无启动期异常；示例接口返回统一返回体，状态码与预期一致（含 401/400 负例） |
| 前端 | 依赖安装 → 构建 → 启动后页面可访问 | 依赖安装成功；生产构建零报错；启动后首页与至少一条受保护路由可访问，静态资源无 404；形态 B/D 的静态资源可直接打开且引用路径有效 |
| 数据库 | 空库从头执行建表/迁移脚本 → 重复执行校验 | 脚本从头执行无报错，表、字段、索引、外键全部建成；幂等脚本可重复执行，非幂等脚本由迁移工具记录版本且不重复跑 |
| 全栈联调 | 前端经 REST 调用后端，后端经 ORM 访问数据库 | 至少一条端到端链路连通，返回体符合接口规范，认证挂载点对白名单与受保护接口行为正确 |

**执行约定**：

1. 命令按当前 shell 改写：Windows 用 `mvnw.cmd` / `npm.cmd` / `curl.exe`，含 JSON 的参数用文件或正确转义；判定标准不因 shell 变化。
2. 每项验证保留证据（命令、关键输出、时间），写入交付说明；未执行的项标「未验证」，不得写「通过」。
3. 环境预检失败不计入回流重试，直接报告缺什么、怎么装。
4. 验证必须在真实运行的服务上发起真实请求；用 mock、假数据或跳过接口制造的「通过」一律视为未验证。

### 4.3 接口示例测试

1. 每个对外接口配套一份示例，包含：请求方法与路径、请求头、请求体、预期 HTTP 状态码、预期统一返回体。
2. 示例与接口定义 1:1 配套，标准模板见 `references/05-自动化测试/接口示例测试.md`。
3. 期望值先于实现确定；实现与示例冲突时改实现，不改预期。
4. 验证门的接口连通环节直接执行该示例，预期不符即判定不通过。

## §5 红线

以下行为一经发现，交付即判定无效，必须回到对应工序返工。

| 编号 | 红线 | 判定后果 |
|---|---|---|
| R-01 | 把未实现或未验证的东西说成「已完成 / 已支持」 | 交付无效，回流工序③ |
| R-02 | 用 mock、假数据、跳过接口或只跑成功路径制造「验证通过」 | 交付无效，重新执行验证门 |
| R-03 | 提交真实密钥、token、`.env` | 立即移除并轮换密钥 |
| R-04 | 用删测试、注释断言、放宽规则、改预期的方式让验证变绿 | 交付无效，恢复原验收标准后重跑 |
| R-05 | 在基线本身跑不起来时继续叠加改动，或未经确认执行不可逆操作（删库、force push、清目录） | 立即停止，报告并等待用户决策 |
