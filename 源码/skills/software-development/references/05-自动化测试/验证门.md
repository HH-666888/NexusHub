## 一、定位

- **位置**：6 工序的第 ⑤ 道，交付前的强制判定点。
- **性质**：门不是工序——只执行校验、输出客观结果，不做语义裁定；判定不通过不得进入工序⑥。
- **输入**：工序④ 装配通过的完整项目。
- **输出**：验证证据（命令、关键输出、时间）。

## 二、五层合格线

| 层 | 校验动作 | 合格线 |
|---|---|---|
| 环境预检 | 确认工具链可用：JDK/Maven、Python/pip、Node/npm、MySQL 客户端、Go（按所选栈取） | 版本满足分支文件约束；缺工具链立即停止并报告缺什么、怎么装，不得跳过 |
| 后端 | 依赖安装 → 服务启动 → 接口连通（成功与失败各至少一条） | 依赖安装无致命错误；服务可启动且无启动期异常；示例接口返回统一返回体，状态码与预期一致（含 401/400 负例） |
| 前端 | 依赖安装 → 构建 → 启动后页面可访问 | 依赖安装成功；生产构建零报错；启动后首页与至少一条受保护路由可访问，静态资源无 404；形态 B/D 的静态资源可直接打开且引用路径有效 |
| 数据库 | 空库从头执行建表/迁移脚本 → 重复执行校验 | 脚本从头执行无报错，表、字段、索引、外键全部建成；幂等脚本可重复执行，非幂等脚本由迁移工具记录版本且不重复跑 |
| 全栈联调 | 前端经 REST 调用后端，后端经 ORM 访问数据库 | 至少一条端到端链路连通，返回体符合接口规范，认证挂载点对白名单与受保护接口行为正确 |

## 三、各栈具体验证命令

**后端**

- Java + Spring Boot（`后端-Java-SpringBoot.md` §11）：
  - 环境预检：`java -version`、`./mvnw -v`（Windows `mvnw.cmd -v`）；MySQL 可连
  - 依赖：`./mvnw -q -DskipTests dependency:resolve`（Windows `mvnw.cmd`）
  - 启动：`./mvnw spring-boot:run`（或 `./mvnw -DskipTests package` 后 `java -jar target/<artifactId>.jar`）
  - 连通：`curl -i -X POST http://localhost:8080/api/v1/auth/login ...` 期望 200 含 `"code":0` 与 token；受保护接口带 Bearer token 期望 200
- Python + FastAPI（`后端-FastAPI.md` §11）：
  - 环境预检：`python --version`（3.10+）、`pip --version`；MySQL 可连
  - 依赖：`python -m venv .venv` → 激活 → `pip install -r requirements.txt`
  - 启动：`uvicorn app.main:app --reload --port 8000`（生产 `--host 0.0.0.0 --port 8000` 不带 `--reload`）
  - 连通：`curl -i -X POST http://localhost:8000/api/v1/auth/login ...`；受保护接口带 token 期望 200

**前端**

- Next.js（`前端-Next.js.md` §13）：
  - 环境预检：`node -v`、`npm -v`，版本满足官方约束
  - 依赖：`npm install`（或 pnpm/yarn，与工程一致）
  - 检查：`npm run lint` 通过，无 error 级告警
  - 构建：`npm run build` 零报错（构建顺带做类型检查）
  - 启动自检：`npm run start` / `npm run dev`，首页与至少一条受保护路由可访问；形态 C 下至少一个 `/api/v1/` 示例接口按接口定义返回统一返回体
- 原生 HTML（`前端-原生HTML.md` §10）：
  - 环境预检：无需构建工具链；用浏览器或 `python -m http.server` 起静态服务验证；只检查文件存在不算通过
  - 页面可打开：浏览器直接打开 `index.html` 与至少一个内页，控制台无致命错误、无资源 404

**数据库**

- MySQL（`数据库-MySQL.md` §11）：
  - 环境预检：`mysql --version` 输出客户端版本；`SELECT VERSION();` 返回服务端版本；目标库存在且有建表权限
  - 从头完整执行：空库跑通 `baseline/` 全套 DDL（或迁移工具从空库回放全部 `migrations/`），无报错
  - 可重复/顺序校验：幂等脚本**连续执行两次**均成功；非幂等脚本提供迁移工具执行记录（版本表）作为证据
  - 表结构核验：按表结构清单核验表、字段、索引、外键全部建成

## 四、执行约定

1. 命令按当前 shell 改写：Windows 用 `mvnw.cmd` / `npm.cmd` / `curl.exe`，含 JSON 的参数用文件或正确转义；判定标准不因 shell 变化。
2. 每项验证保留证据（命令、关键输出、时间），写入交付说明；未执行的项标「未验证」，不得写「通过」。
3. 环境预检失败不计入回流重试，直接报告缺什么、怎么装。
4. 验证必须在真实运行的服务上发起真实请求；用 mock、假数据或跳过接口制造的「通过」一律视为未验证（红线 R-02）。
5. 原型阶段的占位数据（`原型开发.md` §四）只用于设计验证，不作为本门证据；前端验收使用真实接口真实数据。
6. 期望值先于实现确定；实现与预期冲突时改实现，不改预期（SKILL.md §4.3）。

## 五、红线

以下行为一经发现，交付即判定无效，必须回到对应工序返工（SKILL.md §5 原文）：

| 编号 | 红线 | 判定后果 |
|---|---|---|
| R-01 | 把未实现或未验证的东西说成「已完成 / 已支持」 | 交付无效，回流工序③ |
| R-02 | 用 mock、假数据、跳过接口或只跑成功路径制造「验证通过」 | 交付无效，重新执行验证门 |
| R-03 | 提交真实密钥、token、`.env` | 立即移除并轮换密钥 |
| R-04 | 用删测试、注释断言、放宽规则、改预期的方式让验证变绿 | 交付无效，恢复原验收标准后重跑 |
| R-05 | 在基线本身跑不起来时继续叠加改动，或未经确认执行不可逆操作（删库、force push、清目录） | 立即停止，报告并等待用户决策 |

**本工序判定**：五层合格线全部通过 + 证据齐全 → 进入工序⑥ 验收交付；任一失败 → 按 SKILL.md §2.4 回流，连续 3 次不通过按 §2.5 止损。
