# 接口示例测试

> 跨栈通用接口示例测试模板。每个对外接口必须配套一份标准示例，与接口定义 1:1 同步产出，验证门直接执行该示例。
> 示例中 JSON 字段命名遵循接口规范 §2.1：协议字段（信封、分页、令牌）snake_case，业务对象字段 camelCase（如 `userId` / `createdAt`）。

## 一、配套规则

1. 每个对外接口必须配套一份接口示例测试，与接口定义在工序③ 同步产出，保证 1:1 对应。
2. 示例承担双重职能：既是接口文档，也是验证门的可执行校验用例。
3. 验证门的接口连通环节直接按示例发起真实请求，预期不符即判定不通过。
4. 不引入具体测试框架（如 JUnit、pytest、Jest），不覆盖单元测试；本文件只管接口级示例。
5. 每个示例必须包含：请求方法与路径、请求头、请求体、预期 HTTP 状态码、预期统一返回体（成功与失败各一份）。

---

## 二、标准模板

每个接口示例按以下模板填写，字段为固定契约：

```
### 接口名称：{接口中文名}

**请求**
- 方法：{GET / POST / PUT / PATCH / DELETE}
- 路径：/api/v1/{资源路径}
- 请求头：
  Content-Type: application/json
  Authorization: Bearer <token>    # 受保护接口必填；公开接口不写此行
- 请求体 / 查询参数：
  {JSON 或 key=value 形式}

**预期成功响应**
- HTTP 状态码：{200 / 201}
- 返回体：
  {完整 JSON，code=0}

**预期失败响应（至少一种典型失败）**
- HTTP 状态码：{400 / 401 / 403 / 404 / 409}
- 返回体：
  {完整 JSON，code=非 0}
```

## 三、场景一：分页列表接口示例

### 接口名称：获取用户分页列表

**请求**
- 方法：GET
- 路径：`/api/v1/users?page=1&page_size=10&sort_by=createdAt&sort_order=desc`
- 请求头：
  ```
  Content-Type: application/json
  Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
  ```
- 请求体：无（GET 请求）

**预期成功响应**
- HTTP 状态码：`200`
- 返回体：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [
      {
        "userId": 1,
        "userName": "张三",
        "email": "zhangsan@example.com",
        "createdAt": "2026-11-01T10:00:00+08:00"
      },
      {
        "userId": 2,
        "userName": "李四",
        "email": "lisi@example.com",
        "createdAt": "2026-11-01T11:30:00+08:00"
      }
    ],
    "total": 56,
    "page": 1,
    "page_size": 10
  }
}
```

**预期失败响应（参数错误）**
- HTTP 状态码：`400`
- 返回体：

```json
{
  "code": 10001,
  "message": "参数错误：page 必须大于等于 1",
  "data": null
}
```

## 四、场景二：创建资源接口示例

### 接口名称：创建用户

**请求**
- 方法：POST
- 路径：`/api/v1/users`
- 请求头：
  ```
  Content-Type: application/json
  Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
  ```
- 请求体：

```json
{
  "userName": "王五",
  "email": "wangwu@example.com",
  "password": "MyPass123"
}
```

**预期成功响应**
- HTTP 状态码：`201`
- 返回体：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "userId": 3,
    "userName": "王五",
    "email": "wangwu@example.com",
    "createdAt": "2026-11-02T14:30:00+08:00"
  }
}
```

**预期失败响应（冲突）**
- HTTP 状态码：`409`
- 返回体：

```json
{
  "code": 10005,
  "message": "冲突：邮箱已被注册",
  "data": null
}
```

## 五、场景三：鉴权失败接口示例

### 接口名称：获取当前用户详情（未携带令牌）

**请求**
- 方法：GET
- 路径：`/api/v1/users/1`
- 请求头：
  ```
  Content-Type: application/json
  ```
  （未携带 `Authorization` 请求头）
- 请求体：无

**预期成功响应（携带有效令牌时）**
- HTTP 状态码：`200`
- 返回体：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "userId": 1,
    "userName": "张三",
    "email": "zhangsan@example.com"
  }
}
```

**预期失败响应（未认证）**
- HTTP 状态码：`401`
- 返回体：

```json
{
  "code": 10002,
  "message": "未认证：请先登录",
  "data": null
}
```

## 六、验证门执行规则

1. 验证门执行接口连通时，从本文件（或工程内接口文档位置）读取对应接口的标准示例，按示例中的方法、路径、请求头、请求体发起真实 HTTP 请求。
2. 校验项：
   - 实际 HTTP 状态码是否与预期一致。
   - 实际返回体的 `code` 字段是否与预期一致。
   - 实际返回体的顶层字段是否为 `code` / `message` / `data` 三字段，无多余字段。
   - 分页接口的 `data` 结构是否包含 `list` / `total` / `page` / `page_size` 四字段。
3. 任一项不符即判定该接口验证不通过，按判定回流规则退回工序③ 对应步骤修正后重过验证门。
4. 示例中的 `<token>` 占位符在验证门执行时替换为实际登录获取的有效令牌。
5. 公开接口（白名单内）的示例不写 `Authorization` 请求头；受保护接口的示例必须写。
