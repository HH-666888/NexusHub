## 一、选型总流程

```
需求规格
   ↓
① 特征权重判定（§二）→ 决定技术方向（Java 系 / Python 系 / 按默认主干）
   ↓
② 对照表定栈（§三/§四/§五）→ 在方向内定具体栈（Spring Boot？FastAPI？MySQL？）
   ↓
③ 组合合理性检查（§七）→ 四条检查 + 三项查表
   ↓
④ 写决策记录 → 回写需求规格 §9
   ↓
⑤ 路由分支文件（§八）→ 按《SKILL.md》§3 加载工序③ 文件
```

**选型原则**（贯穿全程，违反即选型不合格）：

1. **排序依据固定为三项，权重从高到低**：场景适配度 → 主流程度 → 兼容性。
2. **形态约束优先**：所选技术栈必须全部落在当前形态的可达路径内（见 `形态判定.md` §四）。形态不可达的组合直接排除，不进入对照。
3. **主干优先**：默认选择【主干】分支；只有需求给出明确理由（团队熟悉度、既有代码、生态要求）才选【扩展】分支，并在决策记录中写明理由。
4. **可自动确定的事项直接执行，不反问**；仅在关键大选择（项目形态、语言、框架级决策）无法从需求与默认路径确定时，才按《SKILL.md》§2.1 发起征询。
5. **分层决策**：§二 只定语言方向（Java 系 / Python 系）；同方向内具体栈由 §三/§四/§五 对照表决定——两件事分开做，不混在一起。

## 二、特征权重判定（决定方向）

### 2.1 为什么按特征判

选型不是"Java 好还是 Python 好"，而是**按项目特征决定权重，再映射到栈**。同一个"回测"需求，研究阶段和生产阶段结论不同；同一个"AI 应用"，加不加高并发服务层结论也不同。特征权重判定把这类差异显式化，让选型可解释、可复查。

### 2.2 五特征表

分两级：**主特征**（强命中直接决定方向）与**修正特征**（主特征不区分时打破平局）。

| # | 特征 | 判定问题 | 高命中指向 | 说明（避免写错） |
|---|---|---|---|---|
| 1 | 计算密集度（主） | 核心逻辑是否含大规模数值运算、回测、图像/信号处理？ | 生产/大规模 → Java/C++；研究/验证 → Python | Python 数据处理生态强、底层 C 向量化不慢；慢在纯 Python 循环与高并发吞吐。**研究用 Python、生产要性能上 Java**，不写"回测就 Java" |
| 2 | 业务复杂度与并发（主） | 业务规则是否复杂、事务是否多、是否高并发交互、是否企业级？ | Java | JVM 并发模型、Spring 生态、企业级中间件成熟 |
| 3 | AI 生态依赖（主） | 是否以 LLM 调用、Agent 编排、RAG、ML 为主？ | Python | OpenAI/LangChain/LlamaIndex 等 SDK 均 Python 优先；AI 编排几乎不涉及计算密集与业务并发 |
| 4 | 团队存量（修正） | 团队 / 用户是否已有既定技术栈？ | 存量优先 | 仅在主特征不区分时生效，不覆盖特征 1-3 强命中 |
| 5 | 交付节奏（修正） | 优先快速原型（竞赛/演示/验证）还是长期稳定运营？ | 原型 → Python；长期 → Java | 仅在主特征不区分时生效 |

### 2.3 判定步骤

1. **逐特征判定**：对需求规格逐项过 2.2 五特征表，每个特征给出"高 / 中 / 低"或"命中 / 未命中"结论，结论依据写进决策记录。
2. **主特征方向**：统计特征 1-3 的指向——≥2 个指向同一栈，或唯一"高"命中 → 方向确定；全部"低 / 未命中" → 走默认主干（见 §2.4 规则 3）。
3. **修正特征打破平局**：主特征指向不明确（一票对一票）时，用特征 4-5 打破。
4. **形态过滤**：方向结果必须落在当前形态可达路径内（`形态判定.md` §四），不可达则换次优方向。
5. **定栈**：按 §三/§四/§五 对照表在方向内定具体栈。
6. **落记录**：方向结论 + 各特征判定依据 + 定栈结果 → 写入需求规格 §9 决策记录。

### 2.4 冲突规则

| 情形 | 处理 |
|---|---|
| 主特征 ≥2 指向同一栈 | 直接按该栈选型 |
| 主特征冲突（例：计算密集 + AI 依赖并存） | 按主业务定位分层：以 AI 编排为主 → Python；以数值计算为主、AI 只是附庸 → Java |
| 主特征全低 / 无命中 | 走默认主干：后端 Java（Spring Boot）、前端按形态取 Next.js / 原生 HTML、数据库 MySQL（对齐 SKILL.md §3.2 主干路径） |
| 主特征不区分时 | 修正特征（团队存量、交付节奏）打破平局 |
| 仍平局 | 按选型原则第 1 条：场景适配度 → 主流程度 → 兼容性 |

### 2.5 典型场景对照（特征 → 结论）

| 场景 | 特征命中 | 结论 |
|---|---|---|
| 业务型应用（管理系统、交互平台） | 特征 2 高 | Java（并发 + 企业级生态） |
| 股票回测：策略研究 / 验证 | 特征 1 高，但处于研究阶段 | Python（生态 + 迭代快，backtrader/pandas） |
| 股票回测：生产 / 大规模实盘 | 特征 1 高，生产阶段 | Java（JIT 计算性能 + 并发），极端再上 C++ |
| 纯 AI 应用（LLM 调用、Agent 编排） | 特征 3 高，特征 1/2 低 | Python（AI 生态优先） |
| AI 应用 + 高并发服务层 | 特征 3 高 + 特征 2 中 | 分层：编排逻辑 Python，服务网关 / 接口层 Java / Go |
| 简单 CRUD、无计算无并发无 AI | 特征全低 | 默认主干（§2.4 规则 3） |

## 三、后端选型对照

| 编号 | 项目特征 | 推荐栈 | 主干/扩展 | 命中条件（对齐 SKILL.md §3.2） |
|---|---|---|---|---|
| B1 | 传统企业级、JVM 生态、Spring 体系、需要成熟生态 | Java + Spring Boot | 主干 | 后端选 Java，或需求指定 JVM 体系 / Spring 生态 |
| B2 | 快速迭代、类型安全、异步性能好、Python 团队 | Python + FastAPI | 主干 | 后端选 Python，或需求指定 Python 接口服务 |
| B3 | 已有 Django 生态、或团队强偏好 Django/Flask | Flask / Django | 扩展 | 后端选 Flask 或 Django |
| B4 | 轻量接口服务、Node/Go 团队、或形态 D 轻量接口 | Node.js / Go | 扩展 | 后端选 Node.js 或 Go；形态 D 按单文件服务加载 |

**判定规则**：

- §二 特征权重判定已定语言方向（Java 系 / Python 系）后，在本表对应行内定具体栈：Java 方向 → B1（Spring Boot）；Python 方向 → B2（FastAPI）；B3/B4 仅在有明确理由（既有生态、团队偏好、形态 D）时选，理由写入决策记录。
- 形态 D 的轻量接口：仅允许 `后端-Node-Go.md` 的单文件服务形态（一个入口文件 + 一个配置），不按分层工程展开。

## 四、前端选型对照

| 编号 | 项目特征 | 推荐栈 | 主干/扩展 | 命中条件 |
|---|---|---|---|---|
| F1 | React 体系、需要路由/组件化、或形态 C | Next.js | 主干 | 前端选 Next.js / React 体系，或形态 C |
| F2 | 简单页面、无框架需求、或形态 D、形态 B 静态资源 | 原生 HTML/CSS/JS | 主干 | 前端选原生 HTML/CSS/JS，或形态 D、形态 B 静态资源 |
| F3 | 形态 B 需要后端模板渲染 | 模板页（Thymeleaf / Jinja2） | 单体专用 | 形态 B 需要后端模板渲染 |
| F4 | Vue 团队、或明确指定 Vue | Vue | 扩展 | 前端选 Vue |

**判定规则**：

- 形态约束直接决定可达路径：形态 A → F1 或 F4；形态 B → F3（页面渲染）+ F2（静态资源）；形态 C → F1；形态 D → F2。
- 形态 A 下 F2（原生 HTML）可达但通常不推荐——有交互复杂度时优先 F1/F4。

## 六、版本策略

- 不锁死具体版本号，只写约束：稳定版、组件适配、官方当前推荐实践。
- 具体版本由推理层在执行时判定；验证门（工序⑤）负责暴露不兼容并触发回流。
- 判定前应核对官方发布说明与兼容矩阵。无法联网时，选取已知稳定大版本，并在交付说明的「已知限制」中标注版本假设与后续升级点。

## 七、组合合理性检查点

选型完成后，**四条检查全部通过才放行进入工序③**；任一条不通过按《SKILL.md》§2.4 回流。

1. **形态可达性**：所选技术栈全部落在当前形态的可达路径内（以 `形态判定.md` §四 为准）。例如形态 B 不可达独立前端工程，形态 C 不可达独立后端工程。
2. **组件适配**：ORM 与数据库正确配对（§五 配对表）；前端调用协议与后端一致（统一 REST）；认证、配置等组件与框架版本兼容。
3. **版本约束**：均为稳定版本，组件间相互兼容，符合官方当前推荐实践；不使用已废弃或预览版组件。
4. **规模边界**：整体方案处于中小型范围内，未引入微服务、消息中间件集群等超范围组件，未触碰 SKILL.md §0.1 排除项。

**确定性校验项（可客观核查的部分，由命令或脚本客观判定）**：

| 编号 | 校验 | 方法 |
|---|---|---|
| C1 | 形态可达路径 | 对照 `形态判定.md` §四 可达规则逐角色查表 |
| C2 | ORM × 数据库配对 | 按 §五 配对表查表 |
| C3 | 版本兼容 | 按 §六 约束核对官方发布说明与兼容矩阵 |

语义项（方案整体适配度、规模判断）由推理层判定，不因查表通过而豁免。
