## 一、三层结构

需求规格不采用平铺列表，按三层组织 + 每片标签：

```
需求域（业务顶层，如"图书借阅"）
├── 需求组（功能域，如"借阅流程"）
│   ├── 需求片 R1（原子单元：语义完整可核验 + 三标签 + 三轴级别）
│   ├── 需求片 R2
│   └── …
└── 需求组（功能域，如"图书管理"）
    └── …
```

**引用规则**：下游（接口、页面、表、验收）一律按**需求片编号**引用，不引用整篇需求文档。

## 二、优先级

目标：让工序⑥ 验收时能区分"必做"与"可延后"，也让最小可交付集可判定。对应切片分级中的价值层。

| 级别 | 含义 | 判定标准 |
|---|---|---|
| P0 | 必做 | 缺失则系统不可用或核心流程断裂 |
| P1 | 应做 | 完整交付的一部分，缺失影响体验但可运行 |
| P2 | 可选 | 增强功能，可在 P0/P1 完成后追加 |

**规则**：

- 默认把"核心业务闭环"标 P0（如：登录、主业务 CRUD、核心查询）。
- 用户明确强调的需求自动升为 P0。
- 所有 P0 需求构成工序⑥ 验收的**强制通过项**；P1/P2 未覆盖不阻塞交付，但必须在交付说明中记录。

## 三、歧义处理

目标：需求表述不清时，用**最低成本**消除歧义，不阻塞流程。

**处理规则（按顺序尝试）**：

1. **可合理推断**：结合上下文能唯一确定的，按合理理解执行，**并写入假设记录**（如"用户说'列表'，按分页列表理解"）。
2. **影响核心结果的歧义**：发起征询，一次问完，最多 3 个问题（延续 SKILL.md §2.1 征询原则）。
3. **不影响结果的歧义**：选择默认实现并记录，不发起提问。

**必须**：

- 每个假设都有"假设来源 + 影响范围"记录。
- 假设在工序⑥ 验收时逐条复核，与实际不符即回流修正。

- 需求片编号连续（R1、R2…），下游按编号引用。

## 五、产物落盘

- 需求规格**必须**写入工程根 `docs/requirements.md`，随项目提交，并落盘为项目文件。
- 落盘后立即自检：模板关键节齐全（背景/角色/实体/需求/范围/约束/优先级/假设/决策记录/验收对照）、每片有验收条件、无未记录的假设——不满足则本工序不通过。
- 生成过程中发现缺项或需求变更：回流本工序对应步骤追加/修订，再重走受影响步骤。
