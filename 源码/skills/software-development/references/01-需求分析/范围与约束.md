## 一、范围边界

目标：明确"做什么"与"明确不做什么"，防止范围蔓延。

1. **正面清单**：列出本系统要交付的功能组（对应需求片分组）。
2. **排除项**：明确列出**不做**的部分，写入规格——例如"不做移动端 App""不做消息推送""不做多租户"。排除项来自：用户明确说不做、超出中小型范围（微服务、分布式）、本 skill 范围外（见 SKILL.md §0.1）。
3. **最小可交付集判定**：如果需求可分批，标出"第一批必须交付"的最小集，防止一次交付面过大。

**检查清单**：

- [ ] 排除项已写入规格（无"用户没提就当没这回事"的隐性排除）
- [ ] 每条需求都能归属到某个功能组
- [ ] 明确最小可交付集（适用时）

## 二、隐含约束清单

目标：把用户没明说但必须满足的约束**逐项主动检查**并记录。以下每项都要给出结论（有约束/无约束），不留空：

| 检查项 | 检查问题 | 记录方式 |
|---|---|---|
| 性能 | 响应时间、并发量、数据量是否有要求？ | 无 → 记"无明确性能要求"；有 → 记量化指标 |
| 安全 | 是否需要登录、权限分级、敏感数据脱敏？ | 无 → 记"无认证需求"；有 → 记认证方式 |
| 并发 | 是否存在多人同时操作同一数据（抢单、库存）？ | 有 → 记并发控制要求，对接工序③ |
| 部署环境 | 运行在什么环境（本机、内网服务器、公网）？ | 记环境与依赖（JDK/Node/MySQL 版本约束） |
| 数据规模 | 数据量级（千/万/百万级）？是否需要导入导出？ | 记量级与数据迁移需求 |
| 合规 | 是否涉及敏感个人信息、合规要求？ | 涉及 → 记合规约束（脱敏、留存） |
| 设备/浏览器 | 是否需要兼容特定浏览器或分辨率？ | 记兼容范围 |

**规则**：约束不确定时按《需求规格模板.md》§歧义 标注待确认，不默认"没有要求"。

**衔接**：本清单与《提问规划.md》的 11 维提问有交叉（非功能、部署运维维度）——提问已明确的项直接回填本清单，不重复提问；本清单负责**逐项检查兜底**，确保无漏项。
