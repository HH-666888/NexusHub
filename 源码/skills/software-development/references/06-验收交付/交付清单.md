## 一、定位

- **输入**：工序⑤ 验证门通过的完整项目。
- **产物**：交付包（6 项交付物）。
- **核心原则**：验收以**需求规格（`docs/requirements.md`）为唯一基线**——不是"项目能跑就算完成"，而是"需求逐条落实、未覆盖项有明确记录"。

## 二、交付物清单

| 序号 | 交付物 | 要求 |
|---|---|---|
| 1 | 可运行项目 | 目录结构与分支文件一致；数据库、后端、前端三方向产物完整；引用关系闭合 |
| 2 | 接口定义 | 每个对外接口的方法、路径、请求头、入参、统一返回体、错误码，与实现 1:1 |
| 3 | 接口示例测试 | 每个接口配套标准请求与预期返回，与接口定义同步产出，同时承担接口文档职能 |
| 4 | 运行说明 | 依赖安装、配置项、启动命令与初始化数据的最小说明，写入项目根 `README.md` |
| 5 | 需求验收对照 | `docs/requirements.md` 中逐条标注落实位置（文件/接口）、验证方式与结果（通过 / 未覆盖及原因） |
| 6 | 回滚说明 | 使用 git 时提交一次基线并注明提交号；未使用时在 README 写明改动文件清单与手工回滚步骤 |

全覆盖单元测试体系不纳入默认交付。

## 三、验收核对表

按以下顺序逐项核对（需求规格 §10 验收对照表为本表的落盘位置）：

| 步骤 | 核对内容 | 合格线 |
|---|---|---|
| 1 | 逐条需求 R1..Rn 找落实位置（文件/接口） | 每条需求都有明确落实位置，无"找不到对应实现"的需求 |
| 2 | 逐条验证（结合工序⑤ 证据） | P0 需求全部通过；P1/P2 未覆盖项记录原因 |
| 3 | 验证方式与结果写入需求规格 §10 | 每行：位置 / 方式 / 结果（通过 / 未覆盖及原因） |
| 4 | 六项交付物齐备 | 全部存在且符合 §二 要求 |
| 5 | 交付说明 | 写入验证方式、覆盖范围、结果与已知限制；未执行项标「未验证」，不得写「通过」 |

**规则**：

- P0 需求未覆盖 = 验收不通过，回流处理，不得交付。
- P1/P2 未覆盖：必须在需求规格验收对照中记录原因与后续计划，方可交付。
- 未验证项（如环境缺失导致某层没跑）必须如实标注「未验证」，不得写「通过」。

## 四、失败回流

验收核对发现问题时，按 SKILL.md §2.4 携带可复现信息回流：

| 发现的问题 | 回流节点 | 必须携带的信息 |
|---|---|---|
| 架构/形态与需求矛盾 | 工序② 架构设计 | 矛盾需求、形态选择、矛盾点 |
| 代码/接口问题 | 工序③ 三方向开发 | 失败需求、落实位置、复现命令与预期 |
| 装配/联调问题 | 工序④ 集成装配 | 断裂点、链路、期望与实际 |
| 验证问题 | 工序⑤ 自动化测试 | 失败层、命令、输出、预期 |

回流修正后重走受影响工序，回到本工序重新核对。连续 3 次不通过按 SKILL.md §2.5 止损。

## 本工序判定

六项交付物齐备 + P0 需求全部通过 + 验收对照完整落盘 → **交付完成**。全部六道工序至此闭环。
