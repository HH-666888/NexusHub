## 一、RESTful 方法与路径设计

### 1.1 路径通用规则

1. 所有接口路径以 `/api/v1/` 为统一前缀。
2. 路径末段为资源名词，一律复数、全小写、多词用连字符 `-` 分隔。
3. 嵌套资源格式：`/api/v1/{父资源}/{父id}/{子资源}`，层级不超过 3 层。
4. 路径参数统一用 `{}` 包裹，一律小写 snake_case：主键固定 `{id}`，业务含义参数用 `{order_id}`、`{user_id}` 这类写法。URL 属协议层，不随所选语言的代码命名变化。
5. 非 CRUD 的业务动作通过子路径表达，如 `/api/v1/orders/{id}/cancel`、`/api/v1/users/{id}/disable`。

### 1.2 路径示例

| 业务含义 | 方法 | 路径 |
|---|---|---|
| 获取用户列表 | GET | `/api/v1/users` |
| 获取单个用户 | GET | `/api/v1/users/{id}` |
| 创建用户 | POST | `/api/v1/users` |
| 全量更新用户 | PUT | `/api/v1/users/{id}` |
| 部分更新用户 | PATCH | `/api/v1/users/{id}` |
| 删除用户 | DELETE | `/api/v1/users/{id}` |
| 获取某用户的订单列表 | GET | `/api/v1/users/{id}/orders` |
| 取消订单 | POST | `/api/v1/orders/{order_id}/cancel` |

## 二、统一返回体结构

所有接口（成功与失败）统一返回如下 JSON 结构，以下字段为固定契约：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `code` | integer | 业务状态码。`0` 表示成功；非 `0` 表示业务错误码，详见第三节 |
| `message` | string | 人类可读提示信息。成功时为 `"success"`；失败时为错误描述，可直接展示给用户 |
| `data` | object \| array \| null | 业务数据。成功时承载返回内容；失败时为 `null` 或空对象 `{}` |

**通用要求：**

1. 成功响应的 `code` 必须为 `0`，`message` 为 `"success"`。
2. 失败响应的 `data` 为 `null` 或空对象，不夹带业务数据。
3. 响应体顶层只有 `code` / `message` / `data` 三字段，不出现 `success`、`status`、`error` 等额外字段。

### 2.1 JSON 字段命名总则（协议字段 snake_case，业务字段 camelCase）

全工程 JSON 报文字段命名分为两类，规则确定后全栈统一执行：

| 字段类别 | 命名 | 示例 | 说明 |
|---|---|---|---|
| 协议字段 | snake_case | `code` / `message` / `data` / `page` / `page_size` / `sort_by` / `sort_order` / `total` / `list` / `access_token` / `refresh_token` / `token_type` / `expires_in` | 信封结构、分页参数、令牌字段、错误码相关，跨语言固定 |
| 业务对象字段 | camelCase | `userId` / `userName` / `createdAt` / `orderStatus` | 资源属性，随业务定义，前后端契约一致 |
| 数据库列（非 JSON 层） | snake_case | `user_id` / `created_at` | 仅存在于存储层，由 ORM 映射到 JSON 业务字段 |

**跨语言落地方式：**

1. **Java**：实体 / DTO 字段天然 camelCase，直接输出业务字段；协议字段用注解对齐（分页入参 `@RequestParam(name="page_size")`、出参 `@JsonProperty("page_size")`）。
2. **Python（Pydantic）**：模型内部字段 snake_case（Python 惯例）；业务出参 schema 用 `alias` 输出 camelCase（`model_config = ConfigDict(populate_by_name=True)`），协议字段天然 snake_case。
3. **JS / TS**：业务对象属性直接 camelCase；协议字段按本表字面量使用（拼查询串与解析返回体时写 `page_size`）。
4. `sort_by` 取值与接口返回的 JSON 业务字段一致（camelCase，如 `createdAt`），允许排序的字段白名单在接口定义中列出，后端映射回数据库列。
5. 64 位整型 ID 默认按 number 输出；超出 JS 安全整数（2^53）或使用 Prisma `BigInt` 时，接口定义与实现统一改为 string，同一字段全量一致（number 或 string 二选一）。

## 三、HTTP 状态码与业务错误码

### 3.1 HTTP 状态码语义对齐

| HTTP 状态码 | 语义 | 触发场景 |
|---|---|---|
| 200 | 成功 | GET / PUT / PATCH / DELETE 成功 |
| 201 | 已创建 | POST 创建资源成功 |
| 400 | 请求参数错误 | 入参校验失败、格式非法 |
| 401 | 未认证 | 未携带令牌、令牌过期或非法 |
| 403 | 无权限 | 已认证但无权访问该资源 |
| 404 | 资源不存在 | 路径不存在或目标记录不存在 |
| 409 | 冲突 | 唯一约束冲突、状态冲突 |
| 500 | 服务器内部错误 | 未捕获的系统异常 |

### 3.2 通用业务错误码

业务错误码放在返回体的 `code` 字段，与 HTTP 状态码配合使用。

| code | message | 对应 HTTP 状态码 | 含义 |
|---|---|---|---|
| 0 | success | 200 / 201 | 成功 |
| 10001 | 参数错误 | 400 | 入参缺失、类型错误、长度或范围不合法 |
| 10002 | 未认证 | 401 | 未登录或令牌失效 |
| 10003 | 无权限 | 403 | 已登录但无操作权限 |
| 10004 | 资源不存在 | 404 | 目标记录不存在 |
| 10005 | 资源冲突 | 409 | 唯一约束冲突或状态冲突 |
| 50000 | 系统繁忙，请稍后重试 | 500 | 未捕获的系统异常、代码缺陷、数据库连接失败 |
| 50001 | 服务暂不可用，请稍后重试 | 502 / 500 | 依赖的第三方服务超时或不可用 |

### 3.3 业务模块错误码分段

业务模块错误码从 `11000` 起，按模块分段，每模块预留 100 个号段：

| 模块 | 错误码区间 | 示例 |
|---|---|---|
| 用户模块 | 11000 – 11099 | `11001` 用户名已存在 |
| 订单模块 | 11100 – 11199 | `11101` 订单状态不允许取消 |
| 支付模块 | 11200 – 11299 | `11201` 支付金额不匹配 |

**通用要求：**

1. 通用错误码固定为 `10001`–`10005`。
2. 业务模块错误码在对应模块内连续编号。
3. `message` 为可直接展示给用户的中文描述，内部异常类名或堆栈信息不进入其中。
4. 系统级错误码固定为 `50000`–`50099` 号段，与通用客户端错误码 `10001`–`10005` 分号段使用。

## 四、入参校验规则

### 4.1 校验维度

| 校验项 | 规则 | 失败时返回 |
|---|---|---|
| 必填 | 必填字段缺失时直接拒绝 | code=10001 |
| 类型 | 字段类型必须与定义一致（字符串/数字/布尔/数组/对象） | code=10001 |
| 字符串长度 | 最小长度与最大长度按业务定义，超出即拒绝 | code=10001 |
| 数字范围 | 数值型字段需标注最小值与最大值，超出即拒绝 | code=10001 |
| 枚举值 | 有限可选值必须在白名单内，否则拒绝 | code=10001 |
| 格式 | 邮箱、手机号、URL 等需符合通用格式规则 | code=10001 |

### 4.2 校验位置

1. 所有入参校验必须在接口入口层完成，业务层不再重复做基础类型校验。
2. 校验失败时，直接抛出参数异常，由全局异常拦截器统一转换为 `code=10001` 的统一返回体。
3. 校验失败信息以统一返回体返回，堆栈不进入客户端响应。

## 五、分页与排序参数约定

### 5.1 分页请求参数

所有列表类接口统一使用以下查询参数：

| 参数名 | 类型 | 默认值 | 上限 | 说明 |
|---|---|---|---|---|
| `page` | integer | 1 | – | 页码，从 1 开始 |
| `page_size` | integer | 10 | 100 | 每页条数，最大不超过 100 |
| `sort_by` | string | – | – | 排序字段名，取 JSON 业务字段（camelCase，如 `createdAt`），白名单在接口定义中列出 |
| `sort_order` | string | `desc` | – | 排序方向，取值 `asc` 或 `desc` |

### 5.2 分页返回 data 结构

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [],
    "total": 0,
    "page": 1,
    "page_size": 10
  }
}
```

| 字段 | 含义 |
|---|---|
| `list` | 当前页数据数组 |
| `total` | 符合条件的总记录数 |
| `page` | 当前页码 |
| `page_size` | 每页条数 |

**通用要求：**

1. `page` 从 1 开始计数。
2. `page_size` 超过 100 时强制截断为 100。
3. 排序字段必须在接口定义中显式列出；未在白名单内的排序字段直接拒绝。

## 六、常见方法语义表

| HTTP 方法 | 语义 | 幂等性 | 典型场景 | 成功状态码 |
|---|---|---|---|---|
| GET | 查询资源，不修改数据 | 幂等 | 列表查询、详情查询 | 200 |
| POST | 创建资源，或执行非 CRUD 业务动作 | 非幂等 | 创建记录、取消订单、登录 | 201（创建）/ 200（动作） |
| PUT | 全量更新资源（需提交完整字段） | 幂等 | 全量修改用户信息 | 200 |
| PATCH | 部分更新资源（只提交需修改的字段） | 幂等 | 修改用户昵称 | 200 |
| DELETE | 删除资源 | 幂等 | 软删除或硬删除记录 | 200 |

**通用要求：**

1. GET 方法只承载查询，不执行写操作。
2. 创建资源优先用 POST；更新优先用 PUT（全量）或 PATCH（部分）。
3. 同一资源只保留一种更新入口（PUT 或 POST，不并存）。
