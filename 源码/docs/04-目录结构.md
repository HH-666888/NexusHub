# 目录结构规定

> 版本 v1.0 · 2026-11-01
> 配套文档：[`03-前后端分离契约书.md`](./03-前后端分离契约书.md)（接口、事件、数据层）
> 本文件管**代码放哪、谁能依赖谁**；契约书管**接口长什么样**。两者冲突时：接口以 03 为准，位置以 04 为准。

---

## 声明

1. **本文件是目录与依赖的唯一规定。** 新建文件前先在这里找到它的位置；找不到位置，说明这个文件不该存在，或者需要先改本文件。
2. **改动流程**：先改本文件（含版本号）→ 再动目录 → 再改代码。不允许"先把文件堆进去，回头再补文档"。
3. **三条不可协商的铁律**：
   - **目录即契约**：目录名必须能在对话、事件流、技术文档里对上号（尤其 `pipeline/stages/*` 的六个名字）。
   - **依赖单向**：`features → pipeline → ai → domain`，反向 import 一律视为 bug。
   - **没有杂项目录**：禁止 `utils/`、`common/`、`helpers/`、`misc/`。需要杂项，说明还没想清它属于哪个功能。
4. **违规怎么处理**：CI 上的两条检查（§4.3）红一次就算一次失败，与测试失败同等对待。
5. 本文件不定义接口细节。请求体、响应体、错误码、SSE 帧、事件字段，全部看契约书，**不要在代码里另立一套**。

```

└─ src/
   ├─ app/                            # 只有路由与组合，不写业务
   │  ├─ page.tsx                     #   首页（hero + 我的项目）
   │  ├─ canvas/page.tsx              #   画布页：唯一的数据装配点
   │  ├─ settings/page.tsx            #   设置页
   │  ├─ welcome/page.tsx             #   介绍页
   │  ├─ studio/page.tsx              #   旧工作台（保留兼容 /studio?run= 链接）
   │  ├─ home/page.tsx                #   旧地址，301 到 /
   │  ├─ (auth)/login/page.tsx        #   登录
   │  └─ (auth)/register/page.tsx     #   注册
   │
   ├─ features/                       # 业务切片：一个 feature 一块界面
   │  ├─ canvas/                      #   画布交互（含四分区里的清单/内容/边栏）
   │  │  ├─ components/               #     pipeline-canvas / canvas-stage / canvas-workbench
   │  │  │                            #     planning-outline / step-content / panel-dock
   │  │  │                            #     run-switcher / stage-detail / new-project-cta
   │  │  └─ hooks/                    #     use-animated-layout
   │  ├─ run/                         #   运行控制台、时间轴、过程流工作台
   │  │  └─ components/               #     cockpit / cockpit-header / run-list / run-timeline
   │  │                               #     process-blocks / run-workbench / generation-console
   │  ├─ gate/                        #   门禁表单与三个动作按钮（待从 run/ 抽出）
   │  ├─ artifact/                    #   预览 iframe、下载（待从 run/ 抽出）
   │  ├─ home/                        #   hero 输入、项目卡片行、能力展示
   │  ├─ welcome/                     #   介绍页的四个区块
   │  ├─ settings/                    #   外观面板、模型配置
   │  └─ auth/                        #   登录 / 注册表单
   │
   ├─ core/                           # 纯逻辑（无 React、无 fetch、无环境变量）
   │  └─ canvas/                      #   ← 长期留在这里：布局 / 视口 / 聚焦跟随（842 行）
   │                                  #   ⏳ 过渡：auth / domain / generate / pipeline /
   │                                  #      planning / ports / run / settings 逐刀迁往后端，
   │                                  #      迁完之后 core/ 里只剩 canvas
   │
   ├─ components/
   │  ├─ ui/                          # 跨 feature 的纯展示件（主题切换等）
   │  └─ layout/                      # 应用外壳：顶栏、栅格边距常量
   ├─ api/
   │  ├─ generated/                   #   @hey-api/openapi-ts 产物，禁止手改
   │  ├─ client.ts                    #   唯一的 HTTP 入口；错误信封只在这里解析
   │  └─ sse.ts                       #   EventSource 封装：未知 kind 忽略、断线提示
   └─ lib/                            # 主题变量、时间格式化、常量表
```

> **`core/` 是过渡态，不是终点。** 目录契约的终局是"前端只留 `core/canvas`，其余全在后端"。
> 现在 `core/` 里还有 7 类待迁代码，每一刀迁走一类；在那一刀落地前**不要**把新逻辑写进 `core/`
> —— 否则它会跟着一起搬，等于白搬两次。

### 前端的四条规则

| 规则 | 说明 |
|---|---|
| `app/` 只做组合 | 取数 + 传 props。**出现业务判断就下沉到 `features/`** |
| `features/` 之间不互相 import | 需要协作 → 下沉 `core/`（纯逻辑）或让 `app/` 组合 |
| `core/` 只放纯函数 | 不 import react、不碰 fetch、不读环境变量。可单测、可服务端跑 |
| 错误只在一处解析 | 组件里不允许出现 `res.ok` / `res.status` 判断，一律用 `api/client.ts` |

> 为什么 `core/canvas` 不塞进 `features/canvas/`：它是纯函数且带单测。放在 `core/` 才能立一条可检查的规则——"`core/` 里出现 `import react` 就是违规"。混进 features 后这条规则就废了。

### 后端每个目录"放什么 / 不放什么"

| 目录 | 放什么 | **不放什么** |
|---|---|---|
| `domain/` | Pydantic 模型与枚举常量 | 任何 import、任何逻辑、任何 ORM |
| `db/models.py` | SQLAlchemy ORM 声明 | 业务方法、Pydantic 模型 |
| `shared/` | 错误信封、SSE 工具、ID、时间、分页、限流常量 | 任何业务概念（出现 `run`/`spec` 字样就是错的） |
| `features/*/router.py` | 解析请求 → 调 service → 序列化 | 业务判断、SQL、模型调用 |
| `features/*/service.py` | 编排一次请求的业务 | SQL、把 ORM 对象传出边界 |
| `features/*/repo.py` | **唯一**碰 SQLAlchemy 的地方 | 业务规则、跨表编排 |
| `features/runs/projection.py` | 事件 → 清单/画布数据的投影（读侧） | 写库、调模型 |
| `pipeline/orchestrator.py` | 六道工序推进、门禁挂起、续跑入口 | HTTP、数据库 |
| `pipeline/stages/*/stage.py` | 单道工序：吃产物 + 模型客户端，吐产物 + 事件 | HTTP、数据库、跨工序调用 |
| `pipeline/stages/*/prompts.py` | 提示词字符串 | 任何逻辑（提示词是资产，要能单独 diff） |
| `ai/**` | 模型、RAG、工具、成本 | import `pipeline` 或 `features` |
| `content/playbook/**` | RAG 语料 markdown | 代码 |

## 4. 依赖方向

### 4.1 方向图

```
features ──▶ pipeline ──▶ ai ──▶ domain
    │            │         │
    └────────────┴─────────┴──▶ shared
```

`domain ← 谁都不依赖`；`shared ← 谁都能用`。

### 4.2 五条硬规则

| # | 规则 |
|---|---|
| D1 | `domain/` 不 import 项目内任何模块 |
| D2 | `ai/` 不 import `pipeline/`、`features/` |
| D3 | `pipeline/` 不 import `features/` |
| D4 | `features/` 之间不互相 import；需要协作走 `pipeline/` 或 `ai/` |
| D5 | 只有 `features/*/repo.py` 和 `db/` 可以 import SQLAlchemy；其它模块一律不碰 |

### 4.3 自动检查（进 CI，红一次算一次失败）

后端用 `import-linter`：

```toml
# pyproject.toml
[tool.importlinter]
root_packages = ["app"]

[[tool.importlinter.contracts]]
name = "domain 不依赖任何东西"
type = "forbidden"
source_modules = ["app.domain"]
forbidden_modules = ["app.features", "app.pipeline", "app.ai", "app.db", "app.shared"]

[[tool.importlinter.contracts]]
name = "ai 不依赖上层"
type = "forbidden"
source_modules = ["app.ai"]
forbidden_modules = ["app.pipeline", "app.features"]

[[tool.importlinter.contracts]]
name = "pipeline 不依赖 HTTP 层"
type = "forbidden"
source_modules = ["app.pipeline"]
forbidden_modules = ["app.features"]
```

前端用脚本（约 20 行）：扫 `src/features/*/`，若出现 `from "@/features/<其它名字>` 即报错；扫 `src/core/`，若出现 `from "react"` 或 `fetch(` 即报错。

## 5. 命名与粒度

| 项 | 规定 |
|---|---|
| Python 模块/包 | `snake_case`；类 `PascalCase`；常量 `UPPER_SNAKE` |
| 前端目录 | `kebab-case`；组件文件 `kebab-case.tsx`，导出 `PascalCase` |
| 一个文件一个主导出 | 组件文件只导一个组件；工具模块只导一组同主题函数 |
| 文件长度 | `router/service/repo` 目标 <200 行；超过就拆（如 `runs` 拆出 `projection.py`） |
| 提示词 | 永远单独文件 `prompts.py`，不内联在 `stage.py` |
| 测试文件 | 与源文件同名 + `test_` 前缀，放在镜像路径下 |
| 禁止的目录名 | `utils/`、`common/`、`helpers/`、`misc/`、`core/`（后端）、`base/` |

## 8. 反例清单（明确不要做）

| 反例 | 为什么错 |
|---|---|
| `backend/app/api/v1/routers/` 下再按业务分层 | 退回 Java 分层：一次生成要跨五个目录 |
| `domain/` 与 ORM 各写一份同名类、转换散落各处 | 转换只允许出现在 `repo.py`，否则字段永远对不上 |
| `features/runs/utils.py` | 用语义命名：`projection.py`、`time_label.py` |
| 把 RAG 塞进 `pipeline/` | 会造成 `pipeline → ai` 与 `ai → pipeline` 双向依赖 |
| 前端组件直接 `fetch` | 错误信封解析会散落，一个接口改格式就要找十处 |
| 在 `features/` 里直接调 `ai/model` | 绕过 pipeline，事件流里就没有这次调用的记录（成本、可观测性都丢） |
| 为每个 feature 建一套 `db/session.py` | 连接池会被建 N 次，MySQL 会打满连接数 |
