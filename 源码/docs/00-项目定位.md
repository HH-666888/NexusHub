# 项目定位（v2 · 目标态）

> 状态：**已确认，作为开发目标**。
> 说明：本文写的是「要做成什么样」，不是「现在已做到什么样」。
> 全部功能开发完成后，回头对照第五节逐条检查；确有偏差时，改这份文件，而不是改产品去迁就文字。

---

## 一、一句话定位

**通过 Agent 的工作流编排，面向软件开发的六大流程，实现对开发过程的完整控制；以可视化、透明的方式还原全部细节，最终生成可以直接执行的软件。**

---

## 二、展开：这句话的四个要素

### 1. Agent 的工作流编排

- 主控 Agent 负责拆解需求、派活、收口
- 六道工序各自认领任务，任务可拆分、可回退、可重跑
- 编排的粒度是**任务**，不是阶段；阶段只是任务的归类

### 2. 面向软件开发六大流程

固定映射到软件工程的六道工序：

| 序 | 工序 | 这一道要产出什么 |
|---|---|---|
| 01 | 需求分析 | 验收标准、边界（做什么 / 不做什么） |
| 02 | 架构设计 | 模块划分、数据流 |
| 03 | 自主开发 | 按依赖逐个文件写 |
| 04 | 集成装配 | 入口、路由、配置、依赖对齐 |
| 05 | 自动测试 | 用例、通过率、失败项与修复 |
| 06 | 验收交付 | 分层验收结论、可运行产物 |

### 3. 完整控制 + 可视化透明

- **控制**：暂停、继续、取消、回退、重跑当前道、预算到顶自动停
- **透明**：每一次决策、每一条任务、每一份产物、每一分花费都留痕，可回放
- **可核查**：任意一个节点点开，能看到它为什么存在、花了多久、产出了什么

### 4. 最终产物：可以直接执行的软件

- 不是代码片段、不是设计稿，是**能起进程、能被打开、能点**的软件
- 产物可下载、可本地运行
- 验收结论对应到具体层级（数据库 / 接口 / 页面）

---

## 三、边界：我们不做什么

| 不做 | 原因 |
|---|---|
| 通用 AI 助手（写作、绘画、闲聊） | 只做软件开发这一个场景 |
| 只出代码、不管跑不跑得起来 | 可执行是底线 |
| 黑箱式“一键生成” | 透明是核心卖点，过程必须可见 |
| 号称支持所有技术栈 | 先把一条链路做穿 |

---

## 四、口径约定（避免以后各说各话）

| 词 | 在我们的语境里指什么 |
|---|---|
| **编排** | 任务的动态拆分、顺序执行、回退与重跑；不是“阶段可配置” |
| **完整控制** | 暂停 / 继续 / 取消 / 回退 / 重跑 / 预算熔断，六种操作 |
| **透明** | 事件级留痕：任务、耗时、产物、失败原因、成本 |
| **可执行** | 能起进程、能打开页面、能被点击验证 |
| **Agent** | 一次任务执行单元；主控与工序都是 Agent 的不同角色 |

## 五、开发完成后的自检清单

全部功能做完后，逐条回答；答不上来的就是偏差：

1. 换一个没见过的需求，六道工序是否都能拆出**对应的**任务，而不是套模板？
2. 任意一个任务，能否说清它**为什么被拆出来**、花了多久、产出了什么？
3. 运行到一半，能否**回退到上一道**并重跑？
4. 生成的软件，能否**在本地一条命令跑起来**并点得动？
5. 全过程的花费，能否按任务归因，而不是只有一个总数？
