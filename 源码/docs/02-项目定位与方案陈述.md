# 方案陈述（修订版）

> 主题锚定：**面向软件开发全过程的 AI 原生 Web 应用**
> 一句话定位：**不做"什么都能生成"，做"能自己把代码跑起来、把报错修掉、并告诉你每一分钱花在哪"的软件开发 Agent。**

---

## 一、主题：我们只做软件开发场景

这一条是新的，也是最重要的。它不是"顺便选了个方向"，而是整个方案的地基：

**我们不做通用 AI 助手，不做以文本生成、多模态创作为主的工具，我们只做一件事——把软件开发这个过程的 AI 问题解决掉。**

为什么必须是这个主题，四个理由：

**第一，软件开发的成果是客观可验证的。**
文本和图片生成得好不好，靠人主观判断；代码生成得好不好，**跑一下就知道**。这一条决定了三件事：我们能做"自主修复闭环"（因为有明确的成功/失败信号）、我们能给出硬数据（成功率、返工次数、成本、耗时）、评委能当场验证而不是听我们讲。**这是选软件工程场景真正的理由，不是因为它好讲。**

**第二，赛道的 AI 分全在这个场景里。**
赛题命题背景点名的五个技术坐标——AI Agent 元年、Multi-Agent 系统编排、MCP 协议标准化、AI Native、端云协同——**全部是软件工程场景的母语**。推荐选题方向里，第 1 项"AI Agent 智能助手（含自动化工作流 Agent）"和第 7 项"AI 代码开发辅助（代码审查 Agent、架构设计助手、自动化测试生成平台）"直接命中。而多模态只值 5%，且是别人的主场，我们不在这里正面竞争。

**第三，AI 是核心而不是附属，这话在软件场景里天然成立。**
赛题明确要求"AI 功能应是应用的核心而非附属功能"。一个软件开发的 Agent 工具，AI 不是被"加上去的功能"，它就是产品本身。

**第四，这个场景能让"创新"落在具体的技术问题上，而不是空喊概念。**
软件开发过程中和 AI 相关的问题是一长串真问题：长任务怎么不失控、上下文怎么分配、失败了怎么归因、多贵多便宜的模型怎么分工、多个 Agent 之间怎么传话才不炸上下文。**这些每一个都能做成有深度的技术点，而不是包装。**

> 关于多模态：我们不放弃它的 5%，但只做**"软件开发场景内的多模态"**——把报错截图、设计稿、白板草图喂进去变成任务图，把口述需求变成任务描述。不做通用的图像生成、视频创作、文案生成。**多模态在软件工程里是输入通道，不是产品主线。**

## 二、我的想法：做一个软件开发 Agent 工作流工具

它本身就是落地的软件，不需要别的东西来衬托——现在纯粹的 AI 工具本身就是软件，功能本身就是它的价值。

核心形态是：**用户给一句话或者一份资料，主 Agent 规划，子 Agent 并行执行，代码在云端沙箱里真跑起来，报错了自己读、自己归因、自己修，最后在浏览器里直接看到能运行的东西。**

它给用户交付的不是一段代码文本，而是**一个能运行的软件包**：网页内 iframe 直接预览、Monaco 看源码、ZIP 下载带走，全程不离开这个网页。

**最关键的技术主张，已经从"主 Agent 用 GPT、子 Agent 用 DeepSeek"，升级成"成本感知的动态模型路由"。**

区别在哪：写死"谁干什么"是配置，运行时判断"这一步该花多少钱"才是算法。具体是——引擎在派发每一个子任务之前，先判定这个任务的难度（要改几个文件、依赖有多深、是不是架构级决策、历史上同类任务的成功率是多少），然后动态从三级模型池里挑：

- **决策级**：顶级模型，只在架构决策、方案裁决、复杂归因时调用，量少但价值最高
- **执行级**：DeepSeek 这类模型，快、便宜、能力足够，承担绝大多数写码和改码
- **机械级**：更便宜的模型，做重命名、样板代码、格式化、生成提交信息这类不需要脑子的活

这个路由决策本身是可评估的，我们能给出一个指标叫**路由准确率**——预测的难度档位和实际发生的重试次数、失败率对不对得上。有了这个指标，"技术先进性"才是数据而不是话术。

## 三、痛点：不是"不用写提示词"，是"长任务不失控"

这里我把原来的说法改掉了，因为原来的说法有一个说不通的地方：用户最终还是得输入一句话需求，那"不用写提示词"这个卖点就是虚的。**真正站得住的痛点是另一个。**

现有的 AI 编程工具（Cursor、Claude Code 这一类）本质是"对话式"的，有两个要命的问题：

**一是用户是过程的奴隶。** 得陪着走，一轮一轮喂上下文，看着它写，写偏了赶紧喊停，重开一轮。

**二是它是黑盒。** 跑到一半不知道它在干什么、不知道已经花了多少钱、跑偏了没有后悔药。长任务（超过二十分钟、动十几个文件）一旦在第八步失败，前面的投入基本作废。

所以用户真正要的不是"少打字"，而是——**我交代完可以走开，回来的时候它给了我一个能跑的东西，而且我能看到它这一路上干了什么、花了多少钱、哪一步差点翻车。**

把它拆成四个可验证的能力，这四件事就是产品的全部：

1. **可观测**：跑到第三十分钟，用户知道它在干什么，每一步花了多少钱
2. **可干预**：任务图上的任意节点能暂停、能改指令、能从那个点往下重跑，而不是推倒重来
3. **可恢复**：崩了不从头开始
4. **可预算**：设定成本上限，超了自动降级模型，而不是继续烧

这一改，原本拼在一起的三件事全部归位到同一个问题下，不再是三件事拼盘：

- 云端沙箱 = 让"失控"**看得见**（能跑、能看、能回滚）
- 编排引擎 = 让"失控"**拉得住**（任意节点介入）
- 动态路由 = 让"失控"**有上限**（实时成本面板 + 自动降级）

## 四、用户：先收窄，再放宽

**第一场景是学生和独立开发者**——有想法、有需求，但缺工程能力或者缺时间。典型任务就是课程设计、毕设原型、内部小工具、数据看板这一类。评委是高校教师，这个场景他们共情最强，演示也最好设计。

**远景是所有需要把想法变成可运行软件的人。** 先窄后宽，这是唯一能同时讲清"社会价值"和"商业潜力"的写法。

"全世界所有使用 AI 开发的人"这句话可以留在远景里，但不能当定位用——在评委眼里那等于没有定位，而且演示视频没法让任何人在三十秒内共情。

## 五、技术架构（修掉了原来的三个坑）

**前端层**：React / Next.js + TypeScript，Monaco 编辑器，React Flow 任务图画布，SSE 流式日志。前端不做"日志查看器"，而是**引擎状态的可视化视图**——引擎的状态直接驱动前端渲染。

**编排层**：这里我改了名字，**不叫"自研工作流引擎"，叫"面向 AI Agent 的轻量任务图运行时"**，并且主动划清边界——只支持 DAG（不做任意图）、只支持单写者（文件级锁）、只做至少一次语义（幂等由工具层保证）。通用调度交给 LangGraph.js 或 Vercel AI SDK 承担，我们的精力放在 AI 特有的三件事上：**上下文预算分配、子 Agent 之间的信息传递协议、失败归因**。

**失败归因**是我认为最值得做深的创新点，单独说：失败其实分三类——**环境错**（依赖缺失、端口占用）、**代码错**（逻辑、语法）、**模型错**（理解偏差、指令漂移）。现在所有 AI 编程工具都是**无差别重试**，不管什么错都让模型再试一遍，这是巨大的 token 浪费。正确做法是分流：环境错不进模型、直接修环境；代码错定位到文件行号、用最小上下文修；模型错才升级模型档位或者改写任务描述。**这是成本优势的真正来源，而且是可量化的**——别人没做这件事。

**模型层**：三级模型池（决策级 / 执行级 / 机械级），Function Calling + MCP 工具集成。

**执行层**：Docker 沙箱。安全是硬要求，不是可选项——非 root、只读根文件系统、网络白名单、CPU/内存/时长硬限制、容器池预热（否则冷启动慢到演示尴尬）。预览端口不裸奔，走后端代理加 token。

**数据层**：这里也改了，**不上 MySQL + Redis**。一个月的作品赛，单机 Postgres 或者 SQLite 加内存队列就够。多一个组件就是多一个部署失败点。**在技术文档里解释"为什么我们不上分布式"，比"我们用了 MySQL + Redis"更能得分。**

**交付**：网页内 iframe 预览 / Monaco 源码浏览 / ZIP 下载（含 README 和启动脚本）/ 可选的一键部署与 Git 导出。

## 六、为什么这个方案在评分表上强

- **AI 技术深度 35%**：Agent 与工作流编排是赛题点名的技术坐标；软件工程场景让我们能给出成功率、返工次数、成本、耗时四组客观数据，而不是自说自话
- **技术方案创新 8%**：动态成本路由 + 失败归因分类器，两个都是可以画出对比曲线的
- **交互模式创新 7%**：任务图上的节点级干预（暂停 / 改指令 / 从该点重跑）——把"和 AI 协作"从对话流变成可操作的任务图
- **实用性 10%**：问题定义清楚（长任务失控），面向真实场景（学生的课程设计和毕设）
- **AI 交互体验 3%**：流式输出、AI 思考状态可视化、错误边界

## 七、必须主动承认的三件事（写进文档反而加分）

1. **成本优势目前是待验证的假设，不是既定事实。** 真实成本 = 单价 × token × 重试系数，便宜模型重试三次优势就没了。我们正在做同任务对比实验，如果数据不支持，模型路由的卖点会立刻改。
2. **我们不做通用图灵完备的工作流引擎**，边界就是 DAG / 单写者 / 至少一次，超出范围的我们不承诺。
3. **当前能力边界是"可运行原型"级别**，不是生产级系统。大型项目需要多轮迭代。

## 八、选择理由（重写版）

**赛题符合性**：赛题以 Agent 为主，命题背景点名 Multi-Agent 系统编排与 MCP 标准化；推荐选题方向第 1 项和第 7 项直接命中；评分最重的"AI 技术深度"占比 35%，而我们的全部工作量都在这 35% 里面。

**技术先进性**：多 Agent 编排不是没人做，但"**成本感知的动态路由 + 失败归因分流**"这两件事在同类工具里没有人做。而且我们不做概念先进性，做的是**可测量**的先进性——路由准确率、失败归因准确率、同任务成本对比，每一项都能出数据。

**痛点针对性**：用户群明确（学生与独立开发者），痛点明确（长任务不失控），而且这个痛点现在没有工具解决——Cursor 和 Claude Code 让你陪着走、且成本黑盒；Dify 和 n8n 能画工作流但不执行代码、不交付软件；Devin 和 OpenHands 面向工程师、以 CLI 为主。**我们的空位是：Web 形态 + 多模型成本路由 + 可视化编排干预 + 浏览器内预览交付。** 这个空位很窄，但窄才好讲清楚。

**成本优势**：主 Agent 用顶级模型做规划判断，子 Agent 用 DeepSeek 这类模型做执行，理论上能把效果维持在两者之间、成本降一个量级。**但这一条我们标记为待验证**，理由见第七节。

## 九、演示设计（5–8 分钟视频的三段式）

1. **前 30 秒**：一句话需求进去，看着任务图在画布上长出来，每个节点开始亮起来
2. **中间 3 分钟（必杀技）**：注入一个报错 → 看引擎**归因**（这是环境问题还是代码问题）→ 看它定位文件 → 看它改 → 看它重跑跑通。**可视化"AI 怎么想"比可视化"AI 做完了"值钱得多**
3. **最后 1 分钟**：同一个任务跑两遍，一遍纯顶级模型、一遍我们的动态路由，**成本面板实时滚动对比**

另外，**故意演一次失败**——给一个会失败的任务（比如依赖缺失的密钥），展示人工确认点如何接管。**展示失败处理比展示成功更显工程成熟度。**

## 十、接下来可以深挖的创新点候选池

用户说之后要专注软件开发过程中和 AI 相关的问题，这里列十个可以直接做成技术深度的方向，按性价比排序：

1. **失败归因分类器**（环境错 / 代码错 / 模型错）—— 省 token 的真正来源，可量化
2. **动态成本路由 + 路由准确率指标** —— 把配置变成算法
3. **DAG 节点级干预与断点续跑** —— 长任务不失控的核心
4. **上下文预算分配** —— 哪个子 Agent 该看到多少代码，看多了烧钱、看少了写错
5. **子 Agent 间信息传递协议** —— 避免多 Agent 协作时上下文爆炸
6. **仓库级调用图检索** —— 不是通用文档 RAG，是"改这个函数会影响谁"的代码依赖检索
7. **生成式 UI** —— 根据任务类型自动生成适配的驾驶舱视图
8. **MCP 工具层标准化** —— 文件、执行、预览、版本控制全部封装成 MCP Server
9. **危险操作的人工确认点与沙箱策略** —— AI 安全与可控性那一项
10. **代码变更可解释性** —— 每个改动对应哪条需求、哪个报错，让 diff 自带理由
