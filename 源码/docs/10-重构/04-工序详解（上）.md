# 四、工序详解（上）：需求分析 / 架构设计

> 每道工序统一按同一模板写：输入 → 思考 → 提示词 → 输出契约 → 校验 → 失败处理 → 事件序列 → 界面动作 → 验收。

---

# 第 1 道：需求分析（plan）

## 1. 输入
```json
{ "prompt": "做一个习惯打卡，能看连续天数", "user": { "id": 5 } }
```

## 2. 这一步要产出什么
一份 `AppSpec`：目标、受众、场景、验收标准、范围外、待确认问题。

## 3. 两个任务（不写死，由规划器给，但默认形态如下）

| 任务 | 做什么 | 产出 |
|---|---|---|
| `澄清需求边界` | 找出模糊点、列出范围外 | `questions[]`、`out_of_scope[]` |
| `写验收标准` | 把需求转成可测的条目 | `acceptance[]`（3–6 条） |

## 4. 提示词（system）

```
你是软件需求分析师。只做一件事：把用户的一句话变成可执行的规格。

规则：
1. 不要写代码，不要设计架构。
2. 验收标准必须可机器验证（能写成一条 HTTP 请求或一次页面操作）。
3. 每条验收标准不超过 30 字。
4. 有歧义就问，问题数量不设上限；每个问题必须给出默认答案；能合理假设的写进 assumptions。
5. 输出必须是 JSON，字段见 schema，不要加解释文字。
```

## 5. 输出 schema（Pydantic `AppSpec`）

```json
{
  "goal": "记录每天的习惯完成情况，并展示连续天数",
  "audience": "想养成习惯的个人",
  "scenarios": ["每天打卡", "看连续天数", "看历史"],
  "acceptance": [
    {"id": "a1", "text": "能创建一个习惯"},
    {"id": "a2", "text": "每天能打卡一次，重复打卡不重复计数"},
    {"id": "a3", "text": "连续天数按自然日计算"},
    {"id": "a4", "text": "刷新页面后数据还在"}
  ],
  "out_of_scope": ["多人协作", "提醒推送"],
  "assumptions": ["时区按本地日期"],
  "questions": []
}
```

## 6. 校验（checker）

| 检查 | 不通过 |
|---|---|
| 必填字段非空 | 重试 1 次 |
| `acceptance` ≥ 3 条 | 重试 1 次（提示“再补两条”） |
| 每条 ≤ 30 字 | 截断并标注 |
| 每个问题必须有 `default` | 补一个默认值，不能出现“必答且无默认”的题 |

## 7. 门禁（人工确认）

触发条件（任一）：
- `questions` 非空
- `assumptions` 非空且影响数据模型

流程：
1. 发 `phase(awaiting)` + `gate` 事件（含问题与默认选项）
2. `runs.status = paused`
3. 前端弹窗；用户回答或点“按你的理解继续”
4. `POST /runs/{id}/answers` → 写 `gate.answered` 事件 → 恢复 `running`

超时：5 分钟无回答 → 自动按默认继续，并在事件里标注 `auto: true`。

## 8. 事件序列

```
phase(spec, "需求分析")
task(created, t1 澄清需求边界)
task(created, t2 写验收标准)
task(started t1) → reasoning("先确认…") → task(done t1)
task(started t2) → spec(...) → task(done t2)
[可选] phase(awaiting) + gate(...)
cost(...) usage(...)
```

## 9. 界面动作

- 第 1 张卡片进入“进行中”，副标“正在理解需求”
- 思考过程以 `reasoning` 事件弱化展示（已有区域）
- 门禁弹窗（新增）：问题 + 选项 + “按你的理解继续”
- 完成后副标变成“N 条验收标准”（N 来自 `spec.acceptance.length`）

## 10. 验收
- [ ] 输入习惯打卡 → 验收标准出现“连续天数”
- [ ] 输入投票 → 验收标准出现“一人一票”
- [ ] 两条需求产生的 spec 不同

# 第 2 道：架构设计（design）

## 1. 输入

```json
{ "spec": { ... }, "constraints": { "stack": "python+sqlite+html" } }
```

## 2. 产出两份设计

1. `ArchSpec`：模块、职责、依赖、文件清单
2. `UiSpec`：页面、路由、设计令牌（可合并到 arch 的 `ui` 字段，对外仍是一道工序）

## 3. 任务

| 任务 | 产出 |
|---|---|
| `划模块边界` | modules[]（2–4 个） |
| `定数据流与页面` | dependencies[]、pages[]、files[] |

## 4. 提示词（system）

```
你是软件架构师。基于规格设计一个最小可运行的全栈应用。

约束：
1. 技术栈固定：Python + SQLite + 原生 HTML/CSS/JS，不引第三方框架。
2. 模块 2–4 个，每个模块必须对应至少一个验收标准。
3. 必须给出文件清单，路径相对工作区，例如 db/schema.sql、api/main.py、web/index.html。
4. 依赖只能是单向的，不允许环。
5. 输出 JSON。
```

## 5. 输出 schema

```json
{
  "modules": [
    {"id": "db", "name": "数据库", "responsibility": "存习惯与打卡记录", "files": ["db/schema.sql"], "covers": ["a2","a3"]},
    {"id": "api", "name": "后端接口", "responsibility": "打卡与查询", "files": ["api/main.py"], "covers": ["a1","a2"]},
    {"id": "web", "name": "前端页面", "responsibility": "展示与操作", "files": ["web/index.html"], "covers": ["a4"]}
  ],
  "dependencies": [{"from": "web", "to": "api"}, {"from": "api", "to": "db"}],
  "pages": [{"route": "/", "name": "首页", "modules": ["web"]}],
  "run": {"entry": "api/main.py", "port": 8000}
}
```

## 6. 校验

| 检查 | 说明 |
|---|---|
| 覆盖 | 每条 `acceptance` 至少被一个模块的 `covers` 引用 |
| 无环 | 依赖图拓扑排序 |
| 文件唯一 | 同一文件不被两个模块声明 |
| 入口 | `run.entry` 必须在 files 里 |

不通过：重规划 1 次；仍不通过则降级为默认三模块结构，并写 `error` 标注。

## 7. 事件序列

```
phase(arch, "架构设计")
task(created ×2)
task(started/done 划模块边界) → arch(...) 
task(started/done 定数据流)  → ui(...)（可选）
cost / usage
```

## 8. 界面动作

- 第 2 张卡片进入进行中
- **模块节点从架构卡下方长出**（现有能力，只需事件驱动）
- 每个模块节点显示：名称 + 文件（现有样式）
- 依赖若为环，`check` 事件带失败项 → 卡片标红

## 9. 验收
- [ ] 模块节点数量 = `arch.modules.length`
- [ ] 模块覆盖检查失败时，界面能看到具体哪条未覆盖
