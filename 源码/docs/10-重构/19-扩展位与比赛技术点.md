> 这份文档解决一件事：**核心链路先跑通，但给比赛要求的技术点留好插槽**。

## 1. 用户提问（门禁）——不是只在第一道

### 1.1 现在文档里的设计
- 触发点：需求分析发现歧义（`spec.questions` 非空）
- 形式：`phase(awaiting)` + `gate` 事件
- 交互：弹窗 → 回答 / “按你的理解继续” → `POST /answers`
- 超时：5 分钟自动按默认继续

### 1.2 需要补的能力：**任意阶段都能提问**

AI 不只会在需求阶段“拿不准”。设计阶段可能不知道用几张表，开发阶段可能不知道某个交互细节。

所以把“提问”做成一个**工具**，而不是第一阶段专用：

```python
# app/tools/ask.py
class AskUser:
    """任何阶段都可以调用。调用即暂停整条运行，等用户回答。"""

    def ask(self, *, run_id, stage, questions: list[Question], default: str) -> list[Answer]:
        emit_phase(run_id, "awaiting", label="需要你确认")
        emit_gate(run_id, stage=stage, questions=questions)
        set_status(run_id, "paused")
        answers = wait_for_answers(run_id, timeout=300)   # 阻塞
        emit_gate_answered(run_id, answers)
        set_status(run_id, "running")
        return answers or [default]
```

规则（**当前不设数量限制**）：
- 问题数量不限、轮次不限、阶段不限
- 每个问题必须有默认答案，没有“必答”题
- 允许自由文本作答（选项覆盖不了的情况）
- 一次批量列出，用户一轮答完；不同轮次分别弹窗，不合并
- 答过的问题不再重复问，答案累积进上下文
- 始终提供“全部按默认继续”的出口
- 限额是**以后**的事：`ASK_MAX_QUESTIONS=0`（0 = 不限）、`ASK_MAX_ROUNDS=0`，默认都是不限

### 1.3 事件契约（复用，不新增 kind）

```json
{"kind":"phase","phase":"awaiting","label":"需要你确认"}
{"kind":"gate","stage":"design","questions":[{"id":"q1","text":"…","options":["A","B"]}]}
{"kind":"gate.answered","answers":[{"id":"q1","value":"A"}],"auto":false}
```

> `gate` 与 `gate.answered` 作为 `kind` 的两个新值，前端遇到未知 kind 必须忽略——现有实现已满足。

### 1.4 前端
一个弹窗组件，挂在 `workbench/` 下；样式复用现有 modal。任何阶段收到 `gate` 都弹同一个。

### 1.5 验收
- [ ] 第 2 道触发提问 → 流程暂停 → 回答后继续
- [ ] 不回答，5 分钟后自动继续，事件标 `auto: true`

## 2. skill（技能层）

### 2.1 为什么要独立成层
现在每道工序的能力写死在提示词里。skill 的作用是把“一类任务的标准作业流程”抽出来：角色、步骤、产出契约、自检、示例。后续加一个新技能，不改编排器。

### 2.2 接口

```python
# app/skills/base.py
class Skill(Protocol):
    name: str                 # "spec.writing"
    stage: str                # plan / design / build / assemble / test / deliver
    version: str              # "v1"
    def system_prompt(self, ctx) -> str: ...
    def steps(self, ctx) -> list[str]: ...
    def output_schema(self) -> type[BaseModel]: ...
    def self_check(self, output) -> list[str]: ...   # 返回问题列表
```

### 2.3 注册与选择

```python
# app/skills/registry.py
REGISTRY = {
    "plan":     ["spec.writing", "spec.acceptance"],
    "design":   ["arch.modules", "ui.pages"],
    "build":    ["code.file"],
    "assemble": ["assemble.entry"],
    "test":     ["test.cases", "test.run"],
    "deliver":  ["deliver.package"],
}

def for_stage(stage: str) -> list[Skill]:
    return [REGISTRY_BY_NAME[n] for n in REGISTRY[stage] if enabled(n)]
```

### 2.4 现在怎么落地（不空转）
- 第一版把现有提示词包成 `Skill` 对象（`skills/spec_writing.py` 等），**行为不变**
- 编排器改为 `skill.system_prompt()`，不再直接读 prompt 字符串
- 新增技能只是加一个文件 + 注册
- 事件里带 `skill: "spec.writing@v1"`，便于追踪

### 2.5 后续扩展
- 从“提示词形态”升级为“步骤机形态”：每步一个模型调用，产出中间结果
- 支持从文件加载（`skills/*.yaml`），不改代码

## 3. RAG（检索增强）

### 3.1 现状
数据库有 `rag_documents / rag_chunks` 两张表，代码里是空壳；事件里预留了 `retrieval`。

### 3.2 接口

```python
# app/ai/rag/retriever.py
class Retriever(Protocol):
    def search(self, query: str, *, stage: str, top_k: int = 3) -> list[Hit]: ...

@dataclass
class Hit:
    source: str      # "playbook/验收标准怎么写.md#第2节"
    snippet: str
    score: float
```

### 3.3 开关与降级
```ini
RAG_ENABLED=false        # 默认关；关时 retriever 返回空，不报错
RAG_CORPUS_DIR=content/playbook
```

### 3.4 上线步骤（后续）
1. 准备 6 篇手册（每道工序一篇）
2. 切块 + 向量化（`numpy` 已在依赖里，进程内暴力检索即可）
3. 开 `RAG_ENABLED=true`
4. 每道工序开始时检索一次，命中发 `retrieval` 事件
5. 前端在阶段卡片显示“参考了 2 条依据”

### 3.5 验收

- [ ] 打开 RAG，事件里出现 `retrieval` 且有 2–3 条命中

## 4. MCP（工具集成）

### 4.1 接口抽象

```python
# app/tools/provider.py
class ToolProvider(Protocol):
    def list_tools(self) -> list[ToolSpec]: ...
    def call(self, name: str, args: dict) -> ToolResult: ...

class LocalProvider:      # 文件/命令/预览/HTTP，全部本地实现
class McpProvider:        # 后续接 MCP server
```

编排器只依赖 `ToolProvider`：

```python
tools = provider_for(settings.tool_provider)   # local | mcp
```

### 4.2 降级
- MCP 连不上 → 自动 `LocalProvider`，事件里标 `mcp: false`
- 工具描述统一（名字、参数、返回），保证两边可替换

### 4.3 后续步骤
1. 把文件/命令/预览做成标准工具描述（JSON Schema）
2. 起一个本地 MCP server（stdio）
3. `TOOL_PROVIDER=mcp` 切换
4. 失败自动回退

## 5. React（前端边界）

### 5.1 现状与决定
现有前端是原生 JS，已经实现树、流式、回放、速度。
**第三阶段不迁 React**——迁移不影响产品可信度，只增加风险。

### 5.2 给 React 留的边界
前后端的契约已经是框架无关的：

```
REST /api/v1/*
SSE  /api/v1/runs/{id}/stream
事件 kind + seq + at
```

任何前端框架都能消费。React 版本可以：

- **方案甲**：新做一个 `web-react/` 只读页面，消费同一套接口，用于展示“同一后端、不同前端”
- **方案乙**：只把“工作流树”做成一个 React 组件，嵌进现有页面（iframe 或挂载点）
- **不选**：整体重写现有页面（收益低、风险高）

### 5.3 如果比赛必须体现 React
建议按方案乙：新写一个 `canvas-react/` 小组件，读 `events` 渲染树，挂到现有页面的一个演示路由（`/react-demo/`）。这样：
- 不碰主流程
- 技术点能讲
- 出问题不影响主演示

## 8. 对比赛评分的作用

| 技术点 | 现在 | 加扩展位后 | 需要真做 |
|---|---|---|---|
| 多 Agent 编排 | ✅ 真实 | — | 核心链路 |
| 人工干预/门禁 | ✅ 真实 | 任意阶段可提问 | ask_user |
| skill | ❌ | 有层、有注册、有版本 | 抽出 6 个技能 |
| RAG | ❌ 仅表 | 有接口、有事件、有语料 | 语料 + 检索 |
| MCP | ❌ | 有 Provider 抽象 | 一个 stdio server |
| React | ❌ | 有边界说明与可选组件 | 可选 |

> 结论：**核心链路先做真；扩展位先留好。** 比赛前至少把 skill 与 ask_user 做真，RAG 视语料准备情况，MCP 与 React 作为“已设计、可演示”的加分项。
