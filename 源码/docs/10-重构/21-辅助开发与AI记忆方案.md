# 二十一、辅助开发与 AI 记忆方案

> 版本 v1.0 · 2026-11-11
> 状态：**开发方案**，未动代码。
> 定位：在现有产品上加一个入口，不是做第二个产品。

---

## 0. 一句话

**工作流是 AI 替你做完整开发；辅助开发是你自己一步一步做，AI 在旁边按六道工序帮你。**
记忆只服务“辅助开发”，不进入“工作流”。

---

## 1. 边界：为什么个性化只给辅助

| | 工作流 | 辅助开发 |
|---|---|---|
| 谁写代码 | AI | 用户 |
| 输入 | 一句话 | 用户的项目与代码 |
| 记忆 | **不注入** | 注入 |
| 目标 | 可复现、可验收 | 顺手、越用越懂你 |
| 失败代价 | 产物不对 | 习惯被误导 |

工作流不注入个性的三条理由，答辩时可以直接讲：

1. **可复现**：同一个需求，不同用户、不同时间，结果应当一致，才谈得上验收。
2. **可比对**：演示时要能对比“两次生成”，个性化会让差异无法归因。
3. **正确性优先**：个性会影响默认值和表达，生成链路不应被偏好带偏。

一句话话术：

> 工作流追求正确与可复现，所以用模型的纯粹能力；
> 辅助开发面向个人习惯，所以记忆只在这一侧生效。

## 3. 辅助开发页：信息架构

```
┌──────────┬───────────────────────────────┬──────────────────┐
│ 六阶段    │ 当前阶段工作区                 │ AI 助手           │
│ 01 需求 ●│ 需求卡 / 验收清单              │ 还缺什么           │
│ 02 设计  │ 模块 / 文件 / 接口             │ 检查结果           │
│ 03 开发  │ 代码编辑器（用户写）            │ 问题单             │
│ 04 集成  │ 接线清单                      │ 下一步建议         │
│ 05 测试  │ 用例 + 运行结果                │ [让 AI 补这一步]   │
│ 06 交付  │ 上线前检查清单                 │                  │
├──────────┴───────────────────────────────┴──────────────────┤
│ 状态条：事件 / 检查 / 成本                                     │
└─────────────────────────────────────────────────────────────┘
```

原则：

- **中间是用户的主战场**，AI 在右侧，不抢键盘
- 每个阶段可停、可回退、可跳过，但跳过会留下“未完成”标记
- 所有产出可导出，项目归用户所有

## 4. 六阶段逐阶段

### 01 需求

| 项 | 内容 |
|---|---|
| 用户做 | 写一句话；补验收标准；确认范围外 |
| AI 做 | 追问歧义（不限数量，每题有默认）；把标准改写为可测 |
| 产出 | `需求卡`（目标/受众/场景）+ `验收清单` |
| 门禁 | 验收标准 < 3 条时提示补充 |

### 02 设计

| 项 | 内容 |
|---|---|
| 用户做 | 划模块、定文件、写接口 |
| AI 做 | 覆盖检查（每条验收是否有模块负责）、循环依赖检查、命名建议 |
| 产出 | `模块清单` + `文件清单` + `依赖图` |

### 03 开发

| 项 | 内容 |
|---|---|
| 用户做 | **自己写代码**，可多文件 |
| AI 做 | 解释报错、指出坏味道、检查是否偏离验收、给修改建议 |
| 产出 | 代码文件 + `问题单` |
| 约束 | AI 不自动改文件；“应用建议”需用户点确认（二期） |

### 04 集成

| 项 | 内容 |
|---|---|
| 用户做 | 写入口、挂静态资源、配端口 |
| AI 做 | 检查入口/依赖/静态挂载；给出启动命令 |
| 产出 | 可启动骨架 |

### 05 测试

| 项 | 内容 |
|---|---|
| 用户做 | 写或用 AI 生成的用例；贴运行结果 |
| AI 做 | 从验收标准生成用例；解释失败原因；判断覆盖是否足够 |
| 产出 | 用例表 + 测试记录 |

### 06 交付

| 项 | 内容 |
|---|---|
| 用户做 | 过检查清单；确认风险 |
| AI 做 | 汇总未完成项、生成交付说明与风险清单 |
| 产出 | 交付报告 |

### 4.7 三种 AI 协作状态

辅助项目顶部放一个三态选择，随项目保存：

| 状态 | 名字 | AI 能做什么 | 确认策略 | 适合 |
|---|---|---|---|---|
| ① | 纯对话 | 解释、答疑、给思路 | 不写文件，无需确认 | 学习、问概念 |
| ② | 协作（建议） | 读文件、跑检查、给 diff | **每次写入都要用户点“应用”** | 日常开发，默认 |
| ③ | 自动（Agent） | 读、写、改、再检查 | **会话内全部免确认**，直接写 | 批量改、赶时间 |

三态的共同底线：

- 都只能操作当前项目的文件
- 每次写入前自动快照，可一键撤销
- 所有动作进操作日志（谁、何时、改了哪个文件）
- 自动模式可随时点“停止”，停止后不再继续写

**三态的唯一区别就是“确认策略”**：

- ② = 每次确认
- ③ = 免确认，只靠护栏（快照、撤销、停止、日志、范围限制）

切换说明：

- 状态随项目保存，切到 ③ 时给一次提示“本会话内 AI 将直接修改文件”
- 从 ③ 切回 ② 不会回滚已有改动；需要回滚用手动撤销
- 切到 ① 后 AI 不再调用写文件工具

## 5. 代码能力：从文本框到真实解析

### 5.1 编辑器演进（按顺序，一步一步）

| 阶段 | 形态 | 说明 |
|---|---|---|
| E1 | 高亮文本框 | textarea + 底层着色，零依赖，先跑通“能写、能存、能查” |
| E2 | CodeMirror 6 | 引入真实编辑器内核：缩进、括号、搜索、折叠、多光标 |
| E3 | 语言模式扩展 | Python / Java / JavaScript / HTML / CSS / SQL 六种模式全打；不做 LSP |

演进叙事（答辩时用这一句）：

> 一开始我们用普通文本框保证可用；后来**为了让代码辅助开发更加贴近真实编译**，
> 我们把普通文本框进化为采用**实际的语言解析库（编译器前端）组件**：
> 编辑区接入开源编辑器组件 **CodeMirror 6**，检查从“正则匹配”升级为
> “按语言解析成语法树”。我们没有重写编辑器内核，而是**复用成熟组件**，
> 把精力放在六阶段流程、检查规则与 AI 协作上。

注意措辞：我们引入的是**语言解析库（parser / 编译器前端）**，不是执行编译器；
不编译、不运行用户代码，只做语法与结构分析。

### 5.1.1 CodeMirror 是什么（选型说明）

CodeMirror 不是编译器，也不是后端，它是**跑在浏览器里的代码编辑器组件**。

| | 普通 textarea | CodeMirror 6 | Monaco（VS Code 内核） |
|---|---|---|---|
| 本质 | 浏览器原生输入框 | 模块化编辑器库 | 完整 IDE 内核 |
| 语法高亮 | 需要自己叠一层着色 | 内置，按语言增量解析 | 内置，最完整 |
| 缩进/括号 | 没有 | 有 | 有 |
| 搜索/折叠/多光标 | 没有 | 有 | 有 |
| 体积 | 0 | 约 200–400 KB（按语言加载） | 2 MB 以上，还要 worker |
| 接入成本 | 最低 | 中：需要 vendor 或构建 | 高 |
| 离线 | 天生可用 | vendor 后可用 | 较重 |

关键点：

- CodeMirror 的解析（Lezer）只用于**编辑体验**：高亮、括号、折叠
- 它不执行代码，也不替代后端的 `ast` / `javalang`
- 对我们来说，升级 CodeMirror 是“编辑体验”升级，不是“分析能力”升级

### 5.1.3 组件使用说明（比赛口径）

**算组件。** CodeMirror 是成熟的开源编辑器组件，我们以“引入 + 集成”的方式使用它。

| 组件 / 库 | 作用 | 许可证 | 我们怎么用 |
|---|---|---|---|
| CodeMirror 6 | 编辑器内核（高亮、缩进、搜索、折叠） | MIT | vendor 打包后作为前端组件引入 |
| `javalang` | Java 语法解析 | MIT | 后端调用，产出 AST |
| `esprima` | JavaScript 语法解析 | BSD-2 | 后端调用，产出 AST |
| `tinycss2` | CSS 解析 | BSD-3 | 后端调用 |
| `sqlparse` | SQL 解析 | BSD-3 | 后端调用 |

我们自己写的部分：

- 六阶段工作流与阶段门禁
- 多语言规则表与“问题归因到阶段”
- AI 协作三态、记忆机制
- 页面与交互

口径建议（答辩时）：

> 编辑器我们没有重复造轮子，而是引入开源组件 CodeMirror；
> 真正的差异在六阶段陪跑、跨语言检查与 AI 协作，而不在编辑器本身。

不要说“我们自研了编辑器”，容易被追问；说“集成组件 + 自研流程”更稳。

### 5.1.2 引入方式：开发期构建，运行期单文件

CodeMirror 6 是 ESM 模块包，直接手写一个“单文件”不现实。三种做法：

| 做法 | 运行期 | 开发期 | 评价 |
|---|---|---|---|
| A. 纯 CDN | 依赖外网 | 无 | ✗ 离线不可用，比赛风险高 |
| B. 开发期 esbuild 打包，产物入库 | 单文件、零构建 | 需要 Node，重跑一条命令 | ✓ 推荐 |
| C. 直接引源码 + 浏览器 importmap | 多文件、需现代浏览器 | 无构建 | 可行但文件多、升级麻烦 |

结论：**B。开发期用 esbuild 打成一个 vendor 文件并提交，运行期不装 Node、不联网。**

```
源码：web-v2/vendor-src/editor.js
构建：esbuild → web-v2/vendor/codemirror.bundle.js（入库）
页面：<script src="../vendor/codemirror.bundle.js"></script>
```

好处：

- 部署与现在一样：FastAPI 静态托管，离线可用
- 体积可控：六种语言模式按需打包，估计 300–500 KB
- 升级明确：改依赖后重跑一次构建

代价：仓库多一个构建脚本和一份产物；不引入前端框架，也不改现有页面加载方式。

### 5.2 语言范围：都做，但深度分级

不限定只有 Python。辅助开发面向用户已有代码，语言必须跟用户走。

| 语言 | 解析方式 | 能做的检查 | 深度 |
|---|---|---|---|
| Python | 内置 `ast` | 语法、导入、未使用变量、复杂度、坏味道 | 深 |
| Java | `javalang`（纯 Python 解析器） | 语法、类/方法结构、导入、命名、空 catch、TODO | 中 |
| JavaScript | `esprima`（Python 版） | 语法、函数结构、未使用变量、`var`、`eval` | 中 |
| HTML | 标准库 `html.parser` | 标签闭合、资源引用、内联脚本、缺 alt | 基础 |
| CSS | `tinycss2` | 语法、重复选择器、未使用类（需与 HTML 交叉） | 基础 |
| SQL | `sqlparse` | 语法、缺 WHERE 的 UPDATE/DELETE、SELECT * | 基础 |

深度分级的意思：

- **深**：能给出准确行号与结构，规则确定、误报低
- **中**：语法与结构可靠，语义（类型、继承、框架约定）不承诺
- **基础**：只查模板级问题，解释交给模型

Java 说明：`javalang` 覆盖常见 Java 8–11 语法；Java 17 新语法（record、sealed、switch 表达式）
可能解析失败。失败时降级为“结构检查 + 模型解释”，并在界面标注“该文件仅做基础检查”。

### 5.3 多语言对流程的影响

| 环节 | 变化 |
|---|---|
| 文件识别 | 按后缀选解析器与规则集 |
| 阶段归因 | 每条问题仍归到六阶段之一，规则表按语言配置 |
| 测试用例 | Python/Java 可按函数生成；前端只生成页面级用例 |
| 展示 | 文件树显示语言徽标；检查结果标注解析器版本 |
| 降级 | 解析失败不报错，标“仅基础检查”，转模型解释 |

### 5.4 明确不做

- 不做类型解析、符号表、classpath
- 不接 Maven/Gradle、不跑构建
- 不执行用户代码、不启动 JVM
- 不做跨文件调用图（第一版）

### 5.5 依赖与体积

| 库 | 用途 | 备注 |
|---|---|---|
| `javalang` | Java 解析 | 纯 Python，无 JVM |
| `esprima` | JS 解析 | 纯 Python |
| `tinycss2` | CSS 解析 | 轻量 |
| `sqlparse` | SQL 解析 | 轻量 |

全部可离线安装；不引入需要 Node 的解析链。
编辑器库（CodeMirror）只在前端 vendor 一个构建产物，不引 CDN。

### 5.6 和工作流的关系

- 工作流当前生成栈仍是 Python + SQLite + 原生前端（已实测）
- 辅助开发的分析范围不受此限制，支持用户带来的 Java / JS / HTML / CSS / SQL
- 未来若扩展工作流的生成语言，是另一条线，不影响本方案

### 5.7 与 Docker 运行时：编辑、解析、执行三层

先把三层分开，后面接 Docker 才不会乱：

| 层 | 在哪跑 | 现在 | 将来 Docker |
|---|---|---|---|
| 编辑 | 浏览器 | textarea → CodeMirror | 不变 |
| 解析/静态检查 | 后端 Python | `ast` / `javalang` / `esprima` | 可不变 |
| 编译/运行/测试 | 隔离环境 | **不做** | 容器里做 |

Docker 带来的能力（后续阶段）：

- 真编译：`javac`、`node --check`、`pytest`
- 真运行：按项目类型起容器，端口映射
- 语言工具链：Maven/Gradle、npm、JDK 版本隔离
- 安全：只挂载项目目录、禁网、限 CPU/内存/超时

不把 Docker 放进第一版的原因：

- 本机现在没有 Docker，先用进程/解析保证功能
- 演示阶段容器启动慢，容易冷场

接口上先留位：

```
Runner（协议）
  ├─ LocalRunner     现在：只做解析，不执行
  └─ DockerRunner    将来：挂载项目 → 跑命令 → 收输出
```

这样“编辑器 → 解析器 → 容器”是一条清晰的演进线，答辩时也讲得清：
**先能看懂代码，再能安全地跑代码。**

## 6. AI 记忆（个性化）

### 6.1 生命周期

```
一次辅助开发阶段结束
  → AI 自省：有什么值得长期记住？（0~3 条）
  → 去重、合并
  → 写库：内容 / 为什么记 / 来源 / 置信度
  → 下次进入辅助开发时，按相关度取 ≤5 条注入
```

AI 自主决定记什么，不强制分类（偏好、决策、风格都行）。

### 6.2 约束（只有三条）

1. 不记敏感信息：密钥、密码、完整代码只留摘要
2. 单次推断置信度低，重复出现才升级
3. 记忆只影响默认值与表达，不影响验收标准与事实

### 6.3 条数与作用域

- 每天最多 **3 条**（配置项 `MEMORY_DAILY_LIMIT`，默认 3，可改）
- 默认**全局**生效（跨项目）
- 只在辅助开发注入；工作流不读记忆

### 6.4 注入

```
system_prompt = 阶段提示词
              + "关于这位用户（来自历史记忆，仅作默认值参考）"
              + 最多 5 条记忆
              + "不要因偏好放宽验收标准"
```

界面上显示：`参考了 2 条记忆`，点开可看具体条目。

### 6.5 记忆页（头像菜单进入）

```
AI 记忆                                    [导出] [清空]
─────────────────────────────────────────────────────
11-11  3 条   今天它记住的
              ┌────────────────────────────────────┐
              │ 你偏好先看结论，再看原因             │
              │ 因为：连续 3 次要求“直接说重点”      │
              │ 来源：11-11 需求分析 · 门禁回答      │
              │ 置信度：多次验证     [置顶] [删除]   │
              └────────────────────────────────────┘
11-10  2 条   ...
─────────────────────────────────────────────────────
今天新增 3 条 · 本周引用 12 次 · 最近一次 10 分钟前
```

功能：按天时间线、来源可点、置顶、删除、导出、清空、显示被引用次数。

---

### 6.6 记忆数据必须可见

用户要能随时知道“AI 记了多少、今天记了几条、有没有超限”。

三个位置固定展示：

| 位置 | 展示 |
|---|---|
| 记忆页顶部 | 总条数 / 今日新增 / 本周引用 / 最近一次 |
| 辅助项目顶栏 | `记忆 12 条 · 今日 3/3 · 参考 2 条` |
| 设置页 | 每日上限（默认 3，可改）、清空入口、导出 |

记忆页顶部固定一行：

```
共 27 条 · 今日 3/3 · 本周被引用 12 次 · 最近一次 10 分钟前
```

超限时明确提示：`今日已达上限 3 条，明天继续积累`，不静默丢弃。


## 12. 风险

| 风险 | 应对 |
|---|---|
| 两个入口都做浅 | 先做 P1–P3，P4 视时间 |
| 记忆编造 | 无来源不入库；置信度分级 |
| 提示词膨胀 | 注入 ≤5 条、≤300 字 |
| 编辑器体验差 | 先用高亮文本框，确认后再引库 |
| 评委误解为通用 IDE | 页面文案强调“六阶段陪跑”，不强调编辑器 |
| Java 新语法解析失败 | 降级为基础检查，界面标注，不阻塞 |
| JS 框架写法误报 | 只做语言级规则，不做框架约定检查 |
| CodeMirror 体积 | 只 vendor 核心 + 需要的语言模式 |

## 13. 已定决策

1. 导航用顶栏两个 tab（方案 A）
2. 记忆页放头像菜单，不做第三个 tab
3. 记忆默认全局
4. 记忆只作用于辅助开发；工作流保持纯模型能力
5. 每天最多 3 条，可配置
6. AI 自主决定记什么，只保留三条约束
7. 纯加功能，前后端能复用就复用
8. 编辑器按 E1 → E2 顺序演进，叙事为“文本框 → 真实编辑器内核”
9. 语言不设限：Python 深、Java/JS 中、HTML/CSS/SQL 基础
10. AI 既能建议也能动手：默认对话模式，可切 Agent 模式（改动以 diff 呈现、可撤销）
11. 工作流生成栈暂不变，辅助开发的分析范围独立
12. AI 协作三态：纯对话 / 协作建议 / 自动 Agent，随项目保存
13. 记忆条数与用量必须在记忆页、项目顶栏、设置页可见
14. Docker 作为后续运行时，先留 Runner 接口，第一版不接
15. CodeMirror 采用“开发期 esbuild 打包 + 产物入库”，运行期零构建
16. 自动模式为会话内全部免确认，只保留快照/撤销/停止/日志/范围护栏
17. 语言模式六种全打：Python / Java / JavaScript / HTML / CSS / SQL
18. 对外口径：CodeMirror 是引入的开源组件，自研的是六阶段流程与检查规则
