# 重构方案（从 0 开始）

> 版本 v1.0 · 2026-11-09
> 状态：**方案文档**，不是提交材料。
> 目标：把「演示发生器」换成真实的「需求 → 编排 → 六道工序 → 可运行产物」链路。
> 约束：视觉、文案、页面结构、事件协议、数据库表**基本不变**；只换内容生产与驱动方式。

---

## 0. 一句话结论（先看这个）

**推荐方式一：影子重建（后端编排另起一套，前端复用现有页面，用一个开关切换）。**

理由三条，详见 `11-两方案对比与实施路线.md`：

1. 现有演示随时可切回去当兜底，演示风险最低；
2. 新链路从第一行就是按本方案写的，不会继承“原型接缝”；
3. 前端不复制，避免两套 UI 漂移——只加一个 `?pipeline=real` 的开关。

| 能力 | 现在 | 目标 |

## 5. 关键设计取舍（先给结论，理由在对应章节）

| 取舍 | 结论 | 理由 |
|---|---|---|
| 编排形态 | 单进程内的“规划器 + 任务队列”，不引 Redis | 单机演示，DB 足够；少一个依赖少一个故障点 |
| 并发 | 模块级并发，默认 3 | 与文档一致，资源可控 |
| 状态真相 | 数据库（runs / run_events / tasks） | 前端只读，刷新可恢复 |
| 任务存储 | **不新增表**，任务状态由 `task` 事件重建 | 符合“12 张表不动” |
| 失败重试 | 自动 1 次，第二次升级人工 | 与现有失败回环一致，演示可控 |
| 前端 | 复用现有静态站，不迁 React | 迁移不影响产品可信度，只增加风险 |
| 运行时 | 本机进程 runner（D 盘工作区），Docker 作为可选后端 | 本机 Windows 无 Docker；接口按容器语义设计 |
| 离线兜底 | 录制回放（事件 + 产物快照） | 比赛现场无网也能演示 |
