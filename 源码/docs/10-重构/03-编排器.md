# 三、编排器（主控 Agent）

> 这是整个重构的核心。现有 `demo.py` 是一段“剧本”，重构后要变成“决策循环 + 任务队列”。

## 1. 职责边界

编排器**只做四件事**：

1. **规划**：把 spec 变成任务图（每道工序要有哪些任务）
2. **调度**：按依赖与并发上限派发任务
3. **收口**：检查产出、决定推进/回环/中止
4. **记账**：每次模型调用落成本、每次状态变化落事件

它**不做**：不直接写文件、不直接调模型、不直接起进程——这些是工具层的活。

```
orchestrator
├── planner      需求 → 任务图
├── scheduler    任务图 → 执行（并发/依赖/重试）
├── checker      产出 → 通过/回环/失败
└── recorder     每一步 → 事件 + 成本
```

## 2. 启动流程（POST /runs 之后）

```
1. 落 runs 行（status=running, stage=plan）
2. 写事件 phase(spec, "需求分析")
3. 后台线程 / 任务启动 orchestrator.run(run_id)
4. 立即返回 201 { id }
5. 前端订阅 SSE
```

**关键改动**：`runs/router.py` 里 `demo.start()` 改成：

```python
pipeline = os.getenv("PIPELINE", "real")   # real | demo
if pipeline == "demo":
    demo.start(run.id)
else:
    orchestrator.start(run.id)
```

这样旧的演示随时可切回。

## 3. 主循环（伪代码）

```python
def run(run_id):
    spec = None
    for stage in STAGES:            # plan → design → build → assemble → test → deliver
        emit(phase(stage))
        ctx = load_context(run_id)   # spec / arch / files / prior results
        plan = planner.plan(stage, ctx)   # 本道要做的任务列表
        for task in plan:
            emit(task_created(task))
        ok = scheduler.run(run_id, stage, plan, ctx)  # 并发执行，逐条事件
        if not ok:
            if stage == "test":
                fix_and_retry(run_id, ctx)   # 回环：回 build 修，再回 test
                continue
            fail(run_id, reason); return
        # 提问由各阶段自己触发（ask_user 工具），这里只负责"暂停/等待"这一段
        if pending_gate(run_id):
            emit(phase("awaiting"))
            wait_for_gate(run_id)        # 阻塞直到用户回答或超时
    emit(phase("done"))
    set_status(run_id, "done")
```

## 4. 规划器（planner）

### 4.1 输入
```json
{ "stage": "build", "prompt": "...", "spec": {...}, "arch": {...}, "files": ["db/schema.sql"] }
```

### 4.2 输出（必须是结构化 JSON）
```json
{
  "tasks": [
    { "title": "写打卡数据表", "kind": "code", "file": "db/schema.sql",
      "dependsOn": [], "acceptance": "包含 habit_id 与 day 唯一约束" },
    { "title": "写打卡接口", "kind": "code", "file": "api/main.py",
      "dependsOn": ["写打卡数据表"], "acceptance": "POST /api/checkin 幂等" }
  ]
}
```

### 4.3 规则
- 任务数：plan 2–4、design 2–3、build = 模块数、assemble 1、test = 验收标准条数、deliver 1
- 标题必须含需求里的名词（用于验收检查）
- `dependsOn` 只允许同阶段内，避免跨阶段等待
- 解析失败：重试 1 次，仍失败则降级为“每道工序 1 条任务”，并写 `error` 事件标注降级

## 5. 调度器（scheduler）

### 5.1 并发
- 默认并发 3（`BUILD_CONCURRENCY`）
- 按 `dependsOn` 拓扑排序；无依赖的先跑
- 同一文件不能两个任务同时写（文件锁）

### 5.2 任务执行封装

```python
for task in ready_tasks:
    emit(task(action="started"))
    try:
        result = run_task(task)          # 调模型 + 工具
        emit(task(action="done", ms=..., result=result))
    except TaskFailed as e:
        emit(task(action="failed", reason=e.reason))
        if task.attempts < 2:
            task.attempts += 1
            requeue(task)                # 自动重试一次
        else:
            record_failure(task); batch_ok = False
```

### 5.3 失败分类（决定重试策略）

| 类型 | 例子 | 策略 |
|---|---|---|
| 环境错 | 端口占用、缺依赖 | 不重试，直接报错（附修复建议） |
| 代码错 | 语法错误、接口 500 | 自动重试 1 次，带错误信息 |
| 模型错 | JSON 不合法、空输出 | 重试 1 次，降级提示词 |

## 6. 检查器（checker）

每道工序结束前跑：

| 工序 | 检查什么 | 不通过怎么办 |
|---|---|---|
| plan | spec 必填字段齐全、验收标准 ≥3 条 | 补问一次（门禁） |
| design | 模块覆盖所有验收标准、无循环依赖 | 重规划一次 |
| build | 每个模块文件存在、`py_compile` 通过 | 重试该模块 |
| assemble | 入口文件存在、静态资源可加载 | 重装配 |
| test | 用例全过 | 回环修复 |
| deliver | 进程能起、端口可访问 | 重试启动 |

## 7. 回环修复（唯一允许的倒退）

```
test 失败
  → emit(phase("building", "回环修复"))
  → 建一个 fix 任务（kind=fix，指明失败用例与文件）
  → 模型重写该文件（file.replace=true）
  → emit(phase("checking", "复测"))
  → 重跑失败用例
  → 通过则继续 deliver；仍失败则 run failed
```

限制：**最多回环 2 次**，超过则 `failed` 并写明“已尝试 2 次”。

## 8. 控制点（暂停/继续/取消/回退）

| 操作 | 实现 |
|---|---|
| 暂停 | `runs.status=paused`；调度器在每个任务前检查，暂停时不派新任务 |
| 继续 | `status=running`，调度器继续 |
| 取消 | `status=cancelled`，当前任务跑完即停，不再派发 |
| 回退一道 | 新增接口 `POST /runs/{id}/rewind {stage}`：把 stage 置回该道，清空该道之后的事件？**不清空**，追加 `phase(rewind)` 事件，调度器从该道重跑 |
| 重跑当前道 | `POST /runs/{id}/retry-stage`：同上，只重跑当前道 |

> 事件只追加、不删除，保证可回放；回退表现为事件流里出现第二次 `phase(build)`。

## 8.5 提问（ask_user）：任何阶段、不限数量

AI 拿不准时主动问，不等出错再返工。

- **谁能问**：六道工序都可以，通过 `ask_user` 工具
- **问多少**：不设上限（配置项默认 0 = 不限；以后要限再加）
- **怎么问**：一次批量列出，一轮答完；不同轮次分开弹窗
- **必须有默认**：没有“必答且无默认”的题
- **允许自由文本**：选项覆盖不了时直接写
- **答过不再问**：答案进 `ctx.answers`，后续阶段可见
- **出口**：用户可随时“全部按默认继续”；超时自动按默认继续（`auto: true`）

事件：`gate(round, stage, questions[])` → `gate.answered(round, answers[])`。

## 9. 检查点与续跑

- 每道工序完成时写一条 `checkpoint` 事件：`{ stage, artifacts: [...], eventSeq }`
- 进程重启后：读最后 checkpoint，从下一道继续
- 不做“任务级断点”（成本高、收益低）；最坏情况重跑当前道

## 10. 预算闸门

```
开跑前： budgetPerRun > 0 且 今日花费 < budgetPerDay，否则 402
每阶段： 累计成本 > budgetPerRun → 暂停 + error 事件
每次调用：先估算上限（max_tokens × 单价），超了就不发
```

## 11. 与现有代码的接口

```python
# app/pipeline/orchestrator/__init__.py
def start(run_id: str) -> bool: ...
def stop(run_id: str) -> None: ...
def status(run_id: str) -> str: ...
```

`runs/router.py` 只调这三个函数。

## 12. 线程模型

- 单进程 + 每 run 一个线程（现状即可）
- 线程内并发用 `ThreadPoolExecutor(max_workers=3)`
- 事件写入串行（DB 自增 seq + 行锁）
- 不使用 asyncio：现有代码是同步 SQLAlchemy，改造成本高

## 13. 编排器的可观测性

编排器自己的每一步也发事件：

```json
{"kind":"tool","name":"planner.build","args":{"stage":"build"},"ok":true,"latencyMs":1200}
```

这样评委能看到“主控在思考”，而不是只有结果。

## 14. 失败演示的开关

为了演示“失败与修复”，提供：

```
POST /runs/{id}/inject-failure { "stage": "test", "case": 2 }
```

只在演示模式可用；真实链路里失败应当自然发生，不注入。
