## 一、AI 技术深度（35 分）

### 1.1 官方考察点

| 考察点 | 分值 | 官方要求 |
|---|---:|---|
| 大模型集成质量 | 8 | 合理选择并高质量集成 LLM，Prompt 精巧，输出稳定可控 |
| Agent/工作流设计 | 8 | 实现 AI Agent 或复杂工作流，具备规划、工具调用、自主决策能力 |
| RAG 技术应用 | 6 | 实现 RAG 架构，检索策略合理，生成质量因检索增强而提升 |
| 多模态能力 | 5 | 集成文本、图像、语音、视频，多模态融合自然 |
| AI 安全与可控性 | 4 | 输出安全、可解释，有内容过滤与兜底 |
| MCP/工具集成 | 4 | 通过 MCP 或 Function Calling 集成外部工具/数据源 |

### 1.2 项目实际情况

**已经做到的：**

- 真实 DeepSeek 调用：`app/api/ai/model/client.py`
  - 支持 429 / 5xx 重试和指数退避
  - 记录 `prompt_tokens` / `completion_tokens` / `finish_reason`
  - 支持 `json_mode` 与结构化输出
- 六个阶段全部有真实处理逻辑：
  - `plan`：需求规格、验收标准、门禁提问
  - `design`：模块、文件、依赖、数据流
  - `build`：按依赖顺序逐文件生成，每个文件一个任务节点
  - `assemble`：入口、接线、启动配置
  - `test`：生成用例、起进程、发 HTTP 请求、失败回环修复
  - `deliver`：起预览进程、落产物、三层验收
- 门禁会真实暂停，等待用户回答后继续
- 测试失败会回环到构建阶段修复，最多两轮
- 每次模型调用都记成本，前端能看本轮花费
- 用户自己的 API Key 能注入，缺失时回退服务端 `.env`
- 构建顺序改为读架构阶段 AI 给出的依赖图，不再写死 `db → api → web`

**还没做到的：**

- `app/ai/rag/*` 四个文件都只有 docstring；`rag_documents`、`rag_chunks` 是 0 条
- `app/ai/agent/runtime.py`、`mcp/client.py`、`agent/tools/*` 都只有 docstring
- 没有 Function Calling，也没有 MCP 客户端
- 没有图像/语音/视频输入
- 有语法、SQL、HTML 结构校验，但没有内容过滤、Prompt 注入检测、敏感信息脱敏和安全审计
- 流式是“事件流 + 拿到完整内容后切块播放”，不是模型 token 级流式
- Skill 注册表 `app/api/skills/registry.py` 存在，但流水线没有使用它

### 1.3 预估评分：15 / 35

| 子项 | 满分 | 自评 | 理由 |
|---|---:|---:|---|
| 大模型集成质量 | 8 | 7 | 真调用、真重试、真成本、真结构化；扣在非 token 流式、无模型路由、无 Prompt 评测 |
| Agent/工作流设计 | 8 | 6 | 六道工序、门禁、重试、回环、预览都真实；扣在固定流水线、无工具调用、无动态决策 |
| RAG 技术应用 | 6 | 0 | 只有空模块和空表，`content/playbook` 只有 README |
| 多模态能力 | 5 | 0 | 没有任何图像/语音/视频输入 |
| AI 安全与可控性 | 4 | 2 | 有输入校验、语法校验、提示词约束；缺内容过滤、脱敏、审计、兜底策略 |
| MCP/工具集成 | 4 | 0 | MCP client、Agent runtime、tools 全是空壳 |
| **合计** | **35** | **15** |  |

### 1.4 理由展开

**为什么 LLM 集成能拿 7：**

评委能看到的是“真的在调模型”，而不是模板回复：

- 每次调用有真实 token 用量和成本
- 输出被校验，不合格会重试
- 构建阶段有三次尝试 + 最小实现兜底
- 测试失败会带错误回环
- Prompt 分阶段、有角色、有硬性格式约束

扣分点也很明确：模型返回是一次性的，前端“逐行写入”是后处理；设置页也不让用户选择模型。评委如果追问“为什么用 deepseek-chat、换模型会怎样”，目前没有答案。

**为什么 Agent 只能拿 6：**

严格说，当前是**固定流水线编排**，不是具备自主决策的 Agent：

- 下一阶段是写死的列表，不是模型决定
- 没有工具调用循环
- 没有 Agent 运行时
- “主控 Agent”目前只是 UI 上的一个根节点，不是真的调度器

但六道工序、门禁、任务事件、测试回环、真预览都是真实运行过的，所以不能算 0。

**为什么 RAG 是 0：**

不是“检索效果一般”，是完全没有检索：

```text
app/ai/rag/chunk.py     131 字节，只有注释
app/ai/rag/embed.py     136 字节，只有注释
app/ai/rag/retrieve.py  173 字节，只有注释
app/ai/rag/store.py      74 字节，只有注释
rag_documents           0 条
rag_chunks              0 条
```

**为什么多模态是 0：**

前端没有图片上传、没有麦克风、没有语音识别，也没有视觉模型调用。

**为什么安全只有 2：**

有基础工程安全：登录会话、文件路径校验、Python 编译、SQL 执行、HTML 结构检查。但没有面向 AI 的安全层：Prompt 注入、密钥泄露、输出内容过滤、安全审计都没有。

**为什么 MCP/工具是 0：**

官方允许 Function Calling 替代 MCP，但当前两者都没有：

```text
app/ai/agent/runtime.py  只有 docstring
app/ai/agent/mcp/client.py 只有 docstring
app/ai/agent/tools/*.py  只有 docstring
```

### 1.5 提分建议（按分/天排序）

| 动作 | 预计加分 | 工期 | 说明 |
|---|---:|---:|---|
| RAG：语料 + 切片 + 混合检索 + 依据展示 | +5.5～6 | 1.5 天 | 现有表结构、事件类型都留好了，性价比最高 |
| Function Calling 工具循环 | +3.5～4 | 1 天 | 同时补 Agent 的“工具调用”考察点 |
| 安全 guard：注入检测、脱敏、输出过滤、审计 | +2 | 0.5 天 | 不需要很深，能被评委看到即可 |
| Skill registry 接入 + 主控决策事件 | +1 | 0.3 天 | 不是独立评分项，但支撑 Agent 叙事 |
| 语音输入（Web Speech API） | +2～3 | 0.5 天 | 真多模态输入，不用额外 key |
| 真 token 流式输出 | +0.5～1 | 0.5 天 | 提升 LLM 集成质量与 AI 交互体验 |

**如果只做三项：RAG → Function Calling → 安全 guard。**  
AI 技术深度预计从 **15/35 提升到 26～28/35**。

## 二、创新性（25 分）

### 2.1 官方考察点

| 考察点 | 分值 | 官方要求 |
|---|---:|---|
| 选题创新 | 10 | 发现独特场景或未被满足的需求 |
| 技术方案创新 | 8 | AI 技术组合有新意，有独特方案 |
| 交互模式创新 | 7 | 人机交互方式有创新，超越传统模式 |

### 2.2 项目实际情况

**差异化点：**

1. **不是“代码生成器”，而是把开发过程做成可观察的流水线**
   - 六道工序对应真实软件流程
   - 树上的每个节点对应真实任务/文件
   - 代码流、任务状态、成本、验收结果都能对上

2. **自动模式 + 辅助开发双模式**
   - 工作流：AI 自己跑六道工序
   - 辅助开发：用户自己写代码，AI 按六阶段陪跑
   - 两个模式共用同一套阶段、代码检查、记忆

3. **门禁机制**
   - AI 在需求阶段主动停下来问用户
   - 用户答案会进入后续 Prompt，不是摆设

4. **过程透明**
   - 每个任务有 created / started / done / failed
   - 失败原因、重试、回环修复都展示
   - 成本按真实 token 估算

5. **AI 记忆**
   - 辅助开发中 AI 自主决定记什么，每天最多 3 条
   - 记忆只作用于辅助开发，不污染工作流

**不足：**

- 代码生成/开发辅助赛道已有 Cursor、v0、Claude Code 等强竞品，“AI 帮你写软件”本身不新
- 创新主要集中在“过程透明 + 双模式”，而不是底层 AI 技术组合
- 没有 RAG、工具调用、多模态这些能支撑“技术方案创新”的硬能力
- 交互仍以工作台/树/面板为主，没有对话式、生成式 UI 等新交互

### 2.3 预估评分：18 / 25

| 子项 | 满分 | 自评 | 理由 |
|---|---:|---:|---|
| 选题创新 | 10 | 7 | “开发过程全透明 + 自动/辅助双模式”有记忆点；但赛道内同类多 |
| 技术方案创新 | 8 | 7 | 六阶段编排 + 门禁 + 回环 + 双模式是组合创新；缺 RAG/工具调用，技术厚度不足 |
| 交互模式创新 | 7 | 4 | 树、任务、代码流、预览的联动不错；仍是仪表盘交互，没有新范式 |
| **合计** | **25** | **18** |  |

### 2.4 理由

- 给分点：把“AI 开发”从黑盒聊天变成可审计的流水线，这个叙事在比赛里是有辨识度的；双模式也解决了“全自动不可控、纯辅助不够 AI”的矛盾。
- 扣分点：评委看过很多“AI 生成网页”的作品，如果只演示“一句话生成待办清单”，创新性会被拉到普通水平。必须演示**过程控制**：门禁、失败回环、任务节点、成本、验收，而不是只演示结果。
- 另一个扣分点：没有 RAG/工具调用，技术方案创新只能靠“编排”，不能靠“新能力”。

### 2.5 提分建议

- 演示脚本把“透明过程”放在第一位，结果放第二位
- 增加“主控 Agent 决策”事件，让评委看到 AI 在选择下一步，而不是播固定动画
- 补 RAG 后，演示“AI 写代码时参考了项目规范”，这是技术组合创新
- 补工具调用后，演示“AI 自己读文件、跑检查、再修改”，这是 Agent 能力创新

## 三、前端工程质量（10 分）

### 3.1 官方考察点

| 考察点 | 分值 | 官方要求 |
|---|---:|---|
| 前端代码质量 | 4 | TypeScript 规范、组件结构清晰、可维护、无明显 Bug |
| 组件化与架构设计 | 3 | 组件划分合理、状态管理规范、模块解耦、可复用 |
| 前端性能优化 | 3 | 首屏、渲染性能、懒加载、代码分割、缓存 |

### 3.2 项目实际情况

**做得好的：**

- 页面结构清楚，目录按 `web/<page>/index.html + main.js + style.css` 组织
- 公共头部 `common/appbar.js`、公共样式 `common/app.css`、公共 API `common/api.js` 已抽离
- 工作台树、任务清单、代码流、预览、验收是真实交互，不是静态图
- CodeMirror 只在辅助开发页加载，没有全站引入
- 空态、加载态、错误态基本都有
- 版本号统一管理，静态资源可缓存

**不足：**

- 原生 HTML/CSS/JS，没有 React/Vue/Svelte，也没有 TypeScript
- 没有组件框架、没有状态管理库、没有构建工具
- 页面逻辑集中在单个 `main.js`，工作台 `main.js` 超过一千行
- 没有代码分割、懒加载、性能指标、Lighthouse 数据
- 没有 ESLint / Prettier / 单元测试
- 响应式只做了 CSS 断点，没有逐页移动端验证

### 3.3 预估评分：4 / 10

| 子项 | 满分 | 自评 | 理由 |
|---|---:|---:|---|
| 前端代码质量 | 4 | 2 | 结构可读，但无 TS/框架/规范工具，单文件偏大 |
| 组件化与架构设计 | 3 | 1 | 有公共层，但主要是页面级复用，没有组件化与状态管理 |
| 前端性能优化 | 3 | 1 | 静态资源轻、CodeMirror 按需；无构建优化、无性能数据 |
| **合计** | **10** | **4** |  |

### 3.4 理由

官方评分细则明确写了 **TypeScript 规范使用、React/Vue 等现代框架、组件化、状态管理、代码分割**。本项目是“无构建原生前端”，在这三项上天然吃亏。

但也不能算 0：页面能跑、交互完整、公共层有抽离、静态资源不重。评委如果实际打开页面，体验分（另 10 分）会明显高于工程分。

### 3.5 提分建议

时间不够，不建议重写。可做的低成本动作：

- README 里明确写“为什么选择无构建原生前端”：部署简单、无依赖、便于评审直接打开
- 给核心模块补 JSDoc 类型注释，展示类型意识
- 用 `performance.now()` 记录首屏/工作台渲染耗时，文档里给一组真实数据
- 把工作台 `main.js` 按“树 / 任务 / 代码流 / 预览”拆成几个文件，至少让结构更清楚

## 四、实用性（10 分）

### 4.1 官方考察点

| 考察点 | 分值 | 官方要求 |
|---|---:|---|
| 场景真实性 | 5 | 面向真实需求，问题定义清晰 |
| 解决方案有效性 | 5 | AI 方案真正解决问题，相比传统方案有明显优势 |

### 4.2 项目实际情况

**真实场景：**

- 目标用户：不会写代码或想快速验证想法的人、编程初学者、需要原型的小团队
- 真实痛点：从“一句话需求”到“能点开的软件”之间，有需求澄清、架构、编码、测试、部署多道门槛
- 当前能做的：输入一句话 → 门禁澄清 → 六道工序 → 生成文件 → 起进程 → 浏览器预览
- 已经真实跑通：待办清单项目，六道全部完成，产物在 `127.0.0.1:50000` 可访问

**优势：**

- 不是只给代码片段，而是给可运行产物
- 过程可观察，失败可定位，不是黑盒
- 辅助开发模式让“人写代码、AI 陪跑”也有价值

**不足：**

- 生成质量受模型波动影响，实测出现过测试阶段失败（生成的后端路由 404）
- 架构固定 3 个文件，复杂需求做不了
- 没有部署能力，产物只能本机预览
- 没有真实用户使用数据、满意度、效率对比

### 4.3 预估评分：8 / 10

| 子项 | 满分 | 自评 | 理由 |
|---|---:|---:|---|
| 场景真实性 | 5 | 4 | 需求真实，目标用户清楚；缺用户访谈/使用数据 |
| 解决方案有效性 | 5 | 4 | 真能生成可运行软件；稳定性与复杂度受限 |
| **合计** | **10** | **8** |  |

### 4.4 理由

这是项目的强项。评委只要看到“一句话 → 门禁 → 六道工序 → 真预览”，就能理解价值。

扣分主要在“有效性”的稳定性：模型偶尔生成的路由和测试期望不一致，导致流程失败。比赛演示要选稳定需求，并准备失败回环的演示段。

### 4.5 提分建议

- 准备 2 个稳定 demo：待办清单、习惯打卡；提前跑通并保存截图/录屏
- 文档里放“真实运行记录”：run id、阶段、耗时、成本、预览地址
- 明确边界：当前适合单页/小工具，不适合复杂系统
- 如果有真实同学试用，收集 3～5 条反馈，放进文档

## 五、用户体验（10 分）

### 5.1 官方考察点

| 考察点 | 分值 | 官方要求 |
|---|---:|---|
| UI 设计与视觉表现 | 4 | 界面美观、布局合理、响应式、设计系统统一 |
| 前端交互体验 | 3 | 路由流畅、动画自然、反馈及时、加载状态优雅 |
| AI 交互体验 | 3 | 流式输出、AI 思考状态可视化、错误边界优雅 |

### 5.2 项目实际情况

**做得好的：**

- 统一顶栏、品牌色、卡片、按钮、空态，页面之间视觉一致
- 工作台树 + 任务清单 + 代码流 + 预览 + 验收，信息层次清楚
- 任务清单支持按阶段收放，任务多时不乱
- 代码流有逐行写入效果，文件页签有状态
- 门禁弹窗、暂停/继续、取消、预览 iframe 都是真实交互
- 辅助开发有三态模式、检查结果、问题单、记忆引用
- 错误有中文提示，不是裸报错

**不足：**

- 不是真 token 流式，AI“思考中”的颗粒度不够细

- 错误恢复路径有限：测试失败后主要靠自动回环，用户不能手动改产物
- 没有引导/示例需求一键填入

### 5.3 预估评分：8 / 10

| 子项 | 满分 | 自评 | 理由 |
|---|---:|---:|---|
| UI 设计与视觉表现 | 4 | 3 | 统一、干净、有产品感；缺移动端打磨 |
| 前端交互体验 | 3 | 3 | 树/任务/代码/预览联动顺畅，状态反馈及时 |
| AI 交互体验 | 3 | 2 | 有事件流和代码流，但不是 token 流；错误边界一般 |

### 5.4 理由

视觉和主流程交互是强项，评委打开页面第一印象会不错。

扣分在“AI 交互”这一项：官网明确写了“流式输出渲染流畅、AI 思考状态可视化、错误边界处理优雅”。当前是事件流 + 后处理切块，思考状态只有一条事件文字，错误边界主要靠提示。

### 5.5 提分建议

- 辅助开发先接真 token 流式，演示“AI 正在想/正在写”
- 工作台加载时显示阶段骨架，不要空白
- 窄屏至少保证项目页、辅助页可用；工作台可以提示“建议桌面端”
- 给 3 个示例需求按钮，降低首次使用门槛

## 六、社会价值与商业潜力（10 分）

### 6.1 官方考察点

| 考察点 | 分值 | 官方要求 |
|---|---:|---|
| 社会价值 | 5 | 解决社会问题、促进公平包容、推动行业进步 |
| 商业潜力 | 5 | 有商业模式、市场空间、可持续发展 |

### 6.2 项目实际情况

**可以成立的叙事：**

- 降低软件开发门槛：不会写代码的人也能把想法变成可运行原型
- 编程教育：辅助开发模式可以作为教学工具，AI 按六阶段陪学生做项目
- 过程透明：让学生看到需求、架构、编码、测试、交付的完整流程，而不只是抄代码
- 中小企业/个人开发者：快速验证想法，减少从 0 到 1 的成本

**不足：**

- 没有真实用户数据、留存、付费意愿
- 没有明确商业模式：订阅？按次？教育机构采购？
- 没有成本模型：每次生成的真实模型成本、毛利
- 没有社会价值量化：帮助了多少人、节省了多少时间
- 当前更像“比赛作品/内部工具”，不是可运营产品

### 6.3 预估评分：4 / 10

| 子项 | 满分 | 自评 | 理由 |
|---|---:|---:|---|
| 社会价值 | 5 | 2 | 降低门槛/教育普惠的叙事成立；缺数据与落地 |
| 商业潜力 | 5 | 2 | 有目标场景；无商业模式、无客户验证、无成本模型 |
| **合计** | **10** | **4** |  |

### 6.4 理由

这一项不是靠功能补的，是靠“故事 + 数据 + 商业模式”补的。

当前文档主要在讲技术实现，没有讲清楚“为谁解决什么问题、为什么比现有方案好、怎么持续”。

### 6.5 提分建议（低成本）

- 技术文档加一页“社会价值”：编程教育、低代码门槛、过程透明
- 加一页“商业模式画布”：目标客户、价值主张、收入方式、成本结构
- 用真实运行数据算一笔账：一次生成平均 ¥0.04，传统外包/人力成本对比
- 找 3～5 位同学试用，记录反馈，哪怕样本小，也比“无数据”强
