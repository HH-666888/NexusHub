# 前后端分离契约书

> 版本 v1.3 · 2026-11-01
> 状态：**目标态（binding）**。文中凡标「现状」的条目是迁移前的行为，迁移完成后以本契约为准。
> 效力：这是前后端唯一的接口事实来源。**代码与本文件冲突时，以本文件为准；要改契约先改本文件**，再动代码。

---

## 0. 一句话

浏览器只与 Next.js（React 19）同源通信；Next.js 只渲染与代理，**不持有任何业务状态**；所有运行状态、事件、成本、产物、鉴权真相都在 FastAPI + 数据库侧。

```
浏览器 ──(同源 HTTPS)── Next.js ──(内网 HTTP, /api/* rewrite)── FastAPI ── DB / 向量库 / MCP / 模型
         EventSource                                    SSE 唯一出口
```

---

## 1. 五条总则（任何实现细节都不得违反）

| # | 总则 | 含义 |
|---|---|---|
| R1 | **单一真相源** | 运行状态、事件、成本、产物、会话，只有数据库是真相。前端与服务端内存都不得成为第二份真相。 |
| R2 | **同源** | 浏览器只看到 Next 一个源。跨服务通信靠 `rewrite`，**不引入 CORS、不引入第二域名的 cookie**。 |
| R3 | **契约生成** | 后端 Pydantic 模型是唯一来源，TS 类型由 OpenAPI 生成。**禁止手写第二份类型**。 |
| R4 | **JSON 一律 camelCase** | 后端用 Pydantic alias 输出 camelCase，与现有前端字段保持一致（`runId`、`costCny`、`createdAt`）。数据库列名可以是 snake_case，**JSON 不是**。 |
| R5 | **视图状态放 URL** | `?run=`、`?focus=`、`?new=1` 是唯一的界面状态来源。前端不得把"选中的运行"存进 localStorage 或全局 store。 |

## 2. 职责矩阵（这是最容易做错的部分）

### 2.1 归属表

| 能力 | 归属 | 说明 |
|---|---|---|
| 页面、路由、布局、组件渲染 | **前端** | `app/`、`components/` |
| 画布几何：布局、视口、缩放、聚焦跟随、森林排布 | **前端** | `core/canvas/*`（约 842 行纯函数）。**搬走即毁掉交互手感** |
| 动画时序（进出场、连线、聚焦过渡） | **前端** | 依赖 rAF 与本地几何，过网络就废 |
| 客户端事件流渲染（思考/正文/检查逐段追加） | **前端** | 只消费 SSE，不做业务判断 |
| 表单校验的即时反馈（仅限"空/超长"这类本地规则） | **前端** | 与后端校验重复时，**以后端为准** |
| 主题/外观的 CSS 变量应用 | **前端** | 配置内容来自后端 `GET /settings` |
| 鉴权（会话签发、校验、过期） | **后端** | Next 只透传 cookie |
| 密码哈希、登录失败限流 | **后端** | |
| 运行状态机（spec→arch→ui→build→verify） | **后端** | 前端只读 `stage`/`status` |
| 门禁判定（要不要停、停在哪、问什么） | **后端** | 前端只渲染 `GET /gate` 的结果 |
| Prompt 拼装、模型调用、截断重试、回流上下文 | **后端** | |
| 并行构建调度、并发上限、失败汇总 | **后端** | |
| 产物检查（8 项检查与探针） | **后端** | |
| 成本记账、预算闸门、单价档位 | **后端** | |
| 产物落盘、CSP 预览、导出/导入包 | **后端** | |
| RAG 检索、Agent 编排、工具调用、MCP 客户端 | **后端** | |
| 事件投影（outline / 画布节点数据） | **后端** | 前端拿到的是"该画什么"，不是"原始事件" |

### 2.2 一条判定规则

> **需要"多次读库/多次调用模型"才能算出来的，归后端；只依赖一次响应的纯计算与绘制，归前端。**

依据这条规则：`core/canvas`（纯计算、单次）留前端；`core/planning`（投影、需读事件）去后端；`core/domain` 的**类型**两边都有名字，但**定义权在后端**（见 §9）。

### 2.3 现状 → 目标 的路径映射

| 现状（frontend 内，尚未迁移） | 目标位置 | 动作 |
|---|---|---|
| `frontend/src/app/api/runs/[id]/generate/route.ts`（SSE + 生成编排） | `backend/app/api/runs.py` + `backend/app/pipeline/*` | 迁移 |
| `frontend/src/app/api/runs/[id]/{answers,acknowledge,gate,events,artifact,export}` | 同名，加 `/api/v1` 前缀 | 迁移 |
| `frontend/src/app/api/runs/import/route.ts` | `backend/app/api/runs.py` | 迁移 |
| `frontend/src/app/actions/{auth,run,settings}.ts`（Server Action） | 后端 API + 前端调用 | 改造 |
| `frontend/src/core/{pipeline,generate,planning,domain,run,settings,auth}` | `backend/app/**` | 迁移 |
| `frontend/src/adapters/**`（Drizzle/SQLite/模型） | `backend/app/adapters/**`（SQLAlchemy + MySQL 8 / Pydantic） | 重写 |
| `frontend/src/core/canvas/**` | **留在 `frontend/src/core/canvas`** | 不动 |
| `frontend/src/components/**` | `frontend/src/features/**` + `components/ui` | 不动 |
| `next.config.ts` 的 rewrite | 新增 `/api/:path*` → `http://127.0.0.1:8000/api/:path*` | 新增 |

> 完整的目录规定（每个目录放什么/不放什么、命名、粒度、反例）见 [`04-目录结构.md`](./04-目录结构.md)。本节只保留"从哪儿搬到哪儿"。

### 2.4 依赖方向（违反即 bug）

```
features ──▶ pipeline ──▶ ai ──▶ domain
    │            │         │
    └────────────┴─────────┴──▶ shared
```

| # | 规则 |
|---|---|
| D1 | `domain/` 不 import 项目内任何模块 |
| D2 | `ai/` 不 import `pipeline/`、`features/` |
| D3 | `pipeline/` 不 import `features/` |
| D4 | `features/` 之间不互相 import；协作走 `pipeline/` 或 `ai/` |
| D5 | 只有 `features/*/repo.py` 与 `db/` 可以 import SQLAlchemy |

这五条用 `import-linter`（后端）+ 一个 AST 脚本（前端）在 CI 里自动检查。**能自动检查的架构约束才是约束。**

## 3. 部署与同源规则

1. 浏览器只访问 `https://<域名>`（Next）。**FastAPI 不直接对外暴露**，仅监听 `127.0.0.1:8000`。
2. `next.config.ts` 里：

```ts
async rewrites() {
  return [{ source: "/api/:path*", destination: `${process.env.BACKEND_URL}/api/:path*` }];
}
```

3. `BACKEND_URL` 只走环境变量，默认 `http://127.0.0.1:8000`。
4. 三个进程（Next / FastAPI / MySQL 8）由同一份 `docker-compose.yml` 拉起；`/api/v1/health` 用于就绪探针。
   - MySQL 必须配 `healthcheck`，FastAPI 用 `depends_on: condition: service_healthy`；FastAPI 启动自身再重试 5 次（每次 2s），**不能靠"先启动就先赢"**。
   - `health` 里要带 `db` 字段（`ok` / `down`）：数据库连不上时，前端显示明确错误，而不是白屏或一直转圈。
5. **SSE 必须直通**：rewrite 不得缓存、不得压缩（见 §6.2）。
6. 从零到可演示必须 ≤3 条命令：`docker compose up -d` → `alembic upgrade head` → `python -m app.seed`（种子账号 + 外观默认值）。这条是 §11 的验收项。

## 4. 请求总则

### 4.1 认证

| 项 | 规则 |
|---|---|
| 机制 | HttpOnly cookie，名 `nexus_session`，值为不透明随机串 |
| 属性 | `Path=/; HttpOnly; SameSite=Lax; Secure`（本地开发可去 `Secure`） |
| 有效期 | 7 天，服务端存哈希，**不在 cookie 里放用户信息** |
| 校验 | 每个 `/api/v1/**`（除 `auth/*`、`health`）都要校验；失败返回 **401** |
| 归属 | 资源不属于当前用户时返回 **404**（不泄露 id 是否存在） |

### 4.2 错误信封

所有非 2xx 响应统一为：

```json
{ "error": { "code": "UNAUTHORIZED", "message": "未登录", "hint": "请先登录" } }
```

| HTTP | code | 场景 |
|---|---|---|
| 400 | `BAD_REQUEST` | 请求体不是合法 JSON、字段缺失 |
| 401 | `UNAUTHORIZED` | 无会话/会话过期 |
| 404 | `NOT_FOUND` | 运行不存在，或不属于当前用户 |
| 409 | `CONFLICT` | 状态不允许（例如没有规格就提交回答、重复确认） |
| 410 | `GONE` | 登记还在但文件丢失（产物不一致） |
| 413 | `TOO_LARGE` | 导入包超限 |
| 422 | `VALIDATION_FAILED` | 字段格式不对（`details` 里给逐条原因） |
| 429 | `RATE_LIMITED` | 登录/生成触发限流 |
| 500 | `INTERNAL` | 未预期错误，**不返回堆栈** |
| 502 | `UPSTREAM` | 模型侧失败（超时/限流/500） |

`message` 用中文给用户看，`code` 给程序判断。**前端不得按 `message` 做分支。**

### 4.3 数据类型约定

| 类型 | 规则 |
|---|---|
| 时间 | **毫秒时间戳整数**（`createdAt: 1730000000000`），UTC 语义，前端自己格式化 |
| 金额 | 元，`number`，最多 6 位小数（`costCny: 0.001234`）；**不传字符串** |
| ID | 运行 id 为 26 位以内的小写串；用户 id 为整数 |
| 枚举 | 小写下划线（`offPeak` 例外：保持现有 camelCase）——新增枚举一律小写 |
| 空值 | 缺省字段**不出现**，不要传 `null`；确实要表达"空"用 `null` 并写明含义 |
| 数组 | 无数据传 `[]`，不传 `null` |

### 4.4 幂等与并发

| 接口 | 规则 |
|---|---|
| `POST /runs` | 不幂等，但相同 `Idempotency-Key` 头 30s 内复用同一结果（防连点建出两条运行） |
| `GET /runs/{id}/stream` | **幂等**：已有产物直接回放，不重复计费 |
| `POST /runs/{id}/answers` | 幂等：同一 run 重复提交同一份答案不重复计费 |
| `POST /runs/{id}/acknowledge` | 幂等：重复确认返回 200 |
| `DELETE /runs/{id}/artifacts` | 幂等：没有产物时也返回 200 |

### 4.5 大小与超限

| 项 | 上限 |
|---|---|
| 请求体（JSON） | 1 MB |
| 导入包 | 20 MB |
| 单条事件 `delta` | 64 KB |
| SSE 单帧 | 256 KB |

---

### 4.6 数据层约定（MySQL 8）

数据库定为 **MySQL 8.0+ / InnoDB**（决策记录见附录 C）。**表结构、索引、DDL、备份与保留策略见 [`05-数据库契约.md`](./05-数据库契约.md)**，本节只规定**跨端必须一致**的几条口径。

以下是对齐口径，任何一条不合规都算 bug。

| 项 | 规定 |
|---|---|
| 引擎 | InnoDB（默认）。**不用 MyISAM**，它没有事务和行锁 |
| 字符集 | 库/表/连接三处都 `utf8mb4`；排序规则 `utf8mb4_0900_ai_ci` |
| 时区 | 连接固定 `time_zone='+00:00'`；业务时间一律存 **epoch 毫秒 BIGINT**，不用 `DATETIME` |
| 主键 | 用户 `BIGINT AUTO_INCREMENT`；运行/会话 id 为 `VARCHAR(26) CHARACTER SET ascii COLLATE ascii_bin`（十六进制串，用 ascii 存省 4 倍且比较更快） |
| 外键 | 真实外键 + `ON DELETE CASCADE`：`run_events / cost_records / artifacts` 挂 `runs`，`sessions` 挂 `users`。**不靠应用层保证级联** |
| JSON | 用原生 `JSON` 列（MySQL 8 支持）。**注意 JSON 列不能直接建索引**，需要检索时加生成列 + 索引 |
| 事件写入 | 必须多行批量 `INSERT INTO run_events (...) VALUES (...),(...),...`，与前端事件的 250ms/4000 字合并对齐；一次生成的开销从几百次往返降到几十次 |
| 索引 | `run_events(run_id, seq)` 唯一；`cost_records(run_id, created_at)`；`runs(user_id, created_at DESC)`；`sessions(expires_at)` |
| `sql_mode` | 开 `STRICT_TRANS_TABLES`，禁止静默截断；`ERROR_FOR_DIVISION_BY_ZERO` 一并开 |
| 连接池 | SQLAlchemy `pool_size=5, max_overflow=10, pool_pre_ping=True, pool_recycle=1800`（小于 MySQL 默认 `wait_timeout`，避免死连接） |
| 迁移 | Alembic。MySQL 的 DDL **不是事务性的**，所以每次迁移只做一件事，且必须能重复执行（`IF NOT EXISTS` 一类） |
| 全文检索 | 中文用 `FULLTEXT ... WITH PARSER ngram`（见 §14 的 RAG 方案），默认分词器对中文无效 |

---

### 4.7 限流（固定值，不靠"看情况"）

| 接口 | 上限 | 维度 | 超限响应 |
|---|---|---|---|
| `POST /auth/login` | 5 次 / 分钟 | IP | 429 `RATE_LIMITED` |
| `POST /auth/register` | 3 次 / 分钟 | IP | 429 |
| `POST /runs` | 10 次 / 分钟 | 用户 | 429 |
| `GET /runs/{id}/stream` | 3 个并发连接 | 用户 | 429 + `Retry-After: 5` |
| 其它 `GET` | 120 次 / 分钟 | 用户 | 429 |

429 必须带 `Retry-After`（秒）。限流计数放内存即可（单 worker），**不引入 Redis**。

### 4.8 分页

| 项 | 规定 |
|---|---|
| 方式 | 游标分页（cursor），不用 `offset` |
| 入参 | `?limit=20&cursor=<opaque>`，`limit` 上限 50，默认 20 |
| 游标内容 | `base64("${createdAt}:${id}")`，按 `createdAt DESC, id DESC` 排序 |
| 出参 | `{ items: [...], nextCursor: string \| null }`；没有更多时 `nextCursor: null` |
| 稳定性 | 新增运行不会导致翻页重复或漏项（游标是位置，不是偏移） |

## 5. REST 接口清单

统一前缀 `/api/v1`。下表「现状」列指出与当前实现的差异。

### 5.1 认证

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/auth/register` | `{username, password, confirmPassword}` | `200 { user }` + Set-Cookie |
| POST | `/auth/login` | `{username, password}` | `200 { user }` + Set-Cookie |
| POST | `/auth/logout` | — | `204` |
| GET | `/auth/me` | — | `200 { user }`，无会话时 `401` |

`user`：`{ id: number, username: string, displayName: string }`

> 现状：注册/登录是 Next Server Action 表单（带 `$ACTION_ID` 隐藏字段）。迁移后改为上面的 JSON 接口，Next 的表单直接 POST 到同源 `/api/v1/auth/*`。

### 5.2 运行

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/runs` | `?limit=20&cursor=` | `{ items: RunSummary[], nextCursor: string \| null }` |
| POST | `/runs` | `{ prompt: string }`（1–2000 字） | `201 { run: Run }` |
| GET | `/runs/{id}` | — | `{ run: Run, artifact: Artifact \| null }` |
| DELETE | `/runs/{id}` | — | `204` |

`RunSummary`：`{ id, prompt, stage, status, totalCostCny, createdAt, timeLabel }`
`timeLabel` 由后端算（"3 小时前"这类相对时间），**理由**：服务端时间是权威，避免 SSR 与水合不一致。

> 现状：列表/详情由 Server Component 直接查库；创建/删除走 Server Action。迁移后全部走上面 4 个接口，Next 在 SSR 时内部 fetch。

### 5.3 生成与门禁

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/runs/{id}/stream` | 见 §6 | `text/event-stream` |
| GET | `/runs/{id}/events` | `?afterSeq=0` | `{ runId, events: StoredEvent[] }` |
| GET | `/runs/{id}/gate` | — | `GateView`（见 §8.5） |
| POST | `/runs/{id}/answers` | `{ answers: [{question, answer}], revise?: boolean }` | `{ ok: true, answered: number, blank: number }` |
| POST | `/runs/{id}/acknowledge` | `{}` | `{ ok: true, status }` |
| DELETE | `/runs/{id}/artifacts` | — | `{ ok: true }` |

> 现状差异两处：
> 1. 「清空重跑」现在是 `DELETE /runs/{id}/generate` —— 语义含糊（删除的是产物，不是 generate 这个动作），目标改名 `DELETE /runs/{id}/artifacts`。
> 2. `answers` 的 `answers[].question` 现在是原问题字符串，契约冻结为**字符串**；需要 id 时另加 `questionId`，不得改变 `question` 的含义。
> 3. `/answers` 现状的错误响应是 `{ ok: false, error: "…" }`，与 §4.2 的统一错误信封不一致 —— 迁移时**统一到信封**，前端按 `error.code` 分支。

### 5.9 内部运行时（runtime）

这是**前后端之间**的接口，不是浏览器调用的：Next 侧生成代码、把文件写到磁盘后，调后端把"数据库 + 容器 + 验证"跑起来。

- 只监听 `127.0.0.1`，且必须带请求头 `x-internal-token: <INTERNAL_TOKEN>`；缺 token 一律 401。
- 一个 run 最多一个容器、一个数据库；重复 start 返回同一个（幂等）。
- 所有耗时操作都有上限：启动 60 秒、验证 180 秒，超时返回 `RUNTIME_TIMEOUT`。

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/runtime/databases` | `{ runId }` | `201 { dbName, dbUser, dbPassword }` |
| DELETE | `/runtime/databases/{runId}` | — | `204` |
| POST | `/runtime/{runId}/start` | `{ filesDir, entryPort? }` | `201 { containerId, hostPort, previewUrl, status }` |
| POST | `/runtime/{runId}/stop` | — | `204` |
| GET | `/runtime/{runId}/status` | — | `{ status, previewUrl?, exitCode? }` |
| POST | `/runtime/{runId}/verify` | `{ previewUrl, dbName, dbUser, dbPassword }` | `200 Verdict` |

`Verdict` 形状（与 `verdict.json` 同一份）：

```json
{
  "layers": [
    { "layer": "db",  "passed": 3, "total": 3,
      "checks": [{ "name": "表 todos 存在", "pass": true, "detail": "12 行种子数据" }] },
    { "layer": "api", "passed": 5, "total": 6,
      "checks": [{ "name": "GET /todos", "pass": false, "detail": "500: relation todos does not exist" }] },
    { "layer": "ui",  "passed": 2, "total": 2,
      "checks": [{ "name": "页面能加载", "pass": true, "detail": "标题：记账本" }] }
  ],
  "passed": 10,
  "total": 11,
  "screenshots": ["shot-1.png"]
}
```

错误码（沿用 §4.2 信封）：`RUNTIME_UNAVAILABLE`（docker 不可用）、`RUNTIME_TIMEOUT`、`DB_PROVISION_FAILED`、`PORT_EXHAUSTED`、`VERIFY_FAILED`（验证跑完但有失败项，仍返回 200 的 Verdict，不抛错）。

## 6. SSE 契约

### 6.1 帧格式

```
data: {"kind":"text","delta":"<div"}\n\n
```

- **只用 `data:` 行，不设 `event:` 名** —— 事件类型在 `payload.kind`。理由：与现有实现一致，且前端一个 `onmessage` 就能接全部分支。
- 一帧一个 JSON 对象，**不得**把多个事件塞进一帧。
- 心跳：服务端每 15 秒发一个注释帧 `: ping\n\n`（浏览器不会触发 `onmessage`，但能保活）。

### 6.2 响应头

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-store, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

`no-transform` 与 `X-Accel-Buffering: no` 都必须有 —— 任一层压缩或缓冲，用户看到的就是"卡住不动的流"。

### 6.3 生命周期

| 场景 | 行为 |
|---|---|
| 首次请求 | 从规格化开始跑；每产出一个事件立即 flush |
| 已完成的 run（有 html 产物） | **回放**：只发已有事件与 artifact，不调用模型、不计费 |
| 断点续跑（有 spec/arch/ui 产物但没跑完） | 复用已有产物，只跑缺的部分 |
| 门禁暂停 | 发 `phase(awaiting)` 后**关闭连接**，前端转为渲染 `GateView` |
| 完成 | 发 `artifact`（如有）与 `phase(done)` 后关闭 |
| 出错 | 发 `error` 后关闭，HTTP 状态仍是 200（流已开始） |

### 6.4 事件顺序（偏序，不是全序）

契约只保证这些**必须成立**的关系，其余顺序不作承诺：

1. `spec` 一定在第一个 `phase(spec)` 之后
2. `arch` 在 `spec` 之后，`ui` 在 `arch` 之后
3. `modules` 一定在 `phase(build)` 之后、`artifact` 之前
4. `usage` 与它所属的那次模型调用相邻（同一阶段内）
5. 最后一个事件一定是 `phase(done)` 或 `error`
6. 任何 `reasoning`/`text` 片段都不得跨越 `phase` 边界

前端**不得**依赖 "ts 严格递增" 以外的时序假设。

### 6.5 重连

浏览器 `EventSource` 自带重连。重连即重新 `GET /stream`，服务端按 §6.3 判定是回放还是续跑，**不会重复计费**。前端不得自行实现重连退避。

## 7. 事件清单

`kind` 是判别字段。下表 Status 列：`现状`=已实现，`计划`=契约已定、实现待做。

| kind | Status | 字段 |
|---|---|---|
| `phase` | 现状 | `phase: string`、`label: string`、`note?: "callback"` |
| `reasoning` | 现状 | `delta: string` |
| `text` | 现状 | `delta: string` |
| `spec` | 现状 | `spec: AppSpec`、`gate: SpecGate`、`fallback: boolean` |
| `arch` | 现状 | `arch: ArchSpec`、`check: ArchCheck`、`fallback: boolean` |
| `ui` | 现状 | `ui: UiSpec`、`check: UiCheck`、`fallback: boolean` |
| `modules` | 现状 | `batch: BuildBatchSummary`（**摘要，不含代码**） |
| `usage` | 现状 | `usage: TokenUsage`、`costCny: number`、`priceTier`、`model`、`latencyMs`、`truncated` |
| `check` | 现状 | `results: CheckResult[]`、`summary: CheckSummary` |
| `artifact` | 现状 | `artifact: Artifact` |
| `error` | 现状 | `message: string`、`hint?: string` |
| `tool` | 计划 | `name: string`、`args: object`、`result?: string`、`ok: boolean`、`latencyMs: number` |
| `retrieval` | 计划 | `query: string`、`hits: [{ source: string, snippet: string, score: number }]`、`latencyMs` |
| `cost` | 计划 | `stage: string`、`deltaCny: number`、`totalCny: number` |
| `sql` | 计划（全栈） | `statement: string`、`rowsAffected?: number`、`ok: boolean`、`error?: string` |
| `exec` | 计划（全栈） | `containerId: string`、`phase: "creating"\|"running"\|"exited"\|"killed"`、`exitCode?: number` |
| `verdict` | 计划（全栈） | `layer: "db"\|"api"\|"ui"`、`checks: CheckResult[]`、`passed: number`、`total: number` |
| `preview` | 计划（全栈） | `url: string`、`ready: boolean` |

三条硬规则：

1. **新增 kind 必须先改本文件**，前端遇到未知 kind 必须**忽略而不是崩溃**。
2. `phase` 的 `label` 是给人看的中文，**前端不得按 label 文本判断阶段**，判断一律用 `phase` 字段。
3. 事件里只放**可展示数据**，不放密钥、不放完整源码（代码走产物）。

## 8. 领域模型（关键字段）

> 完整字段以 `backend/app/models/*.py` 的 Pydantic 模型为准；本节列出**跨端共享**的部分，用于人工核对。

### 8.1 Run

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 运行 id |
| `prompt` | string | 用户原话，一字不改 |
| `stage` | enum | `spec`/`arch`/`ui`/`build`/`assemble`/`verify` |
| `status` | enum | `running`/`paused`/`done`/`failed`/`cancelled` |
| `totalCostCny` | number | 累计花费（元） |
| `usage` | TokenUsage | 累计 token |
| `createdAt`/`updatedAt` | int | epoch ms |
| `workflowVersion` | string | `v1` |

> **`paused` 与 `awaiting` 不是一回事**：`paused` 是运行状态（门禁停下、等用户回答）；`awaiting` 只是 SSE 的一个 `phase` 值。前端判断"要不要显示门禁表单"看 `status === "paused"`，**不要**看 phase。

单道工序（stage）另有自己的状态：`pending` / `running` / `passed`，与运行的 `status` 无关，不得混用。

### 8.2 AppSpec

| 字段 | 类型 |
|---|---|
| `prompt` | string（原话） |
| `goal` | string |
| `audience` | string |
| `scenarios` | string[]（按重要性排序） |
| `acceptance` | `{ id, text, kind }[]` |
| `scope` | `{ inScope: string[], outOfScope: string[] }` |
| `questions` | string[]（非空时门禁触发） |
| `model`/`generatedAt` | string / int |

### 8.3 Artifact / CostRecord

| 模型 | 字段 |
|---|---|
| `Artifact` | `id: number`、`runId: string`、`kind: "html"\|"json"`、`name: string`（如 `spec.json`、`plan.html`）、`bytes: number`、`sha256: string`、`createdAt: int` |
| `CostRecord` | `runId`、`stage`、`model`、`inputTokens`、`outputTokens`、`thinkingTokens`、`cacheHitTokens`、`costCny`、`priceTier`、`latencyMs`、`createdAt` |

> **产物内容存库、不落磁盘**（见 [`05-数据库契约.md`](./05-数据库契约.md) §3.6）。所以 `Artifact` 里没有 `path`，只有 `name`；内容通过 `GET /runs/{id}/artifact` 取。同一 run 的同名产物只保留最新一份。

### 8.4 TokenUsage

`{ input: number, output: number, thinking: number, cached?: number }`
—— **thinking 计入 output 预算**，这条是全局不变量，前后端都不得改写含义。

### 8.5 GateView

```json
{
  "runId": "…",
  "status": "paused",
  "hasSpec": true,
  "spec": { "goal": "…", "audience": "…", "acceptance": [], "outOfScope": [], "questions": ["…"] },
  "gate": {
    "active": true,
    "pending": ["问题 1"],
    "answered": [{ "question": "问题 1", "answer": "…" }],
    "acknowledged": false,
    "overrideNote": null
  }
}
```

`hasSpec: false` 时 `spec` 与 `gate` 都为 `null`（运行还没跑到规格化）。**前端必须处理这个分支**，不能假定 spec 一定存在。

## 9. 类型生成与 CI 门禁

链路（前两步是命令，第三步是门禁）：

```bash
# 1. 后端导出 OpenAPI（key 排序 + 2 空格缩进，diff 才有意义）
cd backend && python -m tools.export_openapi openapi.json

# 2. 前端生成类型（@hey-api/openapi-ts，显式支持 TypeScript 6）
cd frontend && npm run gen:types          # → src/api/generated/{types.gen.ts, index.ts}

# 3. 门禁：生成物必须与提交一致
cd frontend && npm run verify:types
```

约定：

1. **`src/api/generated/` 是产物，禁止手改**；也不许在别处复写同一份 interface。
2. 前端只通过 `src/api/client.ts` 发请求、解析错误信封 —— 组件里不出现 `res.ok` / `res.status`。
3. SSE 由 `src/api/sse.ts` 封装，未知 kind 必须忽略（见 §7）。
4. 为什么不是更常见的 `openapi-typescript`：它最高 7.x，peer 只到 TypeScript 5，而项目用 6；
   靠 `--legacy-peer-deps` 硬装等于给以后埋雷。
5. CI 三条：`npm run verify:types` 无 diff、后端 pytest 全绿、前端 `tsc --noEmit`。

**理由**：双语言项目里唯一会致命的是契约漂移。这条不做，"规格改了但事件没改"一定会重演。

## 10. 禁止清单

### 前端不得

1. 直连模型 API，或持有任何密钥（含 `NEXT_PUBLIC_*` 形式的密钥）
2. 自行推断运行阶段/门禁状态（只能读 `stage`、`status`、`GateView`）
3. 把运行状态写进 localStorage / 全局 store 当缓存（URL 是唯一视图状态）
4. 按 `error.message` 文本做分支（只能按 `error.code`）
5. 依赖文档未承诺的事件顺序（见 §6.4）
6. 在客户端做"是否需要门禁"这类业务判断

### 后端不得

1. 返回 HTML 片段给 React 渲染（除产物预览本身）
2. 依赖前端传来的派生数据（例如前端算好的 outline）
3. 在 SSE 里返回未在 §7 登记的事件类型
4. 返回堆栈、SQL、内部路径
5. 把 `timeLabel` 这类展示用的相对时间交给前端算（服务端是时间权威）
6. 直接信任 `answers[].question` 的内容与顺序 —— 一律以服务端 `pending` 为准，做子集校验

## 15. 附录 C：ADR-001 数据库选型（MySQL 8）

| 项 | 内容 |
|---|---|
| 决策 | 采用 **MySQL 8.0+ / InnoDB**，作为唯一数据存储（含 RAG 语料与向量） |
| 背景 | 后端迁移到 Python FastAPI；RAG 占评分 6%，需要一个检索方案 |
| 备选 | ① SQLite：零运维、单文件可复现，但单写者、无库级权限、向量要 `sqlite-vec`；② Postgres+pgvector：向量原生，但团队不熟；③ MySQL 8：团队已在学、国内教学/评委心智最正 |
| 理由 | ① **团队熟练度**是真实收益：把学习成本从"新库"转到"AI 能力"上；② 与"Python 企业级后端"的叙事一致，答辩不需要为数据库额外解释；③ 多 worker/多实例的天花板打开，不必二次搬库；④ 关系数据与向量数据同库，部署面仍是三个进程 |
| 代价 | ① MySQL 社区版**没有原生向量索引**；② DDL 非事务性，迁移要小步；③ 比 SQLite 多一个需要保活的服务 |
| 向量的处理 | embedding 存 `BLOB`（`FLOAT32` 小端序）或 `JSON`；语料 <1 万块时用 **numpy 精确余弦**（毫秒级、无近似损失）；中文关键词召回用 `FULLTEXT ... WITH PARSER ngram`；两路结果加权合并成混合检索。**规模上去再换 FAISS/Chroma，接口不变** |
| 何时重新考虑 | 单次检索语料 >5 万块，或需要多实例共享索引时，换 pgvector 或独立向量库 |
| 不做的事 | 不引入第二个数据库（Chroma/Qdrant/Milvus）作为 RAG 的前置条件 —— 先证明检索有效，再谈规模化 |
