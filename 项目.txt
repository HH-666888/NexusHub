Nexus 以软件开发为目的驱动的agent工作流编排工具（web形态）：
一个网页里的软件工厂。一句话进去，技术方案、界面设计、功能开发、集成交付、自动化测试全程由 AI 自主完成并自主验收——全程可见、可干预、可预算。


项目目标：从一句话的软件开发提示词实现到可交付的完整产品


项目流程：以软件开发流程为工作流编排流程，每个流程分组分块自动执行，每个流程阶段内部由agent自治，流程是确定性状态机


项目agent控制：分组控制，每个流程组用同样的方式实现agent控制，agent控制形态为双层agent控制（主核心agent，子分配agent）


项目结构：
流程层（确定性，纯代码，零 token）
  需求 → ①方案 → ②UI设计 → ③功能实现 → ④集成交付 → ⑤自动化测试
         │        │          │           │            │
阶段层（概率性，每阶段一个完整小组）
  ┌──────────────────────────────────────┐
  │  阶段主 Agent（本阶段的规划 + 验收）    │
  │      ↓ 并行派发                        │
  │  执行 Agent × N（本阶段的具体实现）     │
  │      ↓ 产出结构化产物                  │
  │  阶段主 Agent 验收 → 不过则局部重试      │
  └──────────────────────────────────────┘
这解决了前面一直没解决的成本矛盾——如果连"下一步走哪"都问模型，复杂度是乘法级的。现在流程层零 token，模型只花在真正需要智能的地方。阶段自治的分层 Agent 编排：每一道工序，都是一个有规划、有执行、有验收的完整 AI 小组。


关键性问题指出：

1. 双层架构不是成本方案，是可控性方案，分层不是为了省钱，是为了让"失控"被关在最小的格子里。一个阶段失败了，只有那个阶段的上下文要重建，不是整个任务重跑。这才是分层的价值。省钱的机制必须仍然靠那三条：动态路由、失败归因、上下文预算。分层 = 可控性；路由 = 成本；归因 = 成功率。

2. "流程设计"的正解，也是这个方案真正的技术内核，阶段契约是整个架构的生死线。分层多智能体最经典的失败模式是层间信息丢失：UI 设计阶段产出的东西，功能实现阶段读不懂，最后每个阶段各自为政，拼不起来。每个阶段必须产出一个结构化、可机器校验的产物，而不是一段自然语言描述。真正的风险不是"阶段失败"，而是"阶段无法自我判定失败"——上游产物看着合格、下游用不了。这就是为什么那张契约表必须是结构化 + 可机器校验的。
	额外好处：
	1），它让"流程可视化"变成了"结构可视化"——页面上的每个阶段卡片可以显示"契约是否满足"，而不是显示一句模糊的"进行中"。这是"AI 交互体验 3%"的硬答案。
	2），它让失败归因变得极清晰——阶段边界有明确验收标准，失败立刻能分成两类：上游产物不合格（打回上一阶段）还是本阶段实现有问题（局部重试）。这比我上一轮讲的四分类更干净。
	3），它让上游错误无法伪装通过——自然语言描述可以"看起来对"，schema 和验收清单不会。

3. 五个阶段串成直线就是瀑布模型，要留回退回路。技术方案 → UI → 实现 → 交付 → 测试，如果严格单向，就是瀑布模型。而瀑布模型的缺点，是软件工程课上被反复讲的。
	解法：骨架线性，但带反馈回路。每个阶段内部迭代（agent 自己循环到过验收标准为止）
	1），阶段之间允许回退（测试阶段发现是架构问题 → 打回①重做，只重跑受影响的下游）
	2），这样它就不是瀑布，而是"带反馈回路的阶段化流水线"——比纯瀑布可控，比纯自治 agent 可解释。
